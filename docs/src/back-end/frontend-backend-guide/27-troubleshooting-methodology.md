# 问题排查方法论

有人反馈：“任务列表一直转圈，刚才还好好的。”你打开后端代码，却不知道该从哪个类看起。

先不要改代码。我们按这一次反馈往下查，看看怎样把“好像哪里坏了”，一步步变成一个能验证的问题。下面的时间、日志和耗时都是讲解用的示意，不是本仓库运行记录。

本页按需阅读，不要求先搭微服务。想查某个具体症状，可以直接去 [排查实战手册](/back-end/frontend-backend-guide/28-troubleshooting-playbook)；已经知道要看线程或内存，再去 [诊断工具箱](/back-end/frontend-backend-guide/29-diagnostic-toolbox)。第一次学习仍可沿 [五阶段主线](./index) 继续。

## 27.1 先把“转圈”说清楚

同样是页面转圈，可能是浏览器根本没发出请求，也可能是接口返回了错误，或者请求成功但数据一直没有更新。先在浏览器 Network 中找到对应请求，记下请求路径、时间、状态码和实际耗时。涉及账号或业务数据时，用脱敏后的请求信息沟通，不要把登录凭据一起发到群里。

假设这次看到的是：从 14:02 开始，`GET /api/tasks` 有一部分请求等了约 5 秒，最后返回 504；其他接口暂时正常。现在的问题就不再是“系统挂了”，而是“任务列表接口出现部分超时”。

接着在网关或接口监控中选择同一时间段、同一路径，比较请求量、超时数量和正常时段。浏览器里的一次失败能说明这个用户遇到了问题，不能说明所有用户都失败。HTTP 200 的请求也要看响应内容，不能只按状态码判断业务是否正常。

同时问一下最近有没有发版、改配置、调整数据库或改变依赖服务。假如 14:00 刚发布过查询条件的改动，它值得优先检查；但“时间挨得近”还不是因果关系，后面仍要验证。

如果影响已经很大，这时就通知值班负责人，按现有故障流程决定是否回滚或限制流量。恢复服务与继续定位可以并行，不必为了走完下面的步骤，让故障一直持续。

## 27.2 沿着一个慢请求，找到时间花在哪里

有了时间和路径，下一步是找一条具体的失败请求。系统如果已经接入链路追踪，可以从对应时间段筛选慢请求，点开它的 trace。还没有链路平台时，可以用请求标识查现有日志。

例如，已确认应用日志位于 `/var/log/task-api/app.log`，并且包含这次请求的 `traceId`：

```bash
grep -n -A 20 'traceId=demo-slow-001' /var/log/task-api/app.log
```

路径和标识都要换成实际值。这条命令只能找到已经记录下来的信息，不能替应用补出不存在的分段耗时。`-A 20` 还可能带出其他并发请求的日志，要继续核对请求标识。

假设日志中有这些计时：

```text
14:02:11.100 traceId=demo-slow-001 GET /api/tasks start
14:02:15.920 traceId=demo-slow-001 taskRepository.findPage cost=4800ms
14:02:15.940 traceId=demo-slow-001 response total=4840ms
```

总耗时约 4840ms，其中查询调用占了 4800ms。下一步就围绕查询查，而不是先去调整 HTTP 线程数。

不过，“查询调用用了 4800ms”还不能直接等同于“SQL 执行用了 4800ms”。这段调用里可能包括等待连接、执行查询、网络传输和读取结果。如果有数据库 span 或连接池指标，就继续把这一段拆开。请求在各层之间怎样流转，可回看 [请求生命周期](/back-end/frontend-backend-guide/03-request-lifecycle)。

多服务系统也一样：调用方等下游花了 4.8 秒，只说明慢发生在这次调用期间。要结合下游收到请求的时间、内部耗时和网络情况，才能继续区分。没有接入或正确传播追踪上下文时，也不一定每层都有同一个 traceId。

## 27.3 提一个能被推翻的判断

现在可以提出一个具体猜测：“这次发布新增了筛选条件，任务查询可能扫描了过多数据。”它比“数据库有问题”更有用，因为能写出下一步检查什么、什么结果会推翻它。

先取这条慢请求实际执行的 SQL、参数范围和对应的慢查询记录，再用普通 `EXPLAIN` 查看执行计划。检查过程见 [SQL 与索引](/back-end/frontend-backend-guide/10-sql-and-indexes)。只读排查也应使用授权账号，并确认查询范围；不要为了验证猜测，直接在生产重放大查询。`EXPLAIN ANALYZE` 会实际执行语句，也不能和普通 `EXPLAIN` 混用。

假设检查得到：同类查询的扫描行数明显增加，执行计划没有使用预期索引，数据库记录的执行时间也接近 4.8 秒。这些结果一起，才支持“查询方式不合适”这个方向。

反过来，如果 SQL 执行只用了 20ms，但获取连接等了 4.7 秒，就应转查连接是否被长期占用、事务是否过长，而不是继续加索引。若看到锁等待，再沿 [事务与一致性](/back-end/frontend-backend-guide/11-transactions-consistency) 检查持锁事务。

排查不是每找出一点异常就改一次配置，而是让检查结果决定下一步。猜测没被支持，就收回它，不要把没验证的改动越叠越多。

## 27.4 用同样条件验证，而不是看到一次变快就结束

假设准备在隔离测试环境优化查询。先保留原版本的请求参数、数据规模和并发条件，记录修改前的延迟、错误数和数据库负载；只调整这一处查询或索引，再按相同条件比较。

如果耗时下降、扫描行数减少，且结果内容一致，才有理由认为改动有效。如果只在数据量很小的本机请求了一次，不能据此判断高峰期也会改善。

直接请求接口有时可以帮助缩小范围，但要先确认它有没有副作用。本例是列表读取；扣费、扣配额、提交任务这类写接口，不能拿来随意反复调用。即使一次直接请求返回 200 且耗时 4.8 秒，也只能说明“这次请求成功但很慢”，不能单凭它排除网络、证明某条 SQL 就是原因。

有些问题只出在一个实例。此时可以比较正常和异常实例的版本、配置、请求分布及资源趋势，但“版本相同”不能排除代码问题：同一段代码可能只被某类数据触发。CPU 高、内存高、GC 多也只是检查方向，仍需线程栈、GC 日志或堆分析进一步解释。相关原理见 [OOM 与内存泄漏](/back-end/frontend-backend-guide/20-oom-memory-leak)。

## 27.5 必须先恢复时，怎样尽量留下信息

如果用户影响继续扩大，负责人可能决定回滚刚才的版本。回滚前若时间允许，先保存故障时间段、请求标识、应用日志和监控图。这些通常比立即生成一份大堆转储更容易取得。

只有已经怀疑线程阻塞，且有相应权限时，才考虑采集线程栈。例如在目标 Java 进程所在环境中，确认 PID 为 `12345` 后：

```bash
jstack 12345 > /tmp/task-api-stack-1405.txt
```

采集需要匹配的运行用户、JDK 工具和进程可见性，也可能带来短暂停顿。先确认输出目录的权限和空间，保存后核对文件不是空的。线程栈中如果有很多请求线程停在同一处远程调用，应继续检查该调用的耗时与超时配置；仅有 `WAITING` 状态不能说明线程池已经耗尽。线程池的读法见 [线程池与 Executor](/back-end/frontend-backend-guide/15-thread-pools-executor)。

堆转储可能触发 GC、较长停顿并写出很大的文件，里面还可能包含密码、token 和业务数据。它不是“每次重启前必须做”的操作；只有确实需要分析内存、资源允许并经授权时才采集。生成后按敏感资料保存，不要上传到公开问题单。

摘流量、重启、扩容和回滚都要走团队已有流程。不要临时删除 Pod 的管理标签来“留现场”，这可能影响控制器对副本的管理；也不要以为滚动重启整个 Deployment 就是在保留某一个异常实例。Kubernetes 中这些对象怎样协作，见 [Kubernetes 实战](/back-end/frontend-backend-guide/24-kubernetes-in-practice)。

## 27.6 恢复以后，把尚未解决的事情讲清楚

回滚后，任务列表延迟恢复，说明回滚对这次影响有效；它还不能单独证明新增筛选条件就是全部原因。接下来继续在隔离环境验证查询改动，再决定如何重新发布。

这次处理记录可以这样写：14:02 起部分列表请求超时；查询调用占主要耗时；数据库慢查询与执行计划支持扫描过多的判断；14:08 回滚后延迟恢复；随后在相同数据规模下比较优化前后结果。还没有验证的部分就写“待确认”，不要把推测写成已查明。

最后，再看下次能否更早发现。例如给列表接口保留延迟分布和错误率，给慢查询与连接池等待建立合适的观察入口。具体告警要结合正常流量和处理办法来设，而不是统一套一个百分比。如何把这些数据连起来，见 [可观测性](/back-end/frontend-backend-guide/30-observability)。

到这里，一次含糊的“转圈”已经有了清楚的推进过程：先确认具体请求和影响，再缩小耗时范围，随后验证猜测；需要先恢复时，保留力所能及的信息，恢复后继续完成修复。遇到不同症状，可以带着这个顺序查 [排查实战手册](/back-end/frontend-backend-guide/28-troubleshooting-playbook)，不必每次都把所有工具跑一遍。
