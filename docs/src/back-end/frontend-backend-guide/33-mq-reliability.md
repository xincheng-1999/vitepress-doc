# 异步任务与 MQ：答应了用户的导入，重启后还能继续吗

用户上传一份大 CSV，导入要几十秒。我们不想让浏览器一直等，准备立即返回“已经受理”，后台慢慢处理。可如果刚返回，应用就重启了，那份尚未开始的工作去哪里找？

这才是本篇先要解决的问题。先让单体应用保存并恢复任务，等到确有跨进程分发需求时，再加入 MQ。每多一步，就检查进程在这里崩溃会留下什么。

示例仍是 Java 17 + Spring Boot 3.x `task-api`，本地 `8080`、入口 `/api/tasks`，尚未自带下面这些扩展。可靠性实验以 MySQL 为准；初版内存 H2 在进程结束后丢失数据，不能用它证明重启恢复。后台任务也不要求先拆微服务。

## 1. 先保存“要做什么”，再返回已经受理

修改一条任务状态，只要一条短 SQL，通常在 HTTP 请求内提交后返回就够了。导入很大、需要进度查询或重启恢复时，才值得把受理和执行分开。

`@Async`、线程池和 `CompletableFuture` 能让代码换个执行位置，但工作如果只排在内存里，进程一退出就没了。要让已经受理的请求有地方恢复，先在数据库保存一条后台任务记录。

```text
POST /api/task-imports → 校验文件/权限 → 保存 job(PENDING) → 提交
                     ← 202 Accepted + jobId + 状态查询位置
GET /api/jobs/{jobId} → 返回状态、已处理行数、失败摘要
```

这里的 job 是“执行这次导入”的记录，与导入后创建的普通 task 不同。最初可以记录任务 ID、归属、类型、状态、进度、尝试次数、下次执行时间和安全的错误摘要。状态先从 `PENDING → RUNNING → SUCCEEDED / FAILED` 开始。失败后要么有计划地重试，要么给用户可解释的失败结果，不永远停在转圈页面。

数据库提交之后才能返回 202。源文件也要保留到执行和重试窗口结束，否则记录还在，内容却已经被清理。状态和结果接口都检查用户或租户归属，worker 使用服务端确认的业务范围，不盲信文件或消息里随意填的 ownerId。

## 2. 后台工作者从记录里领取任务

单体内启动一个有界 worker，定期查找待执行 job，就能开始，不需要马上装 MQ。但“查到待执行”还不能直接执行：两个 worker 可能同时读到同一条。

领取要成为一个可判断成败的动作。例如在短事务中使用条件更新，要求 job 仍是 PENDING，只有影响 1 行的执行者可以开始。多个 worker 再按数据库能力考虑行锁、跳过已锁定记录等策略。

领取后如果 worker 崩溃，job 不能永远卡在 RUNNING。可以记录 `lease_until`，让领取权在一段时间后过期，执行者定期续租，恢复者再领取超时任务；同时限制尝试次数。每次领取产生新的 `claim_token` 或递增版本，更新进度和完成状态时都检查它。

为什么还需要这个标识？租约到期只是系统允许别人接手，旧 worker 可能只是在网络里卡住，稍后又恢复了。新的领取标识能拒绝它继续写任务进度；必要时还要让下游资源识别递增的 fencing token。导入产生的业务记录本身仍需幂等，领取权不会自动阻止所有重复副作用。

## 3. 任务已经保存，响应没到，用户再提交一次呢

这次故障不在 worker，而在入口：job 提交成功，浏览器没有收到响应，再点一次就可能新建第二份导入。

可以要求同一次导入操作携带一个幂等键，以 `(owner_id, operation, idempotency_key)` 唯一记录请求摘要和原 job。同键、同内容返回同一个 job；同键却换内容则拒绝。客户端重试复用原键，新的一次操作再换键。

后面即使消息有 eventId 去重，这个入口规则仍然需要：两次 HTTP 请求可能创建两个 job，产生两个不同 eventId。消息去重只认识同一条事件，不会自动识别用户重复提交了同一个意图。

到这里，单体持久任务已经能满足很多导入需求。如果 worker 直接扫描 job 表就够了，可以停在这里。工作只是跨线程执行，和工作能够在重启后恢复，是两件事。

## 4. 需要跨进程分发时，再加入 MQ

当 worker 要独立扩缩、多个系统要订阅，或希望把短期突发流量缓存在队列里，可以引入 MQ。生产者发送消息，Broker 接受并保存消息，消费者收到后处理；发布器和 worker 最初仍可位于同一应用，不必立即拆成不同服务。

队列给的是暂时等待空间。若长期生产速度高于处理速度，等待仍会越积越久，需要入口限流、容量、最大等待时间和降级，不能只叫它“削峰”就当作容量问题已经解决。

消息也不必携带整份 CSV。通常只发 `eventId`、`eventType`、`schemaVersion`、`jobId`、`occurredAt` 和受控追踪信息，消费者按 job 找内容。限制消息大小和敏感字段，确定版本兼容和权限规则。同一个事件重发时 **eventId 不变**；后续发生新的业务事件才产生新 ID。

现在出现一个新问题：job 在 MySQL，消息在 Broker。如果提交 job 后、发送前进程崩溃，数据库有任务，队列却没有。把这两行代码写进一个 `@Transactional` 方法，不能让 MySQL 和 MQ 自动一起提交。

## 5. 用 outbox 保存“这条事件应该发送”

解决上面的窗口，可以在创建 job 的**同一个数据库事务**中，插入一条待发送事件。这个表叫 outbox，意思就是一份待发记录。事务成功后，job 和发送意图都在数据库里，发布器可以重启后继续找它。

![任务与 outbox 同事务提交，发布可能重试，消费效果提交后确认](/backend-guide/features-mq-outbox.svg)

下面是用于理解职责的 MySQL 简化结构，不是要粘到初版 H2 的通用迁移脚本：

```sql
CREATE TABLE outbox_event (
  event_id VARCHAR(64) PRIMARY KEY,
  aggregate_id VARCHAR(36) NOT NULL, -- 与本课程 UUID 字符串标识保持一致
  event_type VARCHAR(80) NOT NULL,
  payload JSON NOT NULL,
  status VARCHAR(16) NOT NULL,
  attempts INT NOT NULL DEFAULT 0,
  next_attempt_at DATETIME(3) NOT NULL,
  created_at DATETIME(3) NOT NULL,
  INDEX idx_outbox_pending (status, next_attempt_at)
);
```

创建时，先校验权限和参数，再在同一事务保存 `background_job(PENDING)` 与 `outbox_event(PENDING)`，提交后返回 202 和 jobId。发布器另行分批读取、认领到期事件，发送并处理确认，成功才标记 SENT；失败或结果未知则记录次数和下次时间，等待重试。

发布器不要在数据库长事务里一直等网络，实际实现还要处理并发领取和领取过期恢复。SENT 只表示获得发送确认，任务是否完成仍看 job。发布失败也不撤销已经受理的 job，系统要继续恢复，超过处理承诺就告警并显示真实状态。

发送确认超时尤其要小心：消息可能已经被 Broker 收到，只是确认没回来。用相同 eventId 重发，接受它可能出现两次。即使收到确认，发布器也可能在写 SENT 前崩溃，下次仍会重发。所以 outbox 保存了可恢复的发送意图，**没有消除重复消息**。也不能先标 SENT 再发送，那会把“根本没发”误记为完成。

生产者收到成功确认，说明 Broker 按当前协议和配置接受了消息，不说明消费者已经处理。同步等确认和异步回调都可以用，关键是接住成功、失败与未知结果并能恢复；单向发送没有确认，不适合把任务是否受理当成已知事实。

如果没有要发往外部的消息，worker 直接可靠扫描 job 就够，不必额外建 outbox。CDC 读取事务日志，或特定 MQ 的事务消息，也是某些场景的替代方案，但要理解其运行和回查要求，不会自动包含消费者的数据库或第三方接口。

## 6. 消费者提交业务效果之后，才确认消息

假设导入完成事件需要创建一条站内通知。消费者收到事件，写入通知，再确认消息，流程看似很短，却仍可能在“通知已提交、确认还没发出”之间崩溃。恢复后消息再次投递，通知就可能重复。

可以让消费者在同一数据库事务中，先记录处理过的 eventId，再创建通知：

```sql
CREATE TABLE consumed_event (
  consumer_name VARCHAR(80) NOT NULL,
  event_id VARCHAR(64) NOT NULL,
  processed_at DATETIME(3) NOT NULL,
  PRIMARY KEY (consumer_name, event_id)
);
```

`consumer_name` 区分不同业务消费者，让它们各自处理一次。事务边界是：

```text
收到事件
  BEGIN
    INSERT consumed_event(consumerName, eventId)
    创建站内通知 / 更新本地业务数据
  COMMIT
确认消费成功

如果 INSERT 命中该主键的重复：
  结束并回滚本次事务；确认确为已提交的相同事件后，按重复成功处理
如果其他错误：
  回滚，不伪装成成功；按错误类别重试或持久隔离
```

提交前崩溃，去重记录和通知一起回滚，下次可以重做；提交后重投，唯一约束拦住重复事件，不再生成通知。不能先 SELECT“没处理过”就放心执行，两个消费者可能同时查到没有，最终仍要由唯一约束仲裁。

Spring 事务代理必须真正覆盖去重记录与业务修改，并在事务外识别预期的唯一约束冲突。不要把所有数据库异常都吞成重复，也不要在已标记回滚的事务里继续提交。如果同一个业务动作可能由不同 eventId 触发，还需要通知的 `(job_id, notification_type)` 等业务唯一键。

Redis `SET NX` 标记与 MySQL 修改通常不在同一事务中：标记成功、业务失败会漏处理，标记到期后旧事件又可能重复。去重记录还要保留到消息保留、重试、恢复和人工回放窗口结束，必要时由长期业务唯一约束继续托底。

最后才是 ack，也就是通知 Broker 本次已处理；一些产品表现为推进消费位点，并非立即从磁盘删除。框架可能在监听方法正常返回时自动确认，如果方法只把任务扔进内存线程池就返回，任务仍可能丢。要么完成业务再确认，要么先可靠转存为本地持久任务。

## 7. 外部调用超时，不能一律当作没执行

前面把通知和去重记录放进同一个数据库，事务能够覆盖。换成“调用短信服务”，本地事务就无法撤销已经发出的短信。

短信服务已经成功、响应却超时，结果对调用方是未知的。优先使用提供方的幂等键、业务单号和查询接口，结合对账确认；没有这些能力，就要明确重复与漏发的取舍，并提供人工恢复，而不是宣称数据库去重后短信也恰好一次。

同样地，数据库短暂不可用适合稍后重试，CSV 格式错误或不支持的事件版本则不会因多试几次自动变好。永久失败应可靠保存原因或隔离事件，之后确认并告警。错误分类决定恢复方式：

| 类别 | 处理方向 |
| --- | --- |
| 暂时故障 | 有上限重试、指数退避并加随机偏移，尊重 Retry-After |
| 永久失败 | 保存终态或隔离记录，给出可查询原因 |
| 结果未知 | 先查询，或按提供方幂等协议重试 |
| 新代码导致大量失败 | 停止盲目重放，告警、修复或回滚后受控恢复 |

`1s → 2s → 4s …` 只是退避示意，实际间隔和总时限按下游能力确定。HTTP 客户端、业务循环和 MQ 都各自重试时，次数会相乘，需要一起计算。

超过阈值可以进入死信队列 DLQ 或失败表，但事情还没结束。保存事件与业务标识、分类、首次和最近失败时间、次数和脱敏摘要，并安排告警、负责人和重放入口。修复后按原 eventId 重放，还要检查任务是否已经取消或过期，不能强行让它复活。

## 8. 试着在每个空隙停掉进程 {#failure-exercises}

先在本地 MySQL 做持久 job 和数据库 worker，不要求安装 MQ；完成之后，再选一种熟悉的 MQ 扩展。文件型 H2 只能演示简化恢复，锁和并发仍要在 MySQL 验证。故障开关仅用于本地测试。

先创建 job，在 worker 执行前停止应用，再启动。查询应还是同一个 job，恢复执行，而不是新建另一份。接着让两个 worker 竞争，确认只有一个正常领取；模拟租约到期后旧 worker 恢复，检查它的写入确实被新版本或令牌拒绝。

加入 MQ 后，把暂停点移动到 outbox 提交之后、发送之前，确认事件能够继续发布。再模拟发送已成功却未记录 SENT，此时消费者可能收到两次同 eventId，站内通知仍应只有一条。最后在业务提交后、ack 前停掉消费者，重投也应得到同样结果。

以下保留其余检查，便于逐项补做：

| 故障 | 要检查的结果 |
| --- | --- |
| 不支持的事件版本 | 有失败记录与告警，不无限重试，也不悄悄报成功 |
| 模拟短信成功但响应超时 | 通过幂等键或查询确认；没有能力则如实记录未知 |
| 重放过期或已取消任务 | 遵守当前业务状态，不自动恢复旧操作 |

每次同时查询 job、outbox、去重记录、业务记录和失败记录。日志写“成功”却找不到通知，或通知存在两条，都说明流程还没处理好。可以用 [测试章节](/back-end/frontend-backend-guide/35-testing) 把这些暂停点变成回归用例。

## 按需补充

### Broker 故障和消息保留要另外验证

Broker 确认后能承受哪些故障，依赖产品、版本、刷盘、副本和确认配置。Kafka、RabbitMQ、RocketMQ 的语义不能互相照抄；任何 SEND_OK 都不是覆盖所有磁盘故障、灾难和误删的承诺。消息过保留期或被误删后，还要靠任务对账和修复，队列不能永久替代业务状态库。

常见的至少一次投递，是在约定的持久性、保留与恢复前提下允许重投，直到确认或进入失败流程；并不说明业务必然成功。至多一次允许丢失，适合部分可丢遥测等场景。某些产品的 exactly-once 对指定读写范围提供事务或去重语义，应准确理解范围，不外推成任意数据库、邮件和支付都只执行一次。常见做法是至少一次投递，加同一本地事务内的幂等效果。

### 顺序和定时触发

旧 RUNNING 事件晚于 SUCCEEDED 到达时，用事件版本或条件更新阻止终态倒退。确需同一任务按序处理，再按业务键分区，结合具体产品验证重试、多生产者和消费者切换的顺序；全局顺序会显著限制并发。

延迟消息让某条消息到未来才可见，适合“十分钟后检查任务”；每天 02:00 生成报表则是定时调度，要定义时区、漏跑补跑、并发和运行历史。多个节点协调谁执行、怎样分片和接管，才是分布式调度，不是在每个副本加 `@Scheduled`。以 `(job_type, business_date, tenant_id)` 等键防重复，触发准时也不表示完成准时。更多见 [功能地图](/back-end/frontend-backend-guide/39-backend-feature-map#batch-jobs)。

### 怎样发现任务卡住了

优先观察最老待执行 job 和消息的年龄，因为它直接对应用户已经等了多久。再看最老待发 outbox、吞吐和耗时、重试与死信增长、RUNNING 租约超时，以及 job 与最终业务记录对账。队列为空不代表业务真的完成。

日志关联 jobId、eventId、consumerName、attempt、traceId，不记录整份个人数据或文件签名 URL；这些高基数字段适合日志和链路，不宜无限做指标标签。队列数少于消费者数时有的实例可能空闲，多于实例数时一个实例也可以消费多个队列，不能据此认定剩余队列无人处理。
