# 33. 消息与任务可靠性：从同步到持久任务，再到 MQ

## 学习目标

读完本章，你应该能：

- 判断一个长任务是否只需要同步处理、持久任务表，还是值得引入 MQ。
- 根据生产、存储、消费各阶段的失败位置，解释“失败”“成功”“结果未知”的区别。
- 用数据库唯一约束、事务和 outbox 建立可恢复流程，明确它们覆盖不了的外部副作用。
- 为重试、退避、死信与积压设计可观测的处理办法，不把“至少一次”说成“绝不重复”。

本章仍是 **Java 17 + Spring Boot 3.x 的单体 `task-api`**，本地 `8080`，核心资源 `/api/tasks`。第一课的 H2 可以帮助学习持久化概念，后续可靠性练习以 MySQL 为准；H2 内存模式在进程退出后不保留任务，不能据此宣称重启可恢复。微服务不是使用后台任务的前提。

## 33.1 起点：什么时候不需要异步

需求：“把一条任务改为完成。”一条短 SQL 更新通常就该在 HTTP 请求内完成，提交成功后返回，不需要 MQ。

需求变成：“导入一份大 CSV，逐行验证并创建任务，可能要几十秒。”这时有三档选择：

| 阶段 | 最小方案 | 适合什么 | 失败边界 |
| --- | --- | --- | --- |
| 同步请求 | 校验、写库、提交后返回 | 小数据、耗时可控，调用方愿意等待 | HTTP 超时不代表数据库未提交；重试创建仍需幂等策略 |
| 单体持久任务 | 先落 job 表，返回 jobId；同一应用的 worker 按记录执行 | 需要查进度、重启恢复，吞吐不大 | 要做任务认领、失败重试、过期恢复；只开线程不算持久化 |
| 持久任务 + MQ | job 与 outbox 同事务；后台发布，worker 消费 | 独立扩缩 worker、多系统订阅、突发缓冲等需求已出现 | 增加 Broker、重复投递、消息过期、积压、运维与一致性成本 |

`@Async`、线程池或 `CompletableFuture` 只改变执行方式。若 HTTP 返回后进程崩溃，尚未执行的内存任务会丢；若需要恢复，应先建立数据库中的任务记录。MQ 是跨进程的消息基础设施，**不是 EventEmitter 的别名或“自动持久化的回调”**；本地事件机制不能替代投递协议、存储、确认和恢复。

“削峰”也有边界：队列只是让暂时的生产速度高于消费速度成为可能，长期不够的处理能力会让等待无限增长。还需要队列容量、入口限流、最大等待时间和降级策略。

## 33.2 先做一个可恢复的单体任务

导入不必复用普通任务 ID：业务任务 `task` 与后台执行记录 `background_job` 是两种资源。

```text
POST /api/task-imports → 校验文件/权限 → 保存 job(PENDING) → 提交
                     ← 202 Accepted + jobId + 状态查询位置
GET /api/jobs/{jobId} → 返回状态、已处理行数、失败摘要
```

建议的最小字段：`job_id`、`owner_id`、`type`、`status`、`attempts`、`next_run_at`、`lease_until`、`claim_token`、`progress`、`last_error_code`、`created_at`。状态可从 `PENDING → RUNNING → SUCCEEDED / FAILED` 开始。失败后是否重试由明确策略决定，不让前端无限转圈。

worker 不能先读一批 `PENDING` 再无条件执行：两个线程可能读到同一行。可以用短事务中的条件更新认领，只有影响行数为 `1` 的执行者开始工作；多 worker 时再选择合适的行锁/跳过锁定策略。长任务需要租约与续租、过期任务恢复、重试次数限制。

**租约过期不等于旧 worker 已停止**。新 worker 认领后，旧 worker 可能从网络阻塞中恢复；应使用新的 `claim_token` 或递增版本对进度/完成写入做条件校验，必要时使用 fencing 思路阻止过期执行者。业务效果本身仍需幂等，不能只靠“已经认领”。

后台任务也要做安全隔离：状态和结果接口验证归属，导入记录服务端确认的用户/租户，worker 按受控业务范围处理，不盲信消息里的任意 `ownerId`。对象存储中的源文件要保留到任务处理和重试窗口结束。

### 任务已落库，HTTP 响应却没到怎么办

用户重复点击或网络重试可能创建第二份 job。为导入请求提供幂等键，例如按 `(owner_id, operation, idempotency_key)` 唯一，并记录请求内容摘要；相同键、相同内容返回原 job，不同内容使用相同键应拒绝。**消息 eventId 去重不能替代入口请求幂等**：两次 HTTP 请求可能生成两个不同 eventId。

## 33.3 引入 MQ 后，先把边界画出来

MQ 的生产者、Broker、消费者是三个角色，可以先由同一个单体中的发布器和 worker 承担，不必立即拆成多个服务。

![任务与 outbox 同事务提交，发布可能重试，消费效果提交后确认](/backend-guide/features-mq-outbox.svg)

最小消息不要塞整份文件，通常包含：`eventId`、`eventType`、`schemaVersion`、`jobId`、`occurredAt` 和受控的追踪上下文。消息大小、敏感字段、版本兼容、权限检查都要有约束。一个业务事件即使被多次发布，**eventId 保持不变**；一份任务后续的新事件则使用新 eventId。

生产者调用成功说明的是 Broker 按当前协议/配置接受到了什么，不等于消费者已处理。同步等待确认与异步回调都可以可靠，前提是正确接住确认与失败并持久化恢复；“同步一定比异步可靠”不是普遍规律。单向发送没有确认，不适合把业务任务是否被接收作为已知事实。

## 33.4 失败矩阵：先分清没有发生与不知道发生没有

### 生产与 Broker

| 失败窗口 | 可能留下什么 | 正确处理 | 错误结论 |
| --- | --- | --- | --- |
| 本地事务提交前进程崩溃 | job 与 outbox 都回滚 | 客户端按入口幂等键重试 | “请求发过来就算受理” |
| job 提交后、普通直接发消息前崩溃 | 有 job，没有消息 | 使用同事务 outbox 或可靠的补偿扫描 | “数据库事务能回滚已经发到 MQ 的消息” |
| Broker 明确拒绝发送 | outbox 仍待发送 | 记录错误，按策略稍后重试 | 忽略返回状态也算成功 |
| Broker 已接收，但发送确认超时 | 消息可能已经存在，生产者结果未知 | 使用相同 eventId 重发；允许重复 | 超时就证明没发出去 |
| 发布成功，标记 outbox 已发送前崩溃 | Broker 有消息，outbox 仍待发送 | 再次发布并由消费者幂等 | “先标已发再发，避免重复” |
| 确认后 Broker 节点/磁盘故障 | 是否保留取决于持久化、副本、确认策略 | 按可靠性目标选协议和配置，验证故障恢复及备份 | 任何 `SEND_OK` 都意味着永远不丢 |
| 消息过保留期限 / 被误删 | 历史消息不可再投递 | 任务对账与修复；受控保留和管理权限 | MQ 可以永久替代业务状态库 |

刷盘、复制与故障切换语义因 Kafka、RabbitMQ、RocketMQ 等产品及版本不同而异。即使启用了同步刷盘或副本确认，也不能宣称能覆盖所有灾难、误操作和软件故障。初学先识别“确认的范围”，再读所选产品的文档，不照搬一份 Broker 配置当普遍保证。

### 消费

| 失败窗口 | 结果 | 恢复方式 |
| --- | --- | --- |
| 收到后、业务事务开始前崩溃 | 没有业务效果 | 未确认消息后续重投 |
| 业务事务中途失败 | 本地修改应全部回滚 | 可重试故障触发重投，重复事件仍安全 |
| 本地事务提交后、ack 前崩溃 | 业务已生效，但 Broker 不知道 | 重投时识别已处理，直接确认，不再次产生效果 |
| 先 ack，再交给内存线程池 | Broker 认为完成，内存任务可能丢 | 不这样做；或先持久化到可恢复的本地任务再 ack |
| 外部接口已经成功，响应超时 | 外部副作用结果未知 | 用第三方幂等键或查单/对账确认，不能盲目再次扣费/发信 |
| 格式非法、版本不支持、业务永久失败 | 重试不会自行修复 | 持久记录失败原因或隔离事件，提交后确认并告警 |

ack 的具体含义可能是确认消息、推进消费位点等，不必然是立即从磁盘删除消息。框架也可能以“监听方法正常返回”触发确认：如果方法只提交了线程池就返回，必须确认任务已经可靠转存，而不是还在内存里。

## 33.5 Outbox：把“应该发送”与业务提交放在一起

核心思路不是“把数据库和 MQ 变成一个事务”，而是**本地事务内同时提交业务记录与待发事件**。只要数据库事务成功，事件的发送意图就存在，可以恢复发送。

下面是 MySQL 的简化表结构，帮助识别职责，不是 H2 通用迁移脚本：

```sql
CREATE TABLE outbox_event (
  event_id VARCHAR(64) PRIMARY KEY,
  aggregate_id VARCHAR(36) NOT NULL, -- 与本课程 UUID 字符串标识保持一致
  event_type VARCHAR(80) NOT NULL,
  payload JSON NOT NULL,
  status VARCHAR(16) NOT NULL,
  attempts INT NOT NULL DEFAULT 0,
  next_attempt_at DATETIME(3) NOT NULL,
  created_at DATETIME(3) NOT NULL,
  INDEX idx_outbox_pending (status, next_attempt_at)
);
```

逻辑事务可以这样阅读：

```text
提交服务（同一个 MySQL 事务）：
  校验权限与参数
  创建 background_job(PENDING)
  插入 outbox_event(PENDING，eventId 固定)
  COMMIT
  返回 202 + jobId

发布器：
  有界读取/认领到期 outbox
  发送消息，等待确认或处理异步确认
  确认成功后标记 SENT
  失败或结果未知则更新 attempts、next_attempt_at，稍后重试
```

发布器不能在数据库长事务中一直等网络；生产实现需处理并发认领、过期认领恢复、发送批次和积压索引。outbox 变成 `SENT` 只代表已获发送确认，不代表任务完成。发布失败不抹掉已被受理的 job，而是让系统对它继续负责；超过服务承诺应告警并显示真实状态。

**何时不需要 outbox？** 如果本地 worker 直接从持久 job 表发现工作，没有要投递到外部的消息，可以只可靠地扫描 job。无需“为了学习可靠性”再造一层无业务价值的 outbox。

**替代方案**：CDC 读取事务日志发布事件，或某些 MQ 的事务消息机制，能解决特定生产一致性问题，但各有运行要求和回查语义。它们都不自动把消费者的数据库和第三方支付接口包进同一个原子事务。

## 33.6 幂等：用唯一约束保护业务效果，而非先查一下

假设任务导入完成事件要给用户增加一条站内通知。采用消费者去重表：

```sql
CREATE TABLE consumed_event (
  consumer_name VARCHAR(80) NOT NULL,
  event_id VARCHAR(64) NOT NULL,
  processed_at DATETIME(3) NOT NULL,
  PRIMARY KEY (consumer_name, event_id)
);
```

`consumer_name` 使不同业务消费者能各自处理一次，而不是一个消费者处理后把别人的工作也跳过。若同一个业务操作可能用不同 eventId 到达，还需业务级唯一键，例如通知的 `(job_id, notification_type)`。

正确的处理边界是：

```text
收到事件
  BEGIN
    INSERT consumed_event(consumerName, eventId)
    创建站内通知 / 更新本地业务数据
  COMMIT
确认消费成功

如果 INSERT 命中该主键的重复：
  结束并回滚本次事务；确认确为已提交的相同事件后，按重复成功处理
如果其他错误：
  回滚，不伪装成成功；按错误类别重试或持久隔离
```

在 Spring 中应让事务代理真正覆盖这段业务，并在事务外正确识别**预期唯一约束**的冲突；不要把所有数据库异常都吞成“重复”，也不要在已经标记回滚的事务中继续提交。这样进程在提交前崩溃，去重记录与效果一起回滚；提交后重投，唯一约束阻止再次执行。

为什么“先 `SELECT`，没有再插入”不够？两个并发消费者可能都读到没有，必须让唯一约束成为最终仲裁。为什么 Redis `SET NX` 一个标记不够？标记成功后业务失败会导致漏处理，标记过期后旧消息又可能重复执行；Redis 标记与 MySQL 修改通常不在同一本地事务中。

### 幂等不跨越所有系统

把去重记录、站内通知放在同一个数据库事务内，不能覆盖“调用短信网关”这种外部副作用。外部调用要优先使用提供方的幂等键或业务单号、查询接口和对账补偿；没有这些能力时，就必须承认重复/漏发的权衡，并设计人工恢复。

去重记录也有保留期：如果记录清掉之后又允许回放更老的消息，效果可能再次发生。去重窗口应覆盖消息保留、重试、灾难恢复和人工回放窗口；必要时用长期业务唯一约束托底。

## 33.7 重试、退避、死信：失败要能停下来，也能找回来

| 失败类型 | 例子 | 应对 |
| --- | --- | --- |
| 暂时性故障 | 数据库短暂不可用、服务端 `503`、明确可重试的限流 | 有上限重试，指数退避并加随机抖动，遵守对方 Retry-After |
| 永久性失败 | CSV 格式错误、不可支持的事件版本、任务已取消 | 写入终态/隔离记录，持久化成功后确认；返回可解释错误 |
| 结果未知 | 第三方处理超时、提交确认丢失 | 先查询或按幂等协议重试，不能简单归为“没执行” |
| 系统性错误 | 新版本代码让大量消息解析失败 | 停止盲目重放，告警、回滚或修复，再受控恢复 |

例如 `1s → 2s → 4s …` 加抖动，直到次数或总重试时长上限。实际间隔按下游能力和恢复窗口配置，不把这个示例当固定标准。多层重试会相乘：HTTP 客户端重试、业务循环重试、MQ 重投若同时各试三次，可能形成远多于三次的外部调用。

超过阈值可以进入 DLQ（死信队列）或专门的失败表。**DLQ 不是垃圾桶，也不意味着业务已经被妥善处理。** 至少保存事件标识、业务标识、失败分类、首次/最近失败时间、次数与安全的错误摘要；有告警、有负责人、有修复后按原 eventId 重放的入口。重放需要审核当前业务状态，不能把已经取消或过期的任务强制复活。

## 33.8 顺序、延迟、定时与投递语义

### 顺序不代替状态约束

更新任务状态时，旧的 `RUNNING` 事件可能晚于 `SUCCEEDED` 到达。最小防线是条件更新/事件版本检查，禁止终态倒退；确需同一任务按序处理时，再评估按业务键分区的顺序消费。全局有序会严重限制并发；重试、消费者切换和多生产者也会影响顺序，必须读具体产品的承诺。

### 延迟消息不等于定时调度

- **延迟消息**：让一条消息在未来某个时间后可见，如“十分钟后检查导入是否仍未完成”；精度和支持范围受产品限制。
- **定时调度**：按时间规则生成执行机会，如“每天 02:00 导出昨天完成的任务”，要定义时区、漏跑补跑、重复执行、并发互斥、运行记录。
- **分布式调度**：多个节点协调由谁执行、如何分片/故障接管；不是给所有副本都加 `@Scheduled` 就完成了。

重复调度与消息重复一样需要业务幂等，例如 `(job_type, business_date, tenant_id)` 唯一。调度器准确触发，也不等于任务按时完成。更多 cron 和导入导出边界见 [功能地图](/back-end/frontend-backend-guide/39-backend-feature-map#batch-jobs)。

### 三种投递语义都有适用范围

| 语义 | 在约定范围内意味着什么 | 不能外推的保证 |
| --- | --- | --- |
| at-most-once 至多一次 | 最多投递一次，可能丢失 | 不适合所有业务，但允许丢弃的遥测等可能接受 |
| at-least-once 至少一次 | 在满足持久性、保留、恢复等前提下重复投递，直到确认或进入失败流程 | 不保证业务一定成功、不保证无限重试，也不代表不会重复 |
| exactly-once 恰好一次 | 某些系统对指定范围的读、处理、写提供事务/去重语义 | 不自动覆盖任意数据库、邮件、短信或支付调用 |

工程上常用“至少一次投递 + 本地事务内幂等效果”实现可接受的业务结果。可以准确描述这个范围，不必把 exactly-once 说成完全不存在，也不能把产品内部 exactly-once 当成全链路“只扣一次钱”的证明。

## 33.9 可观测：不要只数队列里有多少条

| 观测项 | 想回答什么 | 建议动作 |
| --- | --- | --- |
| 最老待发送 outbox 年龄、失败率 | 业务已提交但消息是否卡在生产端？ | 查发布器、Broker 连接、权限与错误分类 |
| 最老待处理 job / 消息年龄 | 用户究竟等待了多久？ | 对照处理时限告警，比单看条数更贴近体验 |
| 消费吞吐、耗时分位、在途数量 | 供需差在哪？ | 区分单条慢、并发受限、下游慢，避免直接加线程 |
| 重试率、重复率、DLQ 增量 | 是否有毒消息或新代码错误？ | 按错误类别和版本聚合，检查最近发布 |
| 卡在 RUNNING 的任务、租约超时 | worker 是否崩溃/失联？ | 恢复认领，检查旧执行者与重复副作用 |
| job 与最终业务记录对账 | 队列没有积压，业务真的完成了吗？ | 查“已确认但效果未落库”等逻辑缺陷 |

日志关联 `jobId`、`eventId`、`consumerName`、`attempt`、`traceId`，但不要记录整份个人数据或文件签名 URL；这些高基数字段适合日志/链路，不宜无限作为指标标签。队列数少于消费者数时，一些产品的额外消费者可能空闲；队列数多于实例数时，一个实例也可能消费多个队列，**不代表剩下队列无人处理**。

## 33.10 动手练习：让故障发生在正确的位置 {#failure-exercises}

不要求先安装 MQ。先在本地 MySQL 做持久 job + 数据库 worker，再在选修阶段接任一种熟悉的 MQ。文件型 H2 只能做简化的重启演示，不能代替验证 MySQL 的并发/锁语义。故障开关仅用于本地测试。

| 练习 | 操作 | 预期结果 |
| --- | --- | --- |
| 重启恢复 | 创建导入 job，在执行前停止应用，再启动 | 同一个 job 可继续，不新增第二份任务 |
| 重复认领 | 同时开两个 worker 竞争一条待执行 job | 正常窗口只有一个认领成功；过期旧 worker 写入受版本/令牌保护 |
| 生产崩溃 | outbox 提交后、实际发送前停止发布器 | job 可查询，重启后事件继续发送 |
| 发送结果未知 | 发送成功后跳过本次 `SENT` 更新，再运行发布器 | 同一 eventId 可能到达两次，但只产生一条站内通知 |
| 消费崩溃 | 本地事务提交后、ack 前停止消费者 | 再次投递被唯一约束识别，不重复产生效果 |
| 永久错误 | 输入不支持的事件版本 | 有可查询失败记录及告警，不无限重试、不悄悄成功 |
| 外部效果 | 用模拟短信服务制造“成功但响应超时” | 用幂等键/查询确认；没有该能力时明确报告未知而非保证未发送 |

**验收依据**：不只看日志“成功”，要查 job 状态、业务记录条数、outbox、去重记录与失败记录是否一致。可用 [测试章节](/back-end/frontend-backend-guide/35-testing) 将这些窗口做成自动化回归。

## 自测与答案

1. `@Async` 已经让请求立即返回，为什么仍可能丢任务？

   **答案**：执行意图若只在内存，进程崩溃就消失；先持久化 job，之后才谈线程如何执行。
2. 发送超时后应该换 eventId 重新发吗？

   **答案**：同一事件不换。超时是结果未知，换 ID 会绕过按 eventId 的去重；入口重复提交还需另一层幂等键。
3. 为什么 outbox 无法消除重复消息？

   **答案**：Broker 已接收、数据库尚未标记 SENT 之间可能崩溃，恢复时必然可能重发；它解决可靠发送意图，不解决消费重复效果。
4. 去重插入成功后业务失败怎么办？

   **答案**：必须与业务效果同一本地事务回滚；分开提交会导致永久漏处理。
5. 消费者完成数据库事务后，调用第三方发信也恰好一次了吗？

   **答案**：没有，数据库事务无法覆盖外部效果；需要第三方幂等能力、查询对账或承认并治理不确定窗口。
6. “每月 1 日凌晨执行”适合只用延迟消息吗？

   **答案**：通常应由调度规则与执行记录管理，明确时区、漏跑补跑、重复和并发；延迟消息最多是其中一种投递工具。
