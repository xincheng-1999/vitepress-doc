# 垃圾回收：接口变慢，真的是 GC 吗

::: info 按需阅读
这一篇从一段 GC 日志出发，解释对象回收和停顿，不要求背收集器参数。内存区域不熟时回看 [JVM 内存模型](/back-end/frontend-backend-guide/18-jvm-memory-model)，第一次学习仍可继续 [五阶段主线](./index)。
:::

任务系统偶尔加载很慢，同一时段的 GC 日志里出现了这一行：

```text
GC(187) Pause Full (G1 Compaction Pause) 1987M->1502M(2048M) 889.331ms
```

这能证明程序在泄漏内存吗？不能。但它提供了三个有用线索：发生了一次 Full GC，回收前后堆使用量从 1987M 变为 1502M，这次暂停约 889ms。

下面先把这行读懂，再解释为什么会暂停，以及怎样决定下一步查什么。

## 1. 一行日志，先读类型、前后占用和耗时

对比两次**示意性的 Java 17 G1 日志**：

```text
[2026-06-01T10:15:32.118+0800][1203.458s][info][gc] GC(142) Pause Young (Normal) (G1 Evacuation Pause) 1843M->412M(2048M) 8.215ms
[2026-06-01T10:18:06.531+0800][1357.871s][info][gc] GC(187) Pause Full (G1 Compaction Pause) 1987M->1502M(2048M) 889.331ms
```

`GC(142)`、`GC(187)` 是对应事件的编号，便于把同一次回收的多行日志串起来。前面的时间戳和运行时长，用于与接口、CPU 和容器指标对齐。

第一行中，`Pause Young` 表示一次年轻代相关暂停；`1843M->412M(2048M)` 是回收前使用量、回收后使用量和该行报告的堆容量，括号里的容量不必永远等于最大堆。堆占用下降很多，暂停 8.215ms，是一次短暂停顿；是否满足服务要求，还要看请求的延迟预算和发生频率。

第二行的 `Pause Full` 是整堆整理相关的 Full GC，暂停更长，回收后仍使用约 1502M。它说明当时有不少存活数据，值得调查；但这些数据可能是正常缓存、尚未处理完的任务、合法增长的业务数据，也可能是不再需要却被保留的对象。**一行日志不能区分这些原因。**

日志里若有 `User`、`Sys` 和 `Real`，前两者是相关 CPU 时间，`Real` 是经过的墙上时间。多条 GC 线程同时工作时，累计 CPU 时间可能大于墙上时间，不能拿前两者直接当请求暂停时长。

## 2. GC 怎样知道哪些对象可以回收

任务创建时会产生入参、临时字符串和响应对象。Java 和现代 JS 引擎都使用自动内存管理，不需要业务代码逐个释放普通对象；这里把回收机制统称为 **GC（Garbage Collection）**。

但 GC 不懂“业务已经不需要这条历史任务”。它判断的主要依据是**可达性**：从当前仍在使用的一组入口出发，沿引用链能不能找到这个对象。

这组入口常叫 **GC Roots**，包括活动线程栈中有效的对象引用、部分 JNI 引用等。长期存活的类及其静态字段，也可以形成让业务对象继续可达的路径。例如：

```text
长期存活的类
  └─ 静态字段 CACHE
       └─ Map
            └─ Task 对象
                 └─ 大量 byte[] 数据
```

即使用户早已不再查看这些任务，只要这条强引用路径仍存在，GC 就不能把它们当成可回收垃圾。反过来，一个对象已经不可达，也不代表马上释放；收集器会按分配压力、占用预测和自身策略安排回收，不是每次都等到“内存全满”才开始。

::: details 两个对象互相引用，为什么仍能被回收
```java
class Node {
    Node next;
}

Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;
a = null;
b = null;
```

假设没有其他可达引用，这两个对象就像一座孤岛。只看引用计数，会发现它们还互相引用，简单计数方案无法据此释放；可达性分析从根找不到它们，就可以判定它们可回收。

这也是为什么“两个对象互相引用”本身不等于泄漏。不要为了防循环引用，盲目在每个方法结束时把所有局部变量都设成 `null`。
:::

## 3. 为什么回收会让请求暂停

收集器要在对象引用不断变化时正确识别和整理存活数据。有些工作可以与业务线程并发完成，有些关键阶段则需要暂停应用线程。这种暂停叫 **STW（Stop The World）**。

暂停发生在这个 JVM 进程内：请求处理线程不能继续执行 Java 业务代码，已在途的网络、其他进程和其他服务实例却不一定都停止。也不能把 889ms 直接加到这个时间窗内每条请求的响应时间上；每条请求与暂停重叠多少、是否排队，都会影响结果。

如果多接口延迟一起抬高，且时间与长 GC 暂停重合，GC 就是重要候选原因；仍要结合精确时间、实例和其他指标确认。CPU 限流、线程阻塞、下游变慢也能产生类似表现。

浏览器和 Node 也会受 GC 暂停影响，可能导致动画掉帧、交互迟缓或服务尾延迟增加。不是“前端 GC 无所谓”，而是两边都需要根据自己的延迟要求观察。

## 4. 年轻代、老年代和 G1，够用的理解是什么

许多请求对象很快不再使用，少数缓存和组件则会存活很久。分代收集利用这个差异，让回收年轻对象的成本通常更容易控制，但不保证每次年轻代回收都很短。

Java 17 在常见服务器配置下通常使用 G1，实际选择应从启动日志或生效参数确认。G1 把堆划为多个 **Region**，分别用于年轻代、老年代等用途；它既有暂停阶段，也有并发工作，不是每次都暂停后扫描整个堆。

读 G1 日志时，可以先区分：

| 常见类型 | 大致在做什么 |
| --- | --- |
| Young GC | 回收年轻区域，可能复制和晋升存活对象 |
| Mixed GC | 在年轻代回收中，也选择部分老年代 Region 回收 |
| Full GC | 整堆回收或整理的后备路径，可能带来较长停顿 |

实际日志还有并发标记等阶段。不要把所有 `Pause Young` 都当作只收年轻代，带有 `Mixed` 的事件还涉及部分老年代。

`-XX:MaxGCPauseMillis=200` 表示希望 G1 尽量达到的暂停目标，**不是 200ms 的硬上限**。G1 会依据预测调整收集范围等策略，不是闹钟响了就停止本次必要工作。它也可能因空间不足等原因退入 Full GC。

::: details 其他收集器，用到时再区分
Parallel 更偏向吞吐目标，Serial 的实现简单，适合某些小规模环境；ZGC、Shenandoah 侧重降低暂停，但可用性、能力和开销要看 JDK 版本与发行版。不能承诺它们在任何负载下都低于 1ms。

CMS 是旧收集器，在 JDK 14 已移除。知道老配置里可能遇到它即可，不必为了这一篇再学一遍所有收集器的演进。
:::

## 5. 没有 GC 日志时，怎样为下一次留下信息

先看现有监控和日志，避免为了诊断立刻改线上参数或重启。若准备在下一次授权发布中增加日志，Java 9+ 可以使用统一日志配置：

```bash
java '-Xlog:gc*:file=./gc.log:time,uptime,level,tags:filecount=5,filesize=20M' \
  -jar app.jar
```

`app.jar` 代表自己的已打包应用，不是本页提供的工程。这条命令会启动进程、创建和轮转日志文件，不是对现有进程的只读查询。示例适合自己的实验环境；线上需确认路径可写、磁盘配额、采集策略和发布方式，不照搬当前目录。

`gc*` 选择相关标签，`time` 和 `uptime` 帮助对齐时间，后面的参数限制轮转文件数量和单文件大小。应连同活动日志为磁盘留余量。GC 日志通常有助于长期观测，但开销取决于标签、级别、频率和写入方式，不能一概称为零成本。

::: details 老项目使用 JDK 8 时
Java 8 使用另一组参数，不能把它们与 Java 17 的统一日志参数混用：

```bash
java -XX:+PrintGCDetails -XX:+PrintGCDateStamps \
  -Xloggc:./gc.log \
  -XX:+UseGCLogFileRotation -XX:NumberOfGCLogFiles=5 -XX:GCLogFileSize=20M \
  -jar app.jar
```

它同样是启动配置，路径、空间和变更范围要先确认。不同收集器日志格式可能不同，不能逐列套用前面的 G1 日志。
:::

## 6. 回到慢接口：下一步怎样查

先把暂停时间和同一实例的接口延迟对齐。如果确实重合，再连续看三件事：暂停是否频繁到影响业务预算、每次耗时怎样、回收后的存活量如何变化。

没有统一的“几分钟一次就不健康”标准。短暂停顿可能因频率太高影响吞吐，一次长暂停也可能打破尾延迟要求；这都要与具体服务目标比较。

如果相近流量下，回收后占用越来越高，就继续找：缓存是否持续增长，队列是否积压，单任务是否加载太多数据，类加载和堆外是否也有变化。这是泄漏线索，但也可能是正常工作集增加。反过来，回收后能下降，也不能保证不存在缓慢泄漏。

不要为了画曲线先强制 Full GC，也不要看到占用高就只改 `-Xmx`。先核对数据量、分配速度、存活对象、容器预算和 CPU 情况；确有配置或收集器方面的依据，再在可控环境里一次改变少量因素，对比结果。

现在开头那行日志能带来的结论是：“发生了一次可能影响请求的长暂停，并留下较高的回收后占用，需要结合趋势继续调查。”至于是谁保留了数据，再到 [OOM 与内存泄漏](/back-end/frontend-backend-guide/20-oom-memory-leak) 沿对象引用链寻找。
