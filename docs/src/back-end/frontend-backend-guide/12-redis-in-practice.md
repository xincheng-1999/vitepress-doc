# Redis：给任务统计加缓存以后，数据该怎么更新

任务首页有一块统计，每次打开都查“各状态有多少条任务”。如果相同结果被反复读取，查询也已经成为明显开销，我们会想：能不能先把结果存起来，下次直接拿？

Redis 常被用来存这份临时结果。但多存一份数据之后，真正要弄清楚的是：原数据改了怎么办，缓存没了怎么办，Redis 连不上又怎么办。本篇围绕这几个问题展开，再按需介绍限流和锁。

先看过 [SQL](./10-sql-and-indexes)、[事务](./11-transactions-consistency) 和 [登录权限](./32-security)，会更容易分清数据职责。**第一版任务 API 尚未集成 Redis**，下面是扩展设计，不是现有接口的隐藏功能。

## 1. 先确认慢在哪里，再决定是否多存一份

如果只有几十条任务，列表却很慢，先检查 SQL、索引、页大小和实际耗时。缺少用户条件、一次查全表，不能靠缓存把问题掩盖过去。

当查询本身合理、重复读取又足够多时，才值得增加缓存。我们的约定是：**MySQL 保存业务数据，Redis 中的统计可以从数据库重建**。这样，缓存消失后仍有地方重新计算，缓存暂时过期也不会改变任务的真实状态。

Redis 把数据主要放在内存中，支持字符串、集合等结构，还可以配置持久化、复制和淘汰策略。这使它适合很多短期数据，但增加它也意味着增加网络调用、内存容量和故障处理。速度要看命令、数据量、网络和部署，不能承诺永远比 MySQL 快某个固定倍数。

## 2. 第一次查数据库，之后在一段时间内复用结果

先看最常用的一种读法，通常叫 **Cache-Aside**，由应用负责查缓存和填缓存：

![应用先查缓存，未命中回源；写入以数据库为准，提交后失效缓存，并保留故障恢复路线](/backend-guide/core-cache-flow.svg)

请求进来后，先完成认证和授权，再确定要查谁的统计。应用用这个范围生成 key，到 Redis 查找；有结果就返回，没有才查 MySQL，把公开响应所需的数据存入 Redis，并设置有效时间。

这个有效时间叫 **TTL**。例如存 60 秒，意味着最多复用这一段时间；过期后，下一个请求重新计算。TTL 既能回收不再使用的缓存，也给漏掉更新的旧数据设一个存活上限。

key 要能区分真正不同的结果。用户私有数据不能都叫 `task:list:page0`，至少要包括用户或租户范围，以及影响结果的筛选、分页等条件。缓存中保存响应需要的字段，不把带密码哈希的 Entity 整个交给页面。命中缓存也必须遵守当前权限，不能跳过授权。

如果本机已经启动了**专用测试 Redis**，可以先观察最小的存取和过期过程。下面不负责安装或启动 Redis，也不连接公司环境：

```bash
redis-cli -h 127.0.0.1 -p 6379
```

进入客户端后执行：

```text
SET learn:task:1 '{"id":"1","title":"SQL"}' EX 60
GET learn:task:1
TTL learn:task:1
INCR learn:counter
```

SET 保存一段 JSON 字符串，GET 原样读回；Redis 不会因为它长得像 JSON 就自动提供字段查询。TTL 通常返回 0 到 60 的剩余秒数，过期后返回 -2；-1 表示这个 key 没有到期时间。计数器首次从 1 开始，重复 INCR 会继续增加。使用带认证的测试环境时，按受控方式注入凭证，不把密码留在命令参数、截图或共享历史里。

## 3. 任务修改以后，先提交数据库，再让缓存失效

假设把一条 TODO 改为 DONE，统计结果也随之变化。常见做法不是立即计算一份新缓存，而是先提交数据库事务，再删除相关统计缓存。下一次读发现没缓存，就会从数据库重新计算。

为什么一定强调“提交后”？如果先删缓存、事务还没提交，另一个请求可能从数据库读到旧统计，再把旧结果填回 Redis。删过缓存，却仍留下旧值。

提交后删除能减少这种窗口，也省去了为无人读取的数据提前计算结果的工作。不过还有两种情况需要处理：数据库已提交，Redis 删除却失败；或者某个慢读已经读到了旧值，在删除之后才完成回填。这两种情况都可能让旧缓存继续存在。读数据库副本时，复制延迟也可能产生同类问题。

因此，先确定业务能接受多久的展示延迟。普通统计可以依靠 TTL，在需要时再增加可靠失效事件、outbox、CDC 或版本检查。余额、库存和权限这类决定能否执行操作的判断，直接以权威数据和业务规则为准，不能依赖可能过期的展示缓存。“延迟双删”能缓解某些时序，但不是强一致性的承诺。

## 4. 缓存没有命中时，不能让所有请求一起压回数据库

现在正常读写能工作了，再想一个瞬间：热门统计刚好过期，一千个请求同时进来。它们都没找到缓存，都去执行相同 SQL，数据库反而比没加缓存时更容易被压垮。

可以把同一个 key 的重建合并，让有限的执行者计算，其余请求等待一小段时间，或在业务允许时先用旧值。等待必须有上限，重建失败也要退出，不能递归等待后无限重试。

另一个情形是 Redis 整体不可用。此时所有 key 都像没命中一样，应用需要有限的连接和读取超时，并给数据库设置回源预算：允许多少并发、超出后快速失败还是返回可接受的旧结果。直接让所有请求改查数据库，只是把故障转移过去。

这些现象有几个常见名字，遇到时可以回表查：

| 名字 | 具体发生了什么 | 常见处理 |
| --- | --- | --- |
| 穿透 | 反复查不存在的数据，每次都查库 | 输入校验、短期空结果缓存、限流 |
| 击穿 | 一个热点 key 失效，很多请求同时重建 | 同 key 请求合并、受控重建、按需返回旧值 |
| 雪崩 | 大量 key 一起过期，或缓存整体不可用 | 过期时间加随机偏移、分批预热、限制回源 |

布隆过滤器有时用来提前排除“不可能存在”的数据。只有数据已完整加入、更新机制正确等前提成立，它的“不存在”判断才可依赖；它可能把不存在判断为存在，也可能因同步延迟让业务数据被误拦。不要直接把它作为关键权限判断。

## 5. 用一个小实验检查这条缓存读写流程

扩展时先选择“公开、允许短暂过期的统计数”，不要从余额或权限开始。这个实验需要你自行实现缓存调用，初版源码并没有附带实现。

先连续读两次：第一次查数据库，第二次命中 Redis，观察 TTL 是否在减少。然后修改数据库并提交，确认相关 key 失效，下一次读能重新计算。到这里验证的是正常路径。

再在本地故意让删除缓存失败，检查旧值最多保留多久、恢复机制是否真的会重试。最后暂停测试 Redis，检查请求能否在预算内结束、数据库查询量是否受控。不要只记录“缓存加上了”：能说明失败时用户看到什么，才知道这份临时数据是否适合你的功能。

## 按需补充

### 其他数据结构什么时候有用

统计缓存用字符串已经够了。需要其他能力时，再选对应结构：

| 结构 | 适合的需求 | 使用时要继续考虑 |
| --- | --- | --- |
| String | 序列化响应、计数器 | JSON 仍是一段字符串 |
| Hash | 一组对象字段 | 不要把它当关系表，也别做成无限大的单 key |
| List | 双端序列、简单队列 | pop 之后崩溃怎样恢复，不是完整可靠消息方案 |
| Set | 去重成员 | 大集合不要一次全量返回 |
| Sorted Set | 排名、按时间排列待处理项 | 谁领取到期项、领取后崩溃怎样恢复 |
| Stream | 有序消息流、消费组 | 确认、待处理恢复、持久性和去重 |

Redis 常见命令串行执行，但多条命令不会因此自动成为一个原子操作，进程内部也不只有一个线程。是否需要脚本或事务，要看这组命令必须一起完成什么。

### 限流：限制的是服务端允许处理多少请求

前端防抖能避免用户连续点击，却阻止不了另一台设备或 curl。服务端限流才是在用户、租户、IP、接口或整体容量上施加资源限制。

固定时间窗口可以用计数器实现，但“增加次数”和“首次设置到期时间”需要一起执行，否则进程可能在两者之间崩溃，留下永久不失效的计数。下面用 Lua 脚本表达这一步：

```lua
-- KEYS[1] 为包含窗口标识的 key；ARGV[1] 为过期秒数
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return n
```

超过阈值返回 429，并按策略给 `Retry-After`。固定窗口在边界处仍可能突发，要求更平滑时再考虑滑动窗口或令牌桶，优先使用成熟组件。

Redis 故障时也要选策略：普通浏览可以有限降级，付费调用、验证码和高风险操作不能无条件放行。IP 不一定代表一个用户，代理头也只能信任受控入口提供的值。

### 分布式锁：暂时由谁来做这件事

只有一个数据库中的配额扣减，优先使用 [条件 UPDATE 与事务](./11-transactions-consistency)。跨进程协调缓存重建或任务领取时，才可能需要租约：

```text
SET learn:lock:export:42 随机唯一ownerToken NX PX 10000
```

它表示“在十秒内，由持有这个随机标识的执行者占用”。释放时必须原子检查标识确实还是自己，再删除；简单在 finally 里 DEL，可能删掉租约过期后别人刚拿到的锁。

执行者也可能暂停超过十秒，恢复后继续工作，而新执行者已经开始。Redisson 等成熟库能处理释放和续期细节，但关键资源仍可能需要递增的 fencing token、数据库条件和业务幂等来拒绝过期执行者。锁用于协调，不能替代唯一约束或跨系统事务。

### 运行后要观察什么

缓存命中率要与回源量一起看，再看内存、淘汰率、慢命令、大 key、热点 key 和网络延迟。Session 或去重记录如果也放 Redis，要确认到期和淘汰策略不会删掉你以为必须保留的状态；若要把 Redis 当主存储，则需要独立设计持久化、复制和恢复，不能沿用本篇可重建缓存的假设。

生产避免全量 `KEYS` 和巨大的 `HGETALL`。`SCAN` 可以分批遍历，但仍有执行成本，期间可能重复或看到变化，并非一致快照。学习环境也不用清库命令来省事。
