# Redis：缓存、限流与锁，分别解决什么

> 学习目标：知道为什么需要 Redis、何时不需要；能画出缓存读写和故障路径，不把缓存、锁、事务当作同一件事。

前置：[SQL](./10-sql-and-indexes)、[事务](./11-transactions-consistency)、[登录权限](./32-security)。本章是能力扩展，第一版任务 API **尚未集成 Redis**。

## 1. 先看问题，不急着装组件

任务列表慢，先测延迟、SQL、页大小和索引。如果几十条任务也慢，通常不是缺 Redis。新增缓存后，你多了一份数据、一条网络依赖、一套过期与故障策略。

Redis 是支持多种数据结构的内存数据存储，可配置持久化、复制和不同淘汰策略。常见命令执行串行化不等于整个 Redis 没有其他线程，也不等于任意一串命令自动原子。性能取决于数据、命令、网络、持久化和部署，**不能承诺永远比 MySQL 快 100 倍**。

主线事实源是 MySQL；Redis 只放可重建缓存和明确设计过的短期状态。某些系统可把 Redis 用作主存储，但那需要单独设计持久化、恢复和故障语义，不能照搬缓存配置。

## 2. 每种数据结构对应什么需求

| 结构 | 常见用途 | 要注意 |
| --- | --- | --- |
| String | 序列化资源、计数器 | JSON 不会自动变成可按字段查询的对象 |
| Hash | 某个对象的字段集合 | 不等同关系表，避免无限增大的单 key |
| List | 双端序列、轻量队列 | 简单 pop 不提供完整可靠消息处理闭环 |
| Set | 去重成员集合 | 巨大集合全量返回会阻塞和占网络 |
| Sorted Set | 排名、按到期时间排序 | 到期后谁领取、崩溃恢复仍要设计 |
| Stream | 有序消息流、消费组 | 仍需确认、待处理恢复、持久化与去重设计 |

学习命令可以在自己机器上的测试 Redis 中做，不要连接公司生产环境：

```bash
redis-cli -h 127.0.0.1 -p 6379
```

```text
SET learn:task:1 '{"id":"1","title":"SQL"}' EX 60
GET learn:task:1
TTL learn:task:1
INCR learn:counter
```

预期依次设置成功、返回 JSON 字符串、TTL 为 0..60 的剩余秒数、计数从 1 增加。TTL 为 -1 是没有到期，-2 是不存在。不要在命令行参数、截图或共享历史里留下密码，优先用受控凭证注入。

## 3. Cache-Aside：先明确谁负责更新

![应用先查缓存，未命中回源；写入以数据库为准，提交后失效缓存，并保留故障恢复路线](/backend-guide/core-cache-flow.svg)

### 读

1. **先认证、授权**，构建包含必要用户 / 租户 / 查询条件的 key。
2. Redis 命中且可用：返回缓存。
3. 未命中：查数据库、转换为公开响应、设置合理 TTL、返回。
4. Redis 超时：按容量预算有限回源或快速失败，不能无限等，也不能让所有请求同时击穿数据库。

不要把包含密码哈希的 Entity 整个缓存给页面。用户私有列表不能只用 `task:list:page0` 这种跨用户共享 key。

### 写

常见方案是：**先数据库事务提交，再使相关缓存失效**。这里的「提交后」很重要：事务还没提交就删缓存，另一请求可能读旧库再回填。

删除优于直接更新缓存的一些理由：不用为无人读取的数据提前组装结果，也减少并发写顺序导致旧缓存覆盖的机会。但它不是强一致保证：

- DB 提交了，删缓存失败，旧值可能保留到 TTL。
- 一个慢读在写发生前读到旧库，写删缓存后才把旧值回填，也会留下旧值。
- 读副本延迟、消息延迟同样会让回填读到旧数据。

可以结合 TTL、失效事件 / outbox、CDC、版本校验、受控重建等策略；「延迟双删」只缓解某些时序，不能当作数学上的保证。**余额、权限、库存等正确性判断不要基于可能过期的展示缓存。**

## 4. 三个常见词，别混着背

| 名词 | 发生了什么 | 可以怎么处理 |
| --- | --- | --- |
| 穿透 | 反复查不存在的数据，每次回源 | 输入校验、短期负缓存、限流，必要时布隆过滤器 |
| 击穿 | 一个热点 key 失效，大量并发同时重建 | 合并同 key 请求、受控互斥重建、允许返回旧值 |
| 雪崩 | 很多 key 集中失效，或整个缓存不可用 | TTL 抖动、容量与限流、分批预热、回源预算 |

布隆过滤器的「不存在」只在**数据已完整加入且维护正确**等前提下可信；同步延迟或错误删除仍会造成业务误拦。它有假阳性，不适合不经思考就用在关键权限判定。

缓存重建要有等待上限和失败退出，不能递归睡眠后无限重试。分布式锁必须唯一 owner token + 原子校验释放；只写 `finally DEL lock` 会误删后来者的锁。

## 5. 限流不是防抖

前端防抖 / 节流改善体验，能被另一个设备或 curl 绕过。服务端限流是**强制资源和配额策略**：按用户、租户、IP、接口或总容量限制。

固定窗口示意，需要把计数和设置 TTL 做成一次原子操作：

```lua
-- KEYS[1] 为包含窗口标识的 key；ARGV[1] 为过期秒数
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return n
```

超过阈值返回 429，按策略给 `Retry-After`。单独先 INCR 再 EXPIRE，中间进程崩溃可能留下无 TTL 的 key。固定窗口还有边界突发问题，可按需求选择滑动窗口或令牌桶；优先使用成熟组件。

还要决定 Redis 故障时 fail-open 还是 fail-closed：普通浏览可有限降级，付费接口、验证码和安全操作通常不能无条件放行。IP 不一定代表唯一用户，代理头也不能随意信任。

## 6. 分布式锁：协调，不是万能正确性证明

如果只是一个数据库里的余额扣减，优先 [条件 UPDATE / 事务](./11-transactions-consistency)。如果是跨进程协调定时任务领取或缓存重建，才考虑分布式锁。

```text
SET learn:lock:export:42 随机唯一ownerToken NX PX 10000
```

这表达一个**有期限的租约**。执行超过租约、长时间 GC 暂停、网络分区、续期失败，都可能导致两个执行者同时认为自己能继续。

Redisson 等成熟库封装了可重入、释放、续期等细节，但并不让这些故障边界消失。关键资源可需要 fencing token、数据库条件和幂等验证。锁不能替代唯一约束，也不能自动实现跨系统事务。

## 7. 运行时还要看什么

- key 数量、内存、淘汰率、命中率与回源量。
- 大 key、热 key、慢命令、网络延迟和客户端连接。
- TTL 和淘汰策略是否会删掉你以为不能丢的 Session / 去重记录。
- 持久化和复制配置是否符合你声称的恢复能力。

生产慎用全量 `KEYS`、巨大 `HGETALL` 等；`SCAN` 是分批游标，**仍有执行成本，且遍历期间可能重复或看到变化**，不是零成本一致快照。不要在学习教程里直接写清库命令。

## 动手与验收

在独立实验中给「公开、可接受短暂过期的统计数」加缓存，而不是先缓存权限或余额：

1. 第一次读回源，第二次命中；观察 TTL。
2. 修改 DB 后提交并失效，下一次读回源。
3. 故意让删缓存失败，验证 TTL / 恢复策略，不声称立即一致。
4. 停掉测试 Redis，确认超时有限，回源流量受控。

## 自测与参考答案

1. Redis 命令原子，两个命令组合一定原子吗？**不是，需考虑脚本、事务和具体语义。**
2. 缓存 key 为什么要包含用户 / 租户？**防止不同权限范围错误共享结果；仍要先授权。**
3. 看门狗续期能保证任何时候都只执行一次吗？**不能，暂停、分区和外部副作用仍需正确性兜底。**
