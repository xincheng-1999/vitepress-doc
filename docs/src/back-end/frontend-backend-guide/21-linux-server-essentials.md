# 进入服务器后，怎样确认任务服务的状态？

页面访问失败，同事让你“上服务器看看”。进入终端以后，先不要急着重启。我们按顺序确认：现在在哪台机器，用哪个账号，任务服务是否运行，接口是否响应，最后再决定要不要操作。

这里仍使用 Java 17 + Spring Boot 3.x 的单体 `task-api`，默认地址为 `127.0.0.1:8080/api/tasks`。按 [CRUD 示例](/back-end/frontend-backend-guide/07-build-a-crud-api) 在本机运行，也能练习大部分观察，不必先租服务器或取得 root 权限。

## 1. 先分清：接下来的命令在哪执行？

公司服务器可能需要先经过 VPN、堡垒机或跳板。访问方式见 [公司内网与访问权限](./22c-private-network-and-access)，用公司批准的流程即可。能登录平台，不代表已有目标机器、sudo 或数据库权限。

如果获准使用标准 SSH，可以在自己电脑的终端连接：

```bash
ssh -p 22 deploy@server.example
```

`server.example` 和账号只是占位，不是教程提供的服务器。首次连接时，要通过管理员或可信记录核对主机指纹，再接受；密钥变化先问清原因，不直接删除 known_hosts 或关闭检查。私钥留在自己的受控设备，公钥按流程授权；新建密钥前确认不会覆盖旧私钥，按策略设置口令。

连接成功后，这个终端中的命令在远端执行。另开一个本机终端，命令仍在自己的电脑执行。容器里还有一套自己的进程、路径和网络视角；不确定位置时，先查：

```bash
whoami
hostname
pwd
java -version
```

输出分别告诉你当前账号、主机名、工作目录和 Java 版本。以后发排查记录，先说明这些信息属于本机、服务器还是容器，避免把不同位置的现象混在一起。

初始示例没有认证和用户隔离，只用于受控本机练习。练习远程登录不需要把这个 API 暴露到公网；换 SSH 端口也不能代替认证、补丁和访问控制。

## 2. 找到正在运行的那份应用

应用启动后是一个进程，不是磁盘上的 jar 文件本身。同一台机器还可能有 IDE、Maven 和其他 Java 服务，所以先列出当前账号能看到的 JVM：

```bash
jcmd -l
```

本地按第 07 章启动时，通常能找到 `dev.learning.tasks.TaskApplication` 或对应启动形式。`jcmd` 随 JDK 提供，只有 JRE、精简容器镜像或权限受限时可能不可用；没有列出，不等于机器上完全没有 Java 进程。

找到目标后，记录它这一次的 PID，再查看详细信息：

```bash
# 把 12345 换成本次确认的目标 PID
ps -p 12345 -o pid,ppid,user,etime,args
```

这里能看到进程用户、父进程、运行时长和启动命令。PID 会被复用，上次记下的数字不能当永久身份；启动命令也可能包含敏感参数，分享前要脱敏。此时只是确认目标，不根据“名字里有 java”批量停止进程。

如果服务由 Linux systemd 管理，而且管理员已经配置了 `task-api` 单元，还可以看：

```bash
systemctl status task-api
```

这不是当前源码自动附带的能力。macOS 没有原生 systemd，托管方式可能是 launchd；Compose 也有自己的管理命令。先认清启动者，之后才能用相应方式管理服务。

## 3. 进程还在，再看它有没有提供接口

有进程，不表示已经启动完成，也不表示 8080 正常。Linux 可查看监听：

```bash
ss -lntp
```

macOS 通常没有 `ss`，可用下面的命令；Linux 安装了 `lsof` 时也能用：

```bash
lsof -nP -iTCP:8080 -sTCP:LISTEN
curl -i --connect-timeout 2 --max-time 5 \
  'http://127.0.0.1:8080/api/tasks?page=0&size=20'
```

正常本机练习应看到 8080 的监听，以及接口返回 200 和分页 JSON。权限不足时，工具可能不显示完整的进程信息。接口响应比单纯看到 LISTEN 更接近实际使用，但查列表成功仍不能保证每条写路径都正常。

若监听的是 `127.0.0.1:8080`，它只接收当前网络环境的本机回环连接。`0.0.0.0:8080` 表示监听所有本地 IPv4 接口，但外部仍可能被路由、防火墙或容器端口发布规则挡住。容器中的 localhost 是容器自己，Compose 的 `mysql:3306` 则是容器网络地址。更多解释见 [网络课](/back-end/frontend-backend-guide/22-networking-for-backend) 和 [Docker 课](/back-end/frontend-backend-guide/23-docker-in-practice)。

连接被拒绝，常见于无监听，也可能是主动拒绝规则；连接超时，只能说明对应阶段没有及时完成。两者都不足以断言数据库损坏。`ping` 检查的也不是 HTTP 端口。

8080 被占用时，先辨认占用者。自己的第二份练习可以改到 8081，并同步修改访问 URL，不必停止不认识的服务。

## 4. 接口异常，去哪里找日志？

当前示例默认把日志写在启动终端，请求日志含 requestId，**不会自动创建 `/var/log/task-api/app.log`**。用 Maven 启动，就回到原终端查看。若已用 Compose 运行，可在对应示例目录查看：

```bash
docker compose logs --tail=100 api
```

若确实由上述 systemd 单元管理，则查看它的日志：

```bash
journalctl -u task-api -n 100 --no-pager
```

部署另外配置了文件日志时，再用 `less` 分页、`tail -n 100` 查看末尾，或用 `tail -f` 跟随。Ctrl+C 只停止跟随，不会停止应用。日志应围绕这次请求的时间和 requestId 查，避免为排错打印完整环境、登录内容或密钥。后面的 [日志课](/back-end/frontend-backend-guide/26-reading-logs) 会具体演示如何关联请求。

有时日志提示的不是代码错误，而是写文件失败或磁盘已满。接下来再沿着这个线索检查路径和资源，不需要一开始把所有系统命令都跑一遍。

## 5. 文件或磁盘报错时，检查应用实际使用的位置

先看当前目录和所在文件系统：

```bash
pwd
ls -lah
ls -ld . "$HOME"
df -h .
```

相对日志、配置和临时文件通常以进程工作目录为基准，不一定相对 jar 所在目录。`/opt/task-api/logs` 只是可能的部署路径，不是示例已经创建好的目录；SSH 用户、服务用户的 `$HOME` 也可能不同。容器里的 `/app` 与宿主同名目录不是天然同一份内容，要看挂载。

路径不存在时，先核对拼写、启动目录和挂载。确定日志目录存在后，可以用 `du -sh ./logs` 看它的占用：`df` 看文件系统空间，`du` 看目录文件占用，回答的问题不同。删除仍被进程打开的文件也未必立即释放空间。空间不足时按保留、归档和轮转规则处理，不直接删除数据库文件；涉及移动、删除前，确认解析后的绝对目标和备份，变量路径加引号。

### 文件在，却读不了：还要看进程用户

`ls -l` 显示的 `rwx` 分别对应读、写、执行，并按属主、属组、其他人分组。对目录来说，`x` 表示允许穿越路径，`r` 允许列举目录项，`w` 与修改目录项有关。因此文件本身可读，父目录不能进入，服务仍会失败。

常见的 `600` 是仅属主读写，适用于某些私钥或秘密文件；`644` 让其他人也可读，不适合一概用于含密码的配置。`750`、`755` 则涉及不同范围的目录穿越或脚本执行权限，不能对目录和普通数据文件机械套用同一模式。

排查时对照进程用户、属主和组、父目录权限；仍有问题再看 ACL、SELinux 或只读挂载。按所需范围修复即可，`chmod -R 777` 会扩大访问，递归 `644` 又会破坏目录穿越，大范围 `chown` 可能改变服务边界。确需管理员操作时走授权流程，不把 `sudo` 当通用修复器；容器挂载还要核对用户的数字编号 UID。

::: details 服务变慢时，先看哪些系统资源？
可以先用 `top`、`df -h` 观察进程和磁盘。Linux 的 `free -h` 应关注 available，不只盯 free；macOS 可用活动监视器或 `vm_stat`，输出含义不同。Linux load average 还包含部分不可中断等待，因此负载高不必然等于 CPU 忙。

需要进一步检查线程或堆时，查 [诊断工具](/back-end/frontend-backend-guide/29-diagnostic-toolbox)，先评估抓取操作对资源和隐私的影响。
:::

## 6. 确认需要停止后，用启动它的方式停止

本地前台练习，在原启动终端 Ctrl+C 即可。服务托管环境先收集必要现场，再通过 systemd 或容器平台的受控流程停止，而不是直接强杀某个 PID。

SIGTERM 给进程处理退出的机会，SIGKILL 无法捕获。但温和停止也不能保证所有业务完成：HTTP 是否排空、后台任务是否完成，要看应用实现、配置和平台期限；持久任务仍需恢复设计。强制终止应在目标、影响和恢复方案确认后按流程使用，相关思路见 [排查方法](/back-end/frontend-backend-guide/27-troubleshooting-methodology) 和 [可靠任务](/back-end/frontend-backend-guide/33-mq-reliability)。

需要把排查报告传到获授权的位置时，SCP 的端口参数是大写 `-P`：

```bash
# 本机已有 report.txt，且目标目录已获授权时使用
scp -P 22 ./report.txt deploy@server.example:/home/deploy/
```

你可以用本机示例练完这条顺序：运行时记录用户、目录、PID、监听地址和列表响应；在原终端 Ctrl+C 后，再请求同一地址。若仍有响应，先查是否有另一份进程，而不是反复重启。默认 H2 随 JVM 退出丢失任务，是内存库的已知行为，不是 Linux 擅自删了数据库。
