# 21. Linux 服务器起步：先认现场，再操作

## 学习目标

- 从进程、当前目录、权限、端口和日志确认一个服务的实际状态。
- 区分 Linux、macOS、容器内部三个观察位置，知道命令并非处处相同。
- 使用 SSH 建立可信连接，遇到端口冲突、磁盘不足时先取证，而不是直接杀进程或改全目录权限。

贯穿对象是 Java 17 + Spring Boot 3.x 的单体 `task-api`，默认 `127.0.0.1:8080/api/tasks`。[CRUD 示例](/back-end/frontend-backend-guide/07-build-a-crud-api) 可在本机运行；本章大部分观察不需要远程服务器或 root 权限。

::: warning 可运行范围
当前示例是本地教学应用，没有登录和数据归属隔离。不要为练 SSH 或端口访问而把它暴露公网。下文 `server.example`、PID `12345`、服务器目录和 systemd 单元均为占位，需要换成自己获授权的真实目标。
:::

## 21.1 进程：应用不是“一个页面”，而是一段正在运行的程序

先按第 07 章启动应用，保留启动终端，再开另一个终端观察：

```bash
whoami
hostname
pwd
java -version
jcmd -l
```

**预期结果**：看到当前用户、主机、目录、Java 版本；同用户可见的 JVM 中能找到 `dev.learning.tasks.TaskApplication` 或相应启动形式。`jcmd` 属于 JDK，只有 JRE、容器精简镜像或权限隔离时可能不可用；没有列出来不等于所有 Java 进程都不存在。

PID 是本机当前进程标识，会被复用。确认目标 PID 后，再读取其用户、父进程、运行时长与命令：

```bash
# 12345 仅为例子，先替换成刚查到的本次 PID
ps -p 12345 -o pid,ppid,user,etime,args
```

同一台机器可能运行 IDE、构建工具和别人的 Java 服务。不能根据“名字含 java”就批量停止，更不能把上次记录的 PID 当永久身份。命令行可能包含敏感参数，分享截图前先脱敏。

## 21.2 路径：相对谁，文件由谁管理

| 概念 | 例子 | 容易出错的地方 |
| --- | --- | --- |
| 当前工作目录 | `pwd` 输出 | 相对日志、配置、临时文件路径常以它为基准，不必然相对 jar 所在目录 |
| 绝对路径 | `/opt/task-api/logs` | 是服务器部署设计，不是示例已经创建的目录 |
| 用户主目录 | `$HOME`、`~` | SSH 用户、服务用户、容器用户可能各不相同 |
| 容器文件系统 | 容器内的 `/app` | 宿主同名路径不一定是相同内容，是否持久化要看挂载 |

```bash
pwd
ls -lah
ls -ld . "$HOME"
df -h .
```

这些命令用于确定位置、属主和所在文件系统。不存在的路径先核对拼写、挂载和启动目录，不要随手创建一个空目录掩盖部署错误。变量路径要加引号，涉及删除/移动前要确认解析后的绝对目标和备份；本章不提供一键清空命令。

`df` 看文件系统可用空间，`du -sh ./logs` 可在确认该目录存在后看它的占用。不要一上来扫描整个根目录或删除数据库文件；日志过大也应先按保留、归档、轮转和现场证据要求处理。删除仍被进程打开的文件，未必立即释放空间。

## 21.3 权限：谁能读、写、进入目录

`ls -l` 的权限通常分属主、属组、其他人三组 `rwx`。文件上的 `x` 表示可执行；目录上的 `x` 允许穿越路径，`r` 允许列举目录项，`w` 与目录修改有关。只有文件可读，但父目录不能穿越，也可能访问失败。

| 常见模式 | 含义 | 不该机械套用 |
| --- | --- | --- |
| `600` | 只有属主读写 | 可用于个人私钥等，但先确认属主和授权方式 |
| `644` | 属主读写，其他人可读 | 含密码的配置不应因“普通文本”就让所有人可读 |
| `750` / `755` | 不同范围的目录穿越与脚本执行权限 | 目录和普通数据文件的要求不同 |

权限失败先确认：进程用户是谁、属主/组是谁、父路径是否可进入、是否有 ACL、SELinux 或只读挂载等额外约束。**不要用 `chmod -R 777`、全目录递归 `644` 或大范围 `chown` 解决所有问题**：前者扩大暴露，后者可能破坏目录穿越或服务边界。

日常用普通账号，确需管理员操作时走授权流程；`sudo` 不是“所有报错前加一下”的修复器。容器内的数字 UID 也要与挂载目录访问设计一致。

## 21.4 端口：进程存在，不代表接口可用

Linux 常用：

```bash
ss -lntp
```

macOS 通常没有 `ss`，可用；Linux 安装了 `lsof` 时也可：

```bash
lsof -nP -iTCP:8080 -sTCP:LISTEN
curl -i --connect-timeout 2 --max-time 5 \
  'http://127.0.0.1:8080/api/tasks?page=0&size=20'
```

**预期结果**：看到当前应用监听 8080；请求返回 `200` 和任务分页 JSON。`ss`/`lsof` 可能因权限只显示部分进程信息。API 响应比“有个 LISTEN”更接近业务事实，但一个列表成功仍不能证明所有写路径正常。

| 现象 | 可确认什么 | 不能直接下的结论 |
| --- | --- | --- |
| 监听 `127.0.0.1:8080` | 接受该网络命名空间中的回环连接 | 不能因此从另一台电脑访问 |
| 监听 `0.0.0.0:8080` | 绑定当前命名空间的所有 IPv4 接口 | 防火墙、路由、端口发布仍可能阻止外部访问 |
| Connection refused | 当前路径上收到拒绝，常见为无监听或主动拒绝 | 不等于数据库数据损坏 |
| 超时 | 在预算内没有完成目标阶段 | 不证明服务器一定没执行，更不能只凭它断言防火墙故障 |

容器内的 `localhost` 指容器自己；Compose 的 `mysql:3306` 是容器网络地址，不是宿主地址。`ping` 不通也可能只是 ICMP 被禁，不能跳过 TCP/HTTP 验证就宣布网络彻底不通。

8080 冲突时，先确认占用进程归属；自己的第二份练习可以改用 8081 并同步修改 URL，不要直接停止不认识的服务。

## 21.5 日志和资源：先看已有证据

当前示例默认把日志写到启动终端，并在请求日志中包含 requestId，**没有默认创建 `/var/log/task-api/app.log`**。若以 Compose 运行，可在示例目录读取容器输出：

```bash
docker compose logs --tail=100 api
```

如果管理员已配置 Linux systemd 单元 `task-api`，才使用下面的服务器观察命令；它们不是当前源码运行后自动拥有的能力：

```bash
systemctl status task-api
journalctl -u task-api -n 100 --no-pager
```

文件日志部署可用 `less` 分页、`tail -n 100` 看末尾；`tail -f` 跟踪时 Ctrl+C 只停止查看，不停止应用。不要为排查打印完整环境、登录请求或密钥。

资源观察可以先用 `top`、`df -h`；Linux 的 `free -h` 关注 `available` 而非只看 `free`，macOS 可用活动监视器或 `vm_stat`，输出含义并不相同。Linux load average 还包含部分不可中断等待，负载高不必然等于 CPU 忙。深入后再抓线程/堆证据，见 [诊断工具](/back-end/frontend-backend-guide/29-diagnostic-toolbox)。

## 21.6 SSH 与服务停止：操作前先确定信任和影响

先分清**怎么获准进入服务器**与**进入后怎样操作**：公司可能要求 VPN / 零信任接入、堡垒机资产审批或跳板中转，不能只拿到 IP 就直连。完整角色、SSH 中转与隧道边界见 [公司内网与访问权限](./22c-private-network-and-access)。能登录平台不代表有目标系统账号、sudo 或数据库权限。

远程练习必须有授权账号和目标，下面不是公共练习服务器：

```bash
ssh -p 22 deploy@server.example
# 传文件的端口参数是大写 -P，目标目录需已获授权
scp -P 22 ./report.txt deploy@server.example:/home/deploy/
```

首次连接先通过管理员或可信渠道核对主机指纹，再接受；主机密钥变化先查原因，不直接删 known_hosts 或关闭验证。私钥不外传，公钥按管理员流程安装；生成新密钥前检查目标，避免覆盖旧私钥，按策略设置口令。换 SSH 端口不能替代认证、补丁与访问控制。

本地前台练习用 Ctrl+C 结束。服务托管环境先通过 systemd/容器平台的受控停止流程，收集必要现场；macOS 没有原生 systemd，后台托管常由 launchd 等负责。环境变量也由启动者传给子进程，修改自己终端不代表既有服务会更新。

SIGTERM 给进程处理退出的机会，SIGKILL 不可捕获；**是否排空 HTTP、是否完成后台任务，取决于应用配置、实现和平台截止时间**。即使发了温和信号也不能保证所有业务完成，持久任务仍需恢复设计。强制终止只应在确认目标、影响、证据和恢复方案后按流程使用，不是默认排障动作。

## 动手练习与预期结果

在本地运行第 07 章示例，完成四项记录：① 当前用户/目录；② 应用 PID 与启动形式；③ 8080 监听地址；④ `GET /api/tasks` 状态和 requestId。然后在原启动终端 Ctrl+C，再请求同一地址。

**预期结果**：运行时接口 `200`，停止后不再能连接该应用；如果仍得到响应，先核对是否有另一进程监听，不再反复盲目重启。默认 H2 重启丢任务属于已知实验边界，不是 Linux 删除了数据库。Linux 与 macOS 各选可用命令，不要求安装一整套服务器工具。

## 自测与答案

1. 文件明明 `644`，服务仍无法读取，先看哪里？

   **答案**：看实际进程用户、属主、父目录穿越权限及 ACL/安全策略/挂载，不递归开放所有权限。
2. 8080 有监听是否证明远程用户一定能访问？

   **答案**：不能，还要看绑定地址、网络命名空间、容器映射、路由与防火墙，以及真实 HTTP 响应。
3. 收到 SIGTERM 是否保证全部作业都已完成？

   **答案**：不保证，取决于退出实现与期限；后台工作需要持久状态、重试和恢复机制。
