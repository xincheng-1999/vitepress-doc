# 一次请求失败后，怎样找到对应的日志？

任务页面提示“创建失败”。先不重启，也不凭感觉改后端代码，我们拿这一次请求往下查：浏览器收到了什么，服务器有没有处理，为什么失败，修复后怎样确认。

这里沿用 [任务 API](./07-build-a-crud-api)。它的处理顺序见 [请求链路](./03-request-lifecycle)，容器输出的读取方式见 [Docker](./23-docker-in-practice)。

## 1. 先留下这一次失败的信息

打开浏览器 DevTools Network，找到对应请求，记下发生时间与时区、当前环境、方法、脱敏路径、状态和耗时。再保存必要的输入条件、预期结果和实际结果。若刚发布或改过配置，也记在同一条时间线上。

这不是为了凑一份长报告，而是为了能找到同一次操作。不同环境、不同时间、不同用户的几条报错混在一起，很难继续判断。

初始 API 会返回 `X-Request-Id` 响应头；错误 JSON 中也有 `requestId`。把它记下来，可以在服务器日志中找这次请求。请求 ID 只是关联标识，不是身份凭证。

分享时不带 Authorization、完整 Cookie、密码、token 或个人敏感信息。HAR、抓包、curl verbose 和 dump 都可能包含这些内容，应在授权范围内采集并脱敏；不必为说明“创建失败”上传整个登录过程。

## 2. 先判断：这次有没有 HTTP 响应？

![按没有响应、4xx、代理5xx、应用错误分层收集证据，再关联请求ID与根因](/backend-guide/core-troubleshooting.svg)

如果根本没有 HTTP 响应，也就未必会有应用生成的 requestId。名字解析失败，先查域名和调用方网络；连接拒绝或超时，先查实际 IP、端口、监听与访问规则；TLS 校验失败，则核对域名、证书链、有效期和客户端时间，不用 `-k` 跳过。这些阶段的命令见 [网络课](./22-networking-for-backend)。

如果有 HTTP 响应，先看是谁返回，以及状态说明了什么。400、405、415 通常先对照请求格式、方法和 Content-Type；404 还要确认入口路径是否改写。401、403 要查认证或授权，但初始 CRUD 并没有这套能力；409、412 属于业务或版本条件冲突，不能盲目覆盖重试。

502、504 可能是代理访问上游失败，应用未必收到，也可能已经执行但响应没回来；500 则需要继续读应用异常，不能仅凭它猜测数据库宕机。浏览器 CORS 错误也不等于操作没发生，`curl` 成功与页面能读响应的区别见 [HTTP 课](./22a-http-and-browser)。

## 3. 用一个可预期的 400，练习关联请求

先在自己的本机运行初始任务 API，再提交空标题：

```bash
curl --noproxy '*' -i --max-time 5 \
  http://127.0.0.1:8080/api/tasks \
  -H 'Content-Type: application/json' \
  --data '{"title":""}'
```

这是本机练习命令。预期返回 400、`X-Request-Id` 和 `{code,message,requestId}`，且没有创建任务。后续安全扩展启用后，应先按它的登录与 CSRF 流程获得测试凭据，不能为复现 400 关闭认证。

Maven 启动时，到原终端找这个 requestId；Compose 已运行时，在对应示例目录看最近日志：

```bash
docker compose logs --since 10m api
# 需要观察后续请求时再跟随；Ctrl+C 只停止查看
docker compose logs -f api
```

当前 `RequestLogFilter` 为每个请求生成 UUID，放入响应头和日志上下文。请求结束时，日志大致是：

```text
INFO [requestId=示意UUID] ... http method=POST status=400 elapsedMs=2
```

这是格式示意，不是本轮运行输出，耗时取决于实际环境。当前访问日志只记录方法、状态、耗时，不打印 query、body、Cookie 或 token。用你实际收到的 ID 找到一行，才能说明这次请求已经经过应用并返回 400。

400 在这里是字段校验按预期拒绝输入，不需要一条 ERROR 堆栈才算“日志正常”。修正标题后可以继续正常创建，再核对响应和列表，确认行为符合契约。

### requestId 为什么能出现在多行日志里？

过滤器把 ID 放入 MDC，也就是附着当前执行上下文的诊断信息，日志格式再把它打印出来。过滤器在 finally 中清理，避免线程复用后把上一次请求的 ID 带给下一次。

切到异步线程或跨服务时，它不保证自动传递。当前样例只有单应用的请求 ID，没有 OpenTelemetry 分布式追踪，也没有集中日志平台。查不到时应继续确认实例、时间、采集位置和日志级别，而不是马上断言请求从未到过服务器。没有访问权限时，把脱敏信息交给负责人查询即可。

## 4. 如果是 500，再读对应异常，而不是所有异常一起读

当前异常处理器会在未处理异常的边界记录 ERROR，再对外返回稳定错误信息和 requestId，不把内部堆栈返回给页面。先用 ID 缩小范围，再读这次异常的类型、业务代码位置和 `Caused by` 链。

例如数据库连接失败时，可能见到这样的嵌套关系：

```text
DataAccessResourceFailureException: ...
  at ...TaskRepository.list(...)
Caused by: SQLNonTransientConnectionException: ...
  at ...
```

这里只说明读法，不保证具体驱动总抛出同一个异常。外层说明业务调用失败，后面的原因更接近底层故障；读完整条链，再决定检查哪一处。连接失败就查地址、账号、可达性；唯一约束冲突就查重复数据；SQL 等待则继续看锁和执行计划。不要把每一层包装异常当成几个独立问题。

`Connection is not available` 常表示从连接池借不到连接，可能是 SQL 慢、锁等待、泄漏或容量不足，不直接证明密码错。先找占用与等待的原因，再评估池大小，避免把更多连接压给已经忙不过来的数据库。

## 5. 请求只是慢，还没有报错时怎么办？

访问日志里的 `elapsedMs` 只能告诉你这次应用处理花了多久，不能指出时间花在哪里。用户看到的总耗时还可能包含 DNS、TLS、代理等待和网络传输；应用内部又可能在等线程、借连接、等锁或调用下游。

先拿正常与异常请求做对照，找到哪一段增长，再看对应日志和资源。若很多请求都慢，要结合请求量、错误率、排队情况、数据库连接和慢查询；同时对照发布、配置和流量变化的时间。

平均耗时可能掩盖少量特别慢的请求，可以再看 P50、P95、P99 等分位数，例如 P99 描述接近最慢那一端的体验。日志适合看单次事件，指标适合看趋势和告警，trace 适合跨组件的单次调用路径。需要时再查 [可观测性选修](./30-observability)，第一次排错不必先部署一整套平台。

::: details 自己加日志时，怎样让下一次排查更容易？
INFO 记录重要生命周期和业务里程碑，WARN 记录可恢复但值得留意的情况，ERROR 记录需要关注的系统失败并保留异常对象。DEBUG / TRACE 用于受控细节，生产通常默认关闭，必要时限定范围和时长。

```java
private static final Logger LOG = LoggerFactory.getLogger(TaskService.class);
LOG.info("task created taskId={}", task.id());
LOG.error("export failed jobId={}", jobId, exception);
```

这是后续扩展写法，不表示已有导出功能。占位符减少提前拼接，但 `log.debug("{}", expensive())` 仍会先执行 `expensive()`，昂贵计算需级别判断或惰性接口。

异常通常在合适边界记录一次，不在每层 catch 后重复打堆栈。预期参数错误也不必 ERROR 刷屏。不要直接打印完整 User Entity，必要 ID 本身也要评估敏感性和保留权限。
:::

## 6. 修好以后，用原来的操作再验证

空标题的例子不需要修改后端，只需修正输入。真实系统故障则可能先要止血，例如暂停有问题的任务、限制异常流量，或回滚已经评估可回滚的应用版本，再处理根因。

生产中的重启、回滚、扩容、dump 都需要授权并评估数据、隐私和资源影响。应用回滚不会自动还原数据库结构和已产生的数据，已经发出的外部请求也不能简单撤销。

修复后重做原步骤，确认状态、数据和日志都符合预期，再为触发条件加回归测试。记录可以很短：“什么请求失败了，实际看到了什么，哪项检查确认了原因，改了什么，重试后的结果是什么。”只写“重启好了”，下一次仍然不知道从哪里查。

### 再做两个对照，别把不同失败当成同一种

先确认一个本机端口没有监听，再向它发送请求。预期没有 HTTP 响应，与上面的 400 明显不同，也不会有对应的任务 Controller 日志；确认端口时沿用网络课的方法，不随意假定某个固定端口无人使用。

如果你已实际运行隔离的 MySQL 练习环境，可以选做暂停测试数据库、请求列表、观察失败时限与异常、恢复后再查询。操作前确认 Compose 项目和目标，不在公司或共享环境故障注入。此前本机 Compose 插件 / daemon 不可用、容器未实测，因此这项仍是待读者完成的演练，不把示意堆栈当成执行记录。
