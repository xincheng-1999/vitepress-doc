# API 设计：把任务需求写成可验证的契约

> 场景：页面把任务标为完成，后端却要求另一个字段名；创建失败也返回 200，前端无法区分成功与错误。
> 这不是“前端多判断一下”能长期解决的事。接口需要双方共同遵守、测试可以验证的契约。

前置：[HTTP 与浏览器](/back-end/frontend-backend-guide/22a-http-and-browser)、[可运行的 CRUD](/back-end/frontend-backend-guide/07-build-a-crud-api)。本篇以单体 `task-api:8080` 的真实行为为基线，不假设已经有微服务或统一响应库。

**学完能做什么：**为一个任务接口写清输入、输出、错误和重试规则；识别不兼容变更；把接口文档转成下一篇的测试清单。

## 1. 先固定当前契约，不先造“万能返回壳”

配套源码位于仓库根目录 `examples/backend-task-api`，完整运行步骤见 [CRUD 实验](/back-end/frontend-backend-guide/07-build-a-crud-api)。

| 方法与路径 | 输入 | 成功响应 |
| --- | --- | --- |
| `POST /api/tasks` | JSON：`title` | 201、新任务、`Location: /api/tasks/{id}` |
| `GET /api/tasks/{id}` | 路径里的真实 ID | 200、单个任务；不存在则 404 |
| `GET /api/tasks?page=0&size=20` | 分页参数 | 200、`{items,total,page,size}` |
| `PUT /api/tasks/{id}` | JSON：`title`、`status` | 200、更新后的任务；不存在则 404 |
| `DELETE /api/tasks/{id}` | 路径 ID | 204、无正文；重复删除仍是 204 |

`{id}` 是文档占位符，要替换为创建响应中的 UUID。当前没有 PATCH、用户隔离、版本冲突检测、请求幂等键或任意条件筛选；不要把规划中的能力写成已经可调用的端点。

创建示例：`{"title":"学习 SQL"}`。标题须是非空白字符串，长度不超过 100 个 UTF-16 单元，业务层去掉两端空白；数字和布尔值不会被自动当成字符串接受。创建后的 `status` 默认是 `TODO`。

更新须提供全部**可编辑字段**，例如 `{"title":"学习 SQL","status":"DONE"}`。允许状态为 `TODO`、`DOING`、`DONE` 字符串，数字枚举被拒绝；`id` 与 `createdAt` 由服务端管理。PUT 不是“只传一个字段，其余自动保持”的 PATCH。

## 2. 输出类型、时间和空值要能直接写成类型

主线成功时直接返回资源，不包 `{code:0,data:...}`：

```ts
type Task = {
  id: string
  title: string
  status: 'TODO' | 'DOING' | 'DONE'
  createdAt: string // 带时区的 ISO 8601 时间点
}
type TaskPage = { items: Task[]; total: number; page: number; size: number }
type ApiError = { code: string; message: string; requestId: string }
```

- **ID**：主线是 UUID 字符串。其他系统若使用 Long / BIGINT，也要考虑 JS 的 `2^53-1` 安全整数限制；先解析成错误数字再转字符串无法恢复精度。
- **时间点**：`createdAt` 对应 Java `Instant`，如 `2026-01-15T08:30:00Z`；不承诺固定小数位数。界面按用户时区展示，不能擅自去掉 Z。
- **日历日期**：未来若有“截止日期”，应另约定 `YYYY-MM-DD`，不要把不带时区的日期强行当作 UTC 时间点。
- **空列表**：返回 `items: []`，不是 null。未知、缺失、空字符串的语义要逐字段定义，尤其不能把 PATCH 的“没改”与“清空”混用。

TypeScript 类型不是网络数据验证器。可用运行时 schema 校验关键响应；OpenAPI 等文档和生成类型也必须与实际实现、测试同步，不会自动消除契约漂移。

## 3. HTTP 状态与业务码各管一层

HTTP 状态负责通用结果分类；`code` 是稳定、可供程序分支的具体错误标识；`message` 给人阅读，可能调整，不能拿中文提示字符串当程序判断条件。

```http
HTTP/1.1 404
Content-Type: application/json
X-Request-Id: 这次请求的关联ID

{"code":"TASK_NOT_FOUND","message":"任务不存在","requestId":"这次请求的关联ID"}
```

| 当前行为 | HTTP 状态 | 错误 code |
| --- | --- | --- |
| 标题约束失败 | 400 | `INVALID_ARGUMENT` |
| 分页越界 | 400 | `INVALID_PAGE` |
| JSON 格式或字段类型无法绑定 | 400 | `HTTP_400` |
| GET / PUT 目标任务不存在 | 404 | `TASK_NOT_FOUND` |
| HTTP 方法 / 请求媒体类型不支持 | 405 / 415 | `HTTP_405` / `HTTP_415` |
| 未预期的内部异常 | 500 | `INTERNAL_ERROR` |

404 路由错误也可能是 `HTTP_404`，与“找到任务接口但资源不存在”不同。协议异常保留框架的重要响应头，例如 405 的 `Allow`；不要被全局 `catch(Exception)` 统一改成 500。

未来加入认证、资源权限和更新版本检测时，再约定 401、403（或隐藏资源存在性的 404）、409 等行为。**这些能力当前尚未实现**，不能把已有 7 个测试说成已覆盖登录与越权。

业务拒绝也是失败，主线不把它们伪装为 `200 + 非零code`。对外不返回堆栈、SQL 和凭据；让用户提供 requestId，再在授权范围内查 [日志](/back-end/frontend-backend-guide/26-reading-logs)。反向代理可能返回 HTML 错误页，客户端也应容忍非 JSON 响应。

## 4. 分页：先统一边界，再讨论游标

主线 `page` **从 0 开始**，默认 0；`size` 默认 20，范围 1～100；教学版要求 `page ≤ 10000`。参数非法返回 400，不静默改成另一个值。

```json
{"items":[],"total":0,"page":0,"size":20}
```

SQL 按 `created_at DESC, id DESC` 稳定排序，偏移量是 `page * size`。第二个排序键用于解决相同创建时间的并列；UUID 本身不代表创建顺序。前端页码器若从 1 开始，只在 UI 适配层减 1，不要改 API 规则。

当前列表与总数是两次查询，**不承诺并发时属于同一快照**；稳定排序也不能阻止翻页期间插入、删除引起的重复或遗漏。深 OFFSET 会增加查询成本，限制页码不是查询优化的替代品。

未来数据量大且主要顺序翻页时，可按 `(created_at,id)` 设计游标、相应范围条件和匹配索引。游标不是简单把数字 base64 编码；它应绑定筛选与排序规则，并按需要防篡改。它也不自动提供快照、恒定耗时或任意跳页。

更多查询成本见 [SQL 与索引](/back-end/frontend-backend-guide/10-sql-and-indexes)。不要把尚未实现的 `cursor` 或筛选参数写进当前请求实验。

## 5. 幂等与并发冲突是两件事

幂等表示同一操作重复执行，预期业务状态效果相同，不要求 HTTP 状态和文本每次完全一致。GET 应只读；PUT 设置完整可编辑字段、DELETE 删除资源，应遵守幂等语义。不能把“每次状态推进一步”藏进 PUT。

主线 POST 每次都创建新任务，**尚无幂等键支持**。客户端超时、取消或收到 504，不能证明后端没有提交；当前不能承诺自动重试创建是安全的，见 [代理与超时](/back-end/frontend-backend-guide/22b-proxy-and-discovery)。

未来增加 `Idempotency-Key` 时，至少设计以下闭环，而不是只加一条 Redis 锁：

1. 为每次真实用户操作生成一个键，同一操作的重试复用；新操作不能复用旧键。
2. 用“已验证用户 + 操作范围 + 键”确定作用域，保存请求内容摘要；同键不同内容应按约定拒绝，例如 409。
3. 用数据库唯一约束处理并发，任务创建与幂等结果记录在同一 MySQL 事务内提交；重复请求读取已记录的任务 ID 和结果。
4. 明确处理中请求、事务回滚、提交后响应丢失、结果保留期限和过期后重试的行为；不能在未产生结果时就返回“缓存成功”。

Redis `SET NX` 成功后进程可能崩溃；锁已写入、任务未创建或结果未缓存，都会留下窗口。多系统副作用还需要另外的一致性设计，不会因为加了请求头就自动“恰好执行一次”。

另一方面，两个人用不同请求同时 PUT 同一任务，可能发生最后写入覆盖。幂等键并不解决这个问题；后续可增加版本字段或 ETag / If-Match 条件更新，明确冲突状态并测试。当前实现仍可能相互覆盖。

## 6. 版本与兼容：新增也未必安全

当前 URL 就是 `/api/tasks`，没有 `/v1` 前缀，不要为了讲版本临时让示例请求改地址。未来有不兼容变更时，可以选 `/api/v2/tasks` 等路径方案，或使用其他明确版本策略，并给旧客户端迁移期。

| 变更 | 应怎样评估 |
| --- | --- |
| 删除 / 改名字段、改变类型、把可选入参改必填 | 通常破坏兼容，应迁移或升版 |
| 增加可选请求字段、增加响应字段 | 经常可兼容，但要检查严格客户端、默认值与权限影响 |
| 增加枚举值、错误码、分页排序规则 | 旧客户端穷举与页面行为可能被破坏，不能一概认为“只增就安全” |
| H2 迁移 MySQL | 对外契约应尽量稳定，但需验证时区、精度、约束、查询与事务行为 |

发布前更新契约与自动测试，观察旧接口调用方，再制定废弃、通知、回滚与下线计划。版本号不是兼容性验证的替代品。

## 练习：把一个变更写成验收清单

不必运行服务或修改源码，先在纸上完成：

1. 页面第 3 页，每页 10 条，对主线 API 应发送什么 URL？空页是什么形状？
2. 创建任务超时后，用户重试。当前能否保证只有一条记录？未来幂等记录至少需要哪些信息？
3. 有人提议把 `status` 改为数字 0/1/2，并只改后端。有什么风险？

**参考答案：**

1. `GET /api/tasks?page=2&size=10`；`items: []`，保留 total、page、size 字段，总数不必为 0。
2. 不能。需要作用域、键、请求摘要、处理状态或结果、保留策略，以及与创建记录协调的原子提交和唯一约束。
3. 字段类型变更会破坏现有客户端，且数字含义可能漂移；主线当前明确拒绝数字枚举。应保持字符串契约或设计迁移版本并验证调用方。

## 常见误解与下一步

- “业务错误就要 200”：主线使用正确 HTTP 失败状态和细分业务码，两者不冲突。
- “PUT 幂等就不会覆盖别人的更新”：幂等不等于并发版本检查。
- “游标一定快、永远不重不漏”：取决于查询、索引和数据变化模型。
