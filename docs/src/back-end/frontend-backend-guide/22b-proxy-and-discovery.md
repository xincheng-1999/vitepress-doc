# 22b. 代理与服务发现：请求中间经过了谁

> 场景：本机 `task-api:8080` 正常，部署后域名却返回 502。浏览器访问的是 Nginx，不是直接访问 Java 进程。
> 本篇不要求先会微服务，而是从“给单体任务系统加一个统一入口”开始。

先读 [网络入门](/back-end/frontend-backend-guide/22-networking-for-backend) 与 [HTTP、浏览器](/back-end/frontend-backend-guide/22a-http-and-browser)。我们的业务仍是 `/api/tasks`：早期 H2 本地练习，部署主线迁移 MySQL。只有确实需要时，才讨论服务拆分。**初始 CRUD 没有登录与用户隔离，只适合受控本地练习；下述公网入口是补齐安全能力后的目标架构，不是当前源码的上线承诺。**

**学完你能做什么：**

- 区分正向代理、反向代理、CDN、网关、负载均衡的角色，不把它们当同义词。
- 读懂一段 Nginx 转发配置，知道请求路径有没有被改写、超时发生在哪段。
- 分清服务发现、注册中心、配置中心；理解普通 Kubernetes Service 的 DNS 答案。

## 22b.1 先画最小部署，不从微服务全家桶开始

开发时，浏览器可以直连 `http://localhost:8080/api/tasks`。部署时，更常见的是同域名入口：

![浏览器经反向代理访问任务服务、数据库，以及可选的静态资源 CDN](/backend-guide/network-proxy-topology.svg)

浏览器请求 `https://tasks.example.com/api/tasks`；反向代理接收 HTTPS，再转发给单体。浏览器不应直接连接 MySQL。后端使用数据库协议连接 MySQL，认证凭据留在服务端。

这个结构里每个组件都有一个明确理由：入口处理 HTTPS 与路由，应用处理业务，MySQL 保存任务。**没有注册中心也完全可以运行单体应用。**

若代理与应用在同一主机，应用可只绑定回环 8080，减少暴露面；若在不同主机或不同容器，代理就不能用自己的 `127.0.0.1` 找对方，需要可达的服务地址及相应访问控制。

## 22b.2 正向代理与反向代理：站在哪一边看

代理接收一侧的连接，再代表它向另一侧发起连接。方向不是“数据往左还是往右”，而是它主要服务谁。

| 角色 | 主要代表谁 | 日常场景 | 谁选择代理 |
| --- | --- | --- | --- |
| 正向代理 | 客户端 | 公司出口代理、开发机配置 HTTP_PROXY | 客户端或客户端网络策略 |
| 反向代理 | 服务端入口 | Nginx 接收域名请求，转发给 `task-api:8080` | 域名、部署与入口配置 |

HTTPS 经过正向代理时，常用 CONNECT 建立到目标的隧道；代理不一定能看到加密正文。企业安装受信任证书并进行解密检查是另一种部署，不应把“有代理”理解成“正文必定被代理解密”。

反向代理通常终止客户端 TLS，所以能按 HTTP 路径路由。它可以再用 HTTP 或 HTTPS 访问上游；这取决于配置和安全要求，而不是因为“代理后面都是安全内网”。

排错时，开发机的 `HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY` 可能改变访问路线。文档中的 `curl --noproxy '*'` 只用于明确需要直连的本地实验，不是让你绕过公司的生产访问策略。

## 22b.3 Nginx：保留路径，先让转发可解释

下面是**配置阅读示例**，不要求现在安装或运行 Nginx。它展示 HTTP 转发关系，省略生产 TLS 证书、静态资源等配置；公网生产入口应启用 HTTPS，不能直接把此示例当完整上线方案。

```nginx
http {
    upstream task_backend {
        server 127.0.0.1:8080;
        keepalive 16;
    }

    server {
        listen 80;
        server_name tasks.example.com;

        location /api/ {
            # 没有 URI 部分：/api/tasks 保持为 /api/tasks
            proxy_pass http://task_backend;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_connect_timeout 2s;
            proxy_send_timeout 10s;
            proxy_read_timeout 10s;
        }
    }
}
```

这里假定代理和应用在同一网络环境，`127.0.0.1:8080` 才能找到应用。upstream 名字 `task_backend` 是配置里的分组名，不会自动创建 DNS 服务。

最常见的路径坑是下面这一字之差：

```nginx
# 在 location /api/ 内，带 URI 部分 /，会用 / 替换匹配前缀
proxy_pass http://task_backend/;
# /api/tasks 将变成 /tasks，后端若只认识 /api/tasks 就可能返回 404
```

上述替换规则适用于这里的普通前缀 location；带变量、正则 location、rewrite 时有额外规则，不能机械套用。出现 404 先比对实际转发路径，而不是先改 Java Controller。

`proxy_connect_timeout` 限制连接上游的阶段；`proxy_read_timeout` 通常是**相邻两次读取之间**允许的空闲时间，不是整次请求的绝对截止时间；`proxy_send_timeout` 也不是“业务执行时间”。超时值要与客户端、业务预算和数据库超时协调，不能统一加大到几分钟掩盖问题。

Host 和转发协议影响后端生成链接、重定向和安全 Cookie。后端只应信任来自**受信任代理**的转发信息；公网客户端也能伪造 `X-Forwarded-*`、`X-Request-ID`，不能把这些头直接当用户身份或审计事实。

真实部署还应记录请求 ID、上游地址、连接时间、响应时间、状态等。主线应用自行生成 `X-Request-Id`，不会直接信任外部请求 ID；代理可记录上游返回的 `$upstream_http_x_request_id`，再关联应用日志。代理未连上应用时则用代理自身的 ID 排查。请求 ID 不应包含隐私。

## 22b.4 CDN、网关、负载均衡：能力可以重叠，职责不同

### CDN：把可缓存内容放到更近的位置

内容分发网络 CDN 在多个位置部署节点，让客户端就近获取缓存内容。任务页面的公开 JS、CSS、图片适合这一思路；带个人数据的 `/api/tasks` 不能照搬静态文件缓存规则。

有的 CDN 还提供动态请求加速、安全防护和反向代理能力，所以“用了 CDN”不等于“每个请求都从缓存返回”。观察缓存头、响应头和回源日志，才能知道是否命中。

共享缓存必须正确处理用户身份、查询参数和缓存键。入门阶段，私人任务接口明确 `Cache-Control: no-store`，比误缓存整个接口安全。不要把登录 Cookie 或令牌塞进 URL，它们可能出现在日志、浏览器历史和中间层缓存里。

### 网关：给 API 加统一入口策略

API 网关常负责路由、认证接入、限流、配额和观测；但**任务属于谁、谁能修改**仍需要应用校验。网关验证“这个 token 是有效用户”不等于已经验证“他能删任务 42”。

Nginx 可以承担部分网关功能，专用网关通常提供更多 API 管理能力。网关是角色，不意味着必须另起一个微服务；单体入门可以先由反向代理和应用安全框架共同完成。

### 负载均衡：多个副本怎样分担请求

负载均衡把请求或连接分给多个可用后端。它可能工作在 TCP 连接层，也可能理解 HTTP；常见策略有轮询、最少连接和按键哈希，不只有一种“平均分配”。

如果未来有两个 `task-api` 副本，都监听各自网络环境的 8080，可在 upstream 中加入两个可达地址。客户端仍访问同一域名和 `/api/tasks`，不必认识副本。

但加副本前要先处理状态：

- **共同数据源**：多个副本应使用同一套正确配置的 MySQL，而不是各带一份内存 H2；后者会出现“刷新一次任务就变了”。
- **会话**：只存在某个进程内的会话可能让请求切到另一副本后失效；选择可共享会话或可验证令牌等方案。
- **本地状态**：上传文件、后台任务、缓存、定时任务都要评估多副本行为，不能仅靠复制进程。
- **健康状态**：进程存活不等于可接业务；启动、数据库不可用、退出期间要正确处理就绪和连接排空。

会话粘滞可以临时把某用户尽量分到同一副本，但不是数据共享、容灾和会话设计的替代品。基础 Nginx 配置中的失败探测也不应被想当然地当作完整主动健康检查。

## 22b.5 BFF：为界面整理数据，不是再写一套数据库

BFF 是“面向特定前端的后端层”。例如移动端任务首页要同时显示“未完成数、最近任务、用户偏好”，可以由这一层组合并裁剪响应，减少客户端多次往返。

单体阶段，可以先在 `task-api` 中提供一个页面聚合接口，不必为 BFF 额外部署进程。只有不同客户端的节奏、权限或聚合逻辑明显分化时，再评估独立 BFF。

不要把边界混为一谈：

- 反向代理主要转发；BFF 主要理解页面需要的数据形状。
- 网关主要执行通用入口策略；BFF 可以包含客户端特定的组合逻辑。
- 核心任务规则、事务与权限仍由明确的业务层承担，不能在多个 BFF 里各写一份。

## 22b.6 可选：RPC 与 gRPC，不要把远程调用当本地函数

当单体足够用时，直接调用 Java 方法最简单。拆出独立通知服务后，网络边界才出现：`task-api` 调用另一个进程，不再享有本地方法调用的失败模型。

RPC 是远程过程调用的风格：让调用方按“某服务的某方法”表达操作。它是一类抽象，不是唯一的传输协议；使用 HTTP 传输的接口也可能具有 RPC 风格。

gRPC 是具体框架，常用 Protocol Buffers 定义服务和消息，再生成客户端 / 服务端代码；通常基于 HTTP/2，支持普通调用及流式调用。它不是“用了 protobuf 就自动变成 gRPC”，也不是发现服务的系统。

| 对比 | 面向资源的 HTTP JSON 接口 | gRPC 常见方案 |
| --- | --- | --- |
| 表达 | 方法 + 路径，如 GET /api/tasks | 服务 + 方法，由协议定义生成代码 |
| 数据 | 可读 JSON，字段约定需管理 | 常用二进制 protobuf，仍要维护兼容性 |
| 浏览器 | fetch 可直接使用 | 常需要 gRPC-Web 等适配与代理，不能当普通 fetch JSON |
| 网络失败 | 超时、断连、部分执行 | 同样存在，类型生成不能消除远程失败 |

RPC 调用要设置截止时间、限制重试，并传递认证和观测上下文。客户端超时或取消不意味着服务端事务已回滚；跨进程也不会自动获得单库事务的原子性。

初学者先把 `/api/tasks` 的契约、错误和超时讲清楚，再把 gRPC 作为选型项。微服务不是“后端入门毕业证”。

## 22b.7 服务发现、注册中心、配置中心：分别回答不同问题

先想一个变化：`task-api` 增加副本，旧副本退出，新副本地址不同了。调用方需要知道“现在该访问谁”，这就是**服务发现**问题。

| 概念 | 回答的问题 | 例子 |
| --- | --- | --- |
| 服务发现 | 某个服务当前有哪些可访问入口？ | DNS 名、负载均衡地址或实例列表 |
| 注册中心 | 实例信息在哪里登记、更新、过期？ | 实例上报地址、心跳，调用方订阅列表 |
| 配置中心 | 某环境的配置是什么、如何版本化和分发？ | 特性开关、超时阈值、业务参数 |

服务发现是能力，注册中心是一种实现支撑，不是同义词。一个产品可能同时提供注册与配置功能，逻辑职责仍然不同。配置中的数据库密码也不是服务发现记录；机密信息应采用合适的密钥管理和权限隔离。

只有一个单体时，环境变量里的固定地址、反向代理 upstream 配置就可能足够。DNS 也能提供稳定名字，因此并不是“只要调用另一个服务，就得上一个注册中心”。

注册信息与健康探测都可能滞后：实例注册了不一定就绪，心跳正常不代表业务数据库可用，缓存实例列表也可能包含已退出节点。因此客户端仍需要超时和失败处理，不能把注册中心当可靠性保证。

### Kubernetes 中的名字到底指向什么

进入 [Kubernetes 实战](/back-end/frontend-backend-guide/24-kubernetes-in-practice) 后，你可能见到 `task-api.default.svc.cluster.local`。默认集群域可以被配置，跨命名空间访问要使用合适名称。

- **普通 ClusterIP Service**：DNS 通常返回 Service 的虚拟 ClusterIP；随后由集群网络机制把流量转给后端端点，**不是 DNS 必然直接返回某个 Pod IP**。
- **Headless Service**（无头，`clusterIP: None`）：DNS 可返回后端端点地址，客户端需要理解多地址和更新。
- 端点是否发布还受就绪状态、Service 配置等影响；名字可解析不等于每个后端都能成功处理业务。

Pod 地址变化，Service 名称和入口可以保持稳定；这正是把“服务名”和“某个具体进程地址”分开的价值。Kubernetes 的服务信息由控制平面维护，不需要为了同一目的再强行加入另一个注册中心。

## 22b.8 502 与 504：先知道是谁返回，再找证据

客户端看到的状态可能来自 CDN、入口代理、网关或应用自身。**收到 HTTP 响应只证明到响应者的路径成功，不证明后面的每一跳成功。**

| 现象 | 可能发生的阶段 | 优先查什么 |
| --- | --- | --- |
| 502 | 上游连接拒绝、连接重置、协议不匹配、响应无效等 | 实际上游地址、监听、HTTP/HTTPS 配置、代理错误日志 |
| 504 | 连接上游超时、等待响应头或读取响应超时等 | 连接时间、响应等待时间、路由策略、应用与数据库日志 |
| 503 | 无可用后端、过载、维护等，依产品与配置而定 | 就绪状态、容量、限流来源、发布过程 |
| 404 | 入口路由未命中，或上游接口不存在 | 请求命中哪层、转发后的路径 |

一个关键反例：代理连接上游时包被丢弃，最终返回 504，此时应用可能根本没收到 HTTP 请求。另一个反例：数据库提交完成后，返回路径断了，客户端同样可能看到失败。**不能由 504 判断“没执行”或“肯定执行了”。**

对创建任务，先用请求 ID、幂等键或业务查询确认结果，再决定是否补偿或重试。只看状态码就让前端无限重试，可能把一次故障变成重复数据和更高负载。

## 22b.9 动手：直连与入口对照，不靠猜测

这些实验不要求新增部署或运行代理。先用已有本地任务服务完成直连部分；只有已经有授权测试入口时，才进行入口对照。文档中的 example 域名不是可用的测试服务。

### 实验一：记录直连基线

```bash
curl --noproxy '*' --max-time 5 -sS -o /dev/null \
  -w 'status=%{http_code} connect=%{time_connect}s first_byte=%{time_starttransfer}s total=%{time_total}s\n' \
  http://127.0.0.1:8080/api/tasks
```

预期：无认证的本地练习得到 `status=200`；开启认证可能是 401。时间值随环境变化。这里的计时均相对操作开始，不能把 first_byte 数字直接当成“纯业务处理时间”；有代理、TLS 时各阶段还会包含更多工作。

### 实验二：对照已有测试入口

若已有 HTTPS 测试域名，**把下列占位域名替换为自己的已授权入口**，再运行：

```bash
curl --max-time 10 -i https://your-test-host.example/api/tasks
```

预期：入口可用时，接口语义应与直连一致；直连 200、入口 404 时查路由与路径；入口 502 / 504 时看代理日志。不要使用 `-k` 跳过证书检查；证书错误应作为独立问题修复。

入口通常不能从客户端直接暴露其内网细节，因此响应头未必包含上游地址。这时需由有权限的人查询脱敏日志，而不是断言“没这个头所以没经过代理”。调试时如改用 `curl -v`，须注意它可能输出令牌、Cookie、Set-Cookie 等敏感内容。

### 实验三：不用破坏环境也能检查路径和超时

在前面的 Nginx 配置中，手工把 `/api/tasks?page=0&size=20` 代入两种 `proxy_pass` 写法，写出上游路径；再假设代理连接上游 2 秒没有成功，指出会涉及哪个超时设置。

预期答案：无 URI 部分时保持 `/api/tasks?page=0&size=20`；带 `/` 的前缀替换示例会变为 `/tasks?page=0&size=20`；建连阶段看 `proxy_connect_timeout`。即便最终返回 504，也不能宣称任务 Controller 已执行。这个实验不需要停服务、改防火墙或制造生产故障。

## 常见误解

- “用了 Nginx 就有微服务”：它同样适合单体部署。
- “有负载均衡就能直接复制 H2 应用”：独立内存数据库不会自动共享任务。
- “网关验过 token，业务就不用鉴权”：应用仍要验证资源所有权和业务权限。
- “DNS、注册中心、配置中心都是存配置的”：分别关注名字解析、实例目录和应用配置，不能互换。
- “内网调用无需加密认证”：网络位置不是身份；应按威胁模型保护每一跳。

## 自测与参考答案

1. 两个任务副本各用自己的 H2，负载均衡能让它们看到同样的数据吗？
2. Kubernetes 普通 Service 的 DNS 答案通常是 Pod IP 吗？
3. 注册中心显示一个实例在线，能否不设置调用超时？
4. POST 创建任务后入口返回 504，可以立即无限重试吗？

**参考答案：**

1. 不能。需要一致的共享持久化方案；本主线部署使用 MySQL，并处理会话和进程内状态。
2. 通常不是，普通 ClusterIP Service 返回虚拟 ClusterIP；无头 Service 等情况不同。
3. 不能。注册、探测、业务状态有时间差，网络也可能失败。
4. 不可以。执行结果不确定，先确认结果，结合幂等设计和有界重试。
