# 性能与高并发

任务列表平时很快，一到活动时段就开始排队。有人建议加缓存，有人说把线程池调大，还有人想直接多开几个副本。该先做哪一个？

先别同时改。我们围绕“请求变多以后，列表为什么变慢”逐步检查，再看缓存、限流、熔断和异步分别能解决哪一段问题。这里是按需阅读的专题，不要求沿 [五阶段主线](./index) 入门时就把这些组件全部装上；数据与压测输出均为示意，没有进行真实容量测试或生产验证。

## 1. 先定义什么叫“变慢了”

先选定接口、查询条件和时间段，比较正常与异常时的请求量、延迟分布、错误率及超时。不要把“处理了很多请求”和“成功完成了很多业务”当成一回事：快速返回 429 或业务失败，也可能让吞吐数字很好看。

例如期望列表在当前业务数据规模下大多数请求能在 300ms 内完成，同时限制超时和失败比例。这只是示例要求，实际标准应来自业务，而不是照抄一个 P99 阈值。

接着看同一时间段的分段耗时与资源。假如 CPU 还有余量，但查询调用耗时升高、连接等待也增加，应先查数据库查询和连接持有时间；直接增加应用线程，可能只会让更多请求同时挤向数据库。

这些观察入口见 [可观测三件套](/back-end/frontend-backend-guide/30-observability)，具体工具见 [排查工具箱](/back-end/frontend-backend-guide/29-diagnostic-toolbox)。

## 2. 在可控环境中，确认从哪里开始排队

已有授权的隔离测试环境时，可以用逐级增加负载的方式验证。先准备与目标场景接近的数据量、查询分布和依赖配置，再从很小并发开始。测试流量不能流向真实支付、收费 API 或共享生产依赖，读接口也可能触发缓存回填与大量查询。

例如 `wrk` 已安装、本机应用确实提供只读列表接口时，可以从这样的规模开始：

```bash
wrk -t1 -c5 -d10s --latency http://127.0.0.1:8080/api/tasks
```

`-t1` 是一个压测线程，`-c5` 是五个连接，`-d10s` 是十秒，`--latency` 输出延迟分布。这不是推荐容量值，只是展示命令格式。执行前还要确认应用和依赖都有足够资源，过程中若达到预设停止条件就停止，不为了“测出极限”把环境拖垮。

假设输出摘要是：

```text
Latency Distribution
  50%   10.00ms
  90%   20.00ms
  99%   45.00ms
4000 requests in 10.00s
Requests/sec: 400.00
```

这只表示这次条件下完成了约每秒 400 次请求。还要检查 socket 错误、超时、非成功状态、业务响应内容以及服务端指标，才能判断是否满足要求。不能由一次十秒、五连接的结果得出“单实例上限就是 400 QPS”。

`wrk` 的连接数不是业务用户数，结果还受压测机能力、网络、请求内容和闭环发请求方式影响，延迟统计也可能低估某些排队影响。复杂流程、鉴权与业务断言可使用 JMeter 等工具；需要精确模拟到达速率时应选择相应负载模型，而不是只提高连接数。

在每一级负载下保存同样的数据。如果吞吐不再明显增长，P99 与连接等待却快速上升，就回到对应查询找原因。慢 SQL、索引选择与分页方式见 [SQL 与索引](/back-end/frontend-backend-guide/10-sql-and-indexes)。

## 3. 先修昂贵的工作，再考虑让它少做几次

假设列表慢的原因是无界查询或循环逐条查询，先处理分页、批量读取、索引与返回字段。把本来不合理的工作缓存起来，可能只是让第一次请求或缓存失效时继续受影响。

查询已经合理，但大量请求仍重复读取相同、允许短暂陈旧的数据，这时才考虑缓存。先回答两件事：缓存什么，写入后怎样失效。

例如公开的任务模板名称、配置字典适合缓存；用户私有列表涉及身份、筛选条件和权限变化，缓存键与失效规则要额外设计。余额、配额扣减等权威判断不能依赖本地缓存的旧值，相关一致性取舍见 [事务与一致性](/back-end/frontend-backend-guide/11-transactions-consistency)。

常见顺序是先查缓存，未命中再查数据库并回填。Redis 让多个实例共享缓存；Caffeine 则保存在当前 JVM 内，少一次网络访问，但每个实例都有自己的副本。命中率、延迟和一致性都要按实际数据测量，不把“本地纳秒、Redis 微秒”当成固定保证。基本策略见 [Redis 实战](/back-end/frontend-backend-guide/12-redis-in-practice)。

::: details 按需看：一个有容量和过期限制的本地缓存

如果自己的 Java 工程已引入 Caffeine，可以先用有限容量缓存允许陈旧的公开模板说明。下面是独立的缓存用法片段，不包含数据库与权限逻辑，也不是仓库中的现成业务服务。

```java
import com.github.benmanes.caffeine.cache.Cache;
import com.github.benmanes.caffeine.cache.Caffeine;
import java.time.Duration;

Cache<Long, String> templateDescriptions = Caffeine.newBuilder()
        .maximumSize(1_000)
        .expireAfterWrite(Duration.ofSeconds(30))
        .build();

// 已从授权的数据源读到公开说明后，才放入缓存
templateDescriptions.put(101L, "每周计划模板");
String description = templateDescriptions.getIfPresent(101L);
```

`getIfPresent` 未命中返回 null，调用方再按自己的数据访问逻辑处理。`maximumSize` 限制条目数，不是严格的内存字节上限；Caffeine 的淘汰也不应简单称为纯 LRU。

三十秒只是示例。各实例本地副本不会因为 Redis 删除了一个 key 就自动失效；广播失效也可能丢失或延迟。需要结合业务容忍时间、缓存击穿、并发回填和故障时回源压力设计，而不是认为“TTL 短就没有一致性问题”。
:::

修改后，用同样条件再测。如果查询压力下降、延迟改善，还要验证缓存未命中、失效与数据变更时的行为。只测热缓存不能代表全部运行情况。

## 4. 请求超过处理能力时，先限制进入量

即使单次查询已经合理，流量仍可能超过系统能稳定处理的范围。这时需要 **限流**：限制某个时间范围内允许多少请求进入，而不是让它们无限排队。

客户端防抖只能减少自家页面的请求，服务端限流约束的是所有到达请求。限流维度还要明确：每用户、每租户、每接口，还是整个系统。按用户限流不等于总量保护，很多用户同时访问仍可能压满系统。

如果网关有多个副本，每个实例各允许 100 次/秒，整体就可能放过约实例数倍的流量。需要全局配额时，要使用共享或协调的限流方案；网关位置可结合 [架构总览](/back-end/frontend-backend-guide/02-architecture-overview) 理解。

::: details 按需看：几种算法怎样选择

| 算法 | 它限制什么 | 使用时要注意 |
| --- | --- | --- |
| 固定窗口 | 每个固定时间段内计数 | 窗口交界处可能集中放行两批请求 |
| 滑动窗口 | 最近一段时间的请求数 | 分桶有近似误差；满足窗口总量也仍可能短时集中到达 |
| 漏桶式整形 | 按近似固定速率放行 | 排队容量与等待时间有限，满了仍需拒绝 |
| 令牌桶 | 以固定速率补充令牌，允许消耗积累的令牌 | 同时限制长期速率与可接受突发量，并不保证匀速输出 |

需要平滑调用一个敏感下游时，可考虑匀速整形；允许短时突发但限制长期速率时，可考虑令牌桶。没有对所有接口都最合适的算法。

Spring Cloud Gateway 的 Redis 限流器等组件可以提供分布式限流，但要核对所用版本、键解析器、Redis 故障策略与实际配置。用户维度应来自可信的认证结果，不能直接信任外部传入的用户头。

如果只保护一个 Java 进程中的昂贵步骤，Guava 的 `RateLimiter` 等单机工具可以作为选择。它限制速率，不等于限制同时在途的并发数；单次调用变慢时，还需要独立的并发隔离或有界队列。Sentinel 等工具可管理更多规则，但不会替你决定业务阈值。
:::

被限流时，应按契约明确返回，例如 HTTP 429，并让客户端退避；不要立即无界重试。测试时分别统计被接收的请求、被拒绝的请求和成功完成的业务，确认没有把“更快拒绝”误当成“处理能力提高”。

## 5. 如果是某个下游变慢，别让等待占满自己

列表有时还会读取外部摘要。即使进入的请求数不变，下游从几十毫秒变成几秒，每个请求持有线程、连接的时间也会变长，最终在调用方排起队。

先设置合适的连接、读取或整体超时，并确定调用方何时取消等待、下游工作是否也能取消。超时不是“操作必定没发生”，写请求尤其不能直接重试。同步调用怎样占用资源，见 [请求的完整链路](/back-end/frontend-backend-guide/03-request-lifecycle)。

**熔断**是在一段统计窗口里失败或慢调用达到条件后，暂时减少或停止对故障下游的调用。常见状态是关闭、打开、半开：正常调用并统计；异常时快速失败；冷却后只放少量探测，再决定是否恢复。具体统计条件、最小调用量和状态转换由组件配置决定。

**降级**则是业务选择：非关键摘要可以暂时省略或返回允许陈旧的数据；权威查询失败不能伪装成真实的空列表或“余额为零”。Resilience4j 等可以实现熔断与隔离，但 fallback 返回什么，需要接口语义允许。

也不要在每次 fallback 中自动再发一条重试任务。原调用可能已经生效，这样会制造重复与积压；可靠任务提交和重试需要另行设计。

## 6. 如果工作本来就很久，再考虑异步

对列表查询而言，先让用户拿到任务编号、以后再取列表，未必符合预期，不能因为同步慢就一律改异步。对于生成报表、处理文件等确实允许稍后完成的工作，才适合拆成“提交”和“执行”。

```text
提交请求 → 验证与可靠记录任务 → 返回可查询的任务编号
                             ↓
                       有容量限制的队列
                             ↓
                     工作进程处理 → 更新结果
```

返回“已接受”之前，要明确任务是否已经可靠保存；数据库写入和发消息之间还可能失败，不能用两行顺序调用就宣称不会丢任务。消息重投、幂等、重试和补偿见 [消息队列可靠性](/back-end/frontend-backend-guide/33-mq-reliability)。

队列只能缓冲短期差异。若到达速度长期大于处理速度，积压仍会一直增长，所以还需要队列容量、最长等待、拒绝策略与失败处理。把积压搬到队列里不等于提升了最终完成速度。进程内异步和持久化队列的区别可查 [异步编程](/back-end/frontend-backend-guide/17-async-programming)。

批处理可以减少往返，但也改变了可见延迟与失败范围。内存里攒计数再定时刷库，进程崩溃会丢未刷数据，取出缓冲与写入失败还要防止丢更新；不能直接用于扣费等不能丢的数据。

## 7. 最后才决定是否调池或加副本

线程池与连接池复用昂贵资源，也限制同时工作的数量。池太小可能等待，太大则可能把压力推到数据库或耗尽内存。先看任务服务时间、等待、拒绝、连接持有与下游容量，再决定调整，分别见 [线程池与 Executor](/back-end/frontend-backend-guide/15-thread-pools-executor) 和 [连接池](/back-end/frontend-backend-guide/13-connection-pools)。

如果剩下的瓶颈在 GC，先看分配量、对象存活与暂停记录，不把“换 GC”当第一步，见 [垃圾回收 GC](/back-end/frontend-backend-guide/19-garbage-collection)。

应用已经能横向扩展、单实例是瓶颈时，多副本可能有效；共享数据库、外部限额或热点锁是瓶颈时，增加应用副本反而可能更糟。还要确认会话、任务状态和本地缓存是否允许多实例运行。扩缩容机制见 [Kubernetes 实战](/back-end/frontend-backend-guide/24-kubernetes-in-practice)。

“峰值请求量 ÷ 单实例安全吞吐”可以作初步估算，不能当最终容量结论。实例之间会共享依赖，还要考虑故障冗余、扩容启动时间、冷热缓存和负载倾斜；安全余量也不应统一取某个百分比。

回到最初的选择题：先把同一接口的瓶颈查清，修掉不必要的工作，再按结果决定缓存、限流、隔离、异步或扩容。每次改动后用相同条件比较，并确认数据与接口语义没变。性能够用之后，权限与数据保护同样不能省略，可接着按需看 [安全](/back-end/frontend-backend-guide/32-security)。
