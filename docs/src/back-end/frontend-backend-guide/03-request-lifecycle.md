# 新增任务的请求，到达后端以后发生了什么？

前面已经知道请求怎样找到服务器，也分清了用户访问网页和工程师登录服务器。现在回到用户点击“新增任务”的这一次操作，继续看它到达后端以后怎样被处理。

先不必记住所有框架名字。沿着“接收请求 → 处理任务 → 保存数据 → 返回结果”往下看就可以了。

## 1. 应用先接住 HTTP 请求

页面把标题转成 JSON，发送到 `POST /api/tasks`。本地练习时，请求直接到达监听 8080 的应用；如果前面有反向代理，就先由代理接收，再转发给应用。

本课程使用 Spring Boot 和 Spring MVC，内嵌的 Tomcat 负责接收 HTTP 连接，并把请求交给应用处理。你暂时可以把它理解为应用对外接收请求的那一部分。

请求进入后，还会经过一些公共处理。例如，配套工程用 Filter（过滤器）为请求生成 ID 并记录日志。后面加入登录时，Spring Security 的过滤器链也会在这里参与检查身份。

## 2. 根据路径找到方法，再读出标题

Spring MVC 接下来要找出“这次请求应该由谁处理”。它会同时看 HTTP 方法和路径，比如 `POST /api/tasks`，再找到对应的 Controller 方法。

负责协调这件事的入口叫 `DispatcherServlet`。你以后在文档或日志里看见这个名字，知道它属于请求分发过程就够了。

找到方法后，Spring 会把 JSON 转成 Java 请求对象。例如：

```text
HTTP 请求体：{"title":"学习 SQL"}
                   ↓
Java 请求对象：CreateTaskRequest，title 为“学习 SQL”
```

JSON 只是传输的数据格式，不是网络里直接飞过来了一个 Java 对象。转换时如果类型不对，或者字段没有通过校验，请求会在这里被拒绝，还没有进入保存任务的业务代码。

请求对象只接收允许用户填写的内容。本例创建时只需要标题；ID、初始状态和创建时间由后端生成。

## 3. Controller 把任务交给业务代码

读出请求以后，Controller 调用 Service。Service 负责“创建任务”这件事：检查规则，生成 ID，把初始状态设为 TODO，再调用 Repository 写入数据库。

这几个名字先对应到各自的工作即可：Controller 接 HTTP，Service 处理业务，Repository 读写数据库。它们之间是同一个 Java 程序里的方法调用，不是又发了几次 HTTP 请求。

![一次请求经过过滤器、路由和参数转换，再调用业务代码并写入数据库](/backend-guide/core-request-flow.svg)

Repository 使用 JDBC 访问数据库。用 H2 内存库时，是在进程内读写；换成 MySQL 后，就要通过数据库连接，把 SQL 发给独立运行的 MySQL。

如果这次操作放在数据库事务里，正常完成后会提交。事务究竟怎样保证一组修改一起成功，会在后面的 SQL 课程里实际演示。

## 4. 把保存结果返回给页面

创建成功后，后端把任务的 ID、标题、状态和创建时间组成响应对象。Spring 再把它转成 JSON，写入 HTTP 响应。

第一个实验中的成功状态是 `201 Created`。页面收到响应，才把新任务显示出来。

注意这里的先后顺序：数据可能已经保存，但响应还在返回途中。如果这时断网，页面看到的可能是超时。因此，页面没有收到成功消息，并不能直接说明数据库里没有这条任务。

## 5. 出错时，先看请求走到了哪里

这条处理过程也能帮助你判断错误。

标题为空，通常在参数校验时就返回 `400`；路径没有对应接口，可能返回 `404`；数据库连接异常，则要继续看数据库和应用日志。具体状态由错误位置及接口约定决定，不能把所有失败都处理成 `500`。

配套工程会在响应头里返回 `X-Request-Id`，并在日志里记录同一个 ID。以后联调时，可以拿着这个 ID 找到对应请求，而不是在所有日志中凭时间猜。

Spring MVC 的全局异常处理负责这一范围内的错误。代理连接失败或后台线程出错，并不会自动都回到同一个异常处理方法里；在学到相关功能时，我们再分别处理。

::: details 补充：为什么有些接口返回了，后台工作还没完成？
创建任务通常会等数据库操作完成，再返回 `201`。但导出大量任务可能需要更久，所以也可以先可靠地记录导出请求，返回 `202` 和任务 ID，让后台继续处理。

这时前端仍然可以写 `await fetch(...)`，但它等到的只是“导出请求已被受理”，不是“文件已经生成”。页面需要继续查询进度。后台任务还要保存状态和处理重启恢复，具体见 [消息与后台任务](./33-mq-reliability)。

同步处理请求时，线程也可能在等待数据库连接或 SQL 完成。线程池和数据库连接池管理的是不同资源，应用变慢后需要分别检查，见 [连接池](./13-connection-pools)。这里先不展开性能参数。
:::
