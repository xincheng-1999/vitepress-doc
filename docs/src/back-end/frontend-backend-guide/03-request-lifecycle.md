# 一个请求进入 Spring 之后

> 学习目标：把浏览器 Network 中的一行请求，对应到服务器入口、参数绑定、业务方法、SQL、事务和响应；发生错误时知道往哪里查。

前置：[网络](./22-networking-for-backend)、[HTTP 与浏览器](./22a-http-and-browser)、[代理](./22b-proxy-and-discovery)。Java 代码此时看不懂没关系，先跟箭头。

## 1. 把一次「新增任务」展开

![请求从代理进入 Servlet 过滤器、Spring MVC、业务服务和数据库的完整路径及异常边界](/backend-guide/core-request-flow.svg)

一次正常请求的故事：

1. 前端把对象 `JSON.stringify` 成 JSON，经 HTTP 发送 `POST /api/tasks`。
2. 如有 Nginx，它先接收，再建立 / 复用**另一条连接**转发到 `task-api`。本地直连时没有这一跳。
3. Tomcat 接收 HTTP，在本课程的同步 Spring MVC 模型中，由工作线程处理请求。
4. Servlet **Filter** 可做请求 ID、日志、CORS、安全过滤；Spring Security 也是通过过滤器链工作。
5. **DispatcherServlet** 是 Spring MVC 入口：根据方法与路径查找处理器。MVC Interceptor 的 `preHandle` 在匹配处理器后、调用前运行。
6. Spring 的参数解析器通过消息转换器把 JSON 转成请求对象；`@Valid` 配合校验依赖检查字段。
7. **Controller** 把协议输入交给 **Service**。Service 执行业务规则、权限与事务内操作。
8. **Repository** 通过 JDBC 发参数化 SQL。独立 MySQL 场景先从连接池借连接；教学 H2 也是通过 JDBC，但不是跨网络访问。
9. 事务提交后构造结果。Spring 用 JSON 转换器把 Java 响应对象序列化，写回 HTTP。
10. 浏览器收到状态码和 JSON，页面才更新列表。即便数据库已提交，这一步也可能因断网失败。

不要背框架类名，先能解释**哪一步跨网络、哪一步只是函数调用、哪一步写入事实数据**。

## 2. 请求里的数据会换四次形状

| 位置 | 示例 | 为什么分开 |
| --- | --- | --- |
| HTTP 字节 | `{"title":"学习 SQL"}` | 网络中没有真正的 Java / JS 对象 |
| Request DTO | `CreateTaskRequest` | 只接受允许客户端设置的字段 |
| 业务 / 存储对象 | 如 `TaskRow`（概念示意） | 包含数据库 ID、状态、创建时间等；小实验为简化映射复用 TaskResponse，不另建此类 |
| Response DTO / VO | `TaskResponse` | 只暴露允许前端看到的字段 |

如果请求直接绑定数据库实体，客户端可能把 `ownerId`、`admin`、`price` 等本不该改的字段一并提交，这类问题常叫**过度绑定 / Mass Assignment**。

这些名称是团队约定，不是必须为每一个对象机械创建四个类。目标是保护边界，不是增加样板代码。

## 3. 异常不是「任何位置都自动兜住」

`@RestControllerAdvice` 主要参与 Spring MVC 的异常处理，**不自动兜住所有过滤器、后台线程、代理或连接错误**。

| 失败位置 | 可能现象 | 去哪里看 |
| --- | --- | --- |
| DNS / TCP / TLS | 没有 HTTP 响应 | 客户端网络证据、端口、DNS、证书 |
| 反向代理 | 502 / 504 | 代理访问日志与错误日志、上游连接 |
| 安全 Filter | 401 / 403 | 安全组件的异常处理与认证配置 |
| 路由匹配 | 404 / 405 | URL、HTTP 方法、映射路径 |
| JSON / 参数校验 | 400 / 415 | Content-Type、请求体、校验信息 |
| Service 业务规则 | 404 / 409 等约定状态 | 业务异常码、数据状态、权限 |
| SQL / 数据库 | 约束异常、500、超时 | SQL、事务、连接池、数据库日志 |
| 后台任务 | HTTP 已返回但任务失败 | 持久任务记录、worker 日志、重试与告警 |

异常处理要保留**服务端堆栈和请求关联 ID**，对外返回稳定、可理解的错误。不能把数据库密码、SQL 原文或整段堆栈直接回给用户。

## 4. 线程池、连接池与等待

一个同步请求可能依次等：入口排队 → 空闲工作线程 → 数据库连接 → SQL 锁 → 数据库执行 → 外部服务。

- **线程池**：限制同时执行任务的线程数量。
- **连接池**：复用有限的数据库 / HTTP 连接。
- **两者不是同一池**，线程充足也可能卡在借连接。
- 线程已经创建的数量，不等于当前正在忙的数量。一次 `jstack` 计数不能单独证明线程池打满。

以平均每秒 50 个请求、平均处理时间 0.2 秒估算，系统内平均在途请求约为 `50 × 0.2 = 10`。若处理时间涨到 5 秒，在途请求约为 250。这个稳态估算有助于理解「变慢会引起积压」，不是精确配置公式。

本课程使用同步 MVC；异步 Servlet、WebFlux、虚拟线程等模型不能简单套用「一个请求始终占一个平台线程」。这些在 [并发专题](./14-single-thread-to-multithread) 按需深入。

## 5. 同步业务与异步业务，不等于有没有 await

普通创建任务：`POST` 返回 `201` 时，任务记录已创建。

大量任务导出：`POST /api/exports` 返回 `202` 和 `exportId`，代表**已经可靠受理，不代表文件已生成**。后台更新 `PENDING → RUNNING → SUCCEEDED / FAILED`，前端通过查询接口获知结果。

前端两种情况都可能写 `await fetch(...)`。`await` 只是等待这次 HTTP 完成，不决定后台业务是否已完成。后台工作若只放内存线程池，进程重启可能丢失；所以先设计持久任务和恢复，再考虑 MQ。

## 6. 身份、请求 ID 和链路上下文

- **身份**来自经过验证的 Session、token 或可信服务身份，不是「读到了 uid 头就可信」。
- **请求 ID**把一次请求的响应与服务端日志关联，单体第一阶段足够实用。
- **traceId / spanId**用于分布式追踪，跨服务传播应遵循组件协议。一个随机 `X-Request-Id` 不等于自动接入追踪系统。
- 安全上下文、MDC 等通常与当前线程有关，切到线程池后不能假设自动传播；用完也要清理，避免复用线程串数据。

如果由网关注入身份头，必须阻止外部绕过网关、删除并覆盖客户端同名头，并验证服务间信任。单体起步直接使用应用内安全框架，反而更容易看清边界。

## 动手：跟踪同一个请求

在 [CRUD 实验](./07-build-a-crud-api) 中：

1. 创建一条正常任务，观察 `201`、`Location` 和 JSON。
2. 发空标题，观察 `400`，确认没有新记录。
3. 查一个不存在的 ID，观察 `404`。
4. 用错误 HTTP 方法，观察 `405`；传不支持的 Content-Type，观察 `415`。
5. 对照 [日志课](./26-reading-logs)，把响应里的 `X-Request-Id` 对应到终端日志。

**预期**：每种错误都能说清楚失败在哪一层，不把所有红色请求都叫「后端挂了」。

## 自测与参考答案

1. JSON 字段类型错了，Service 一定会执行吗？**不会，通常在参数解析或校验阶段就失败。**
2. 返回 504 能证明数据库没有写入吗？**不能，上游是否接收、执行、提交都要进一步核实。**
3. MVC 的全局异常处理能处理后台导出线程异常吗？**不能，后台要自己记录失败状态并进入恢复流程。**
