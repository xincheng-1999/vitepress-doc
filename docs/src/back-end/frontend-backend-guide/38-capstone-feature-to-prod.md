# 综合实战：把任务 API 做成别人能使用的小系统

前面已经能创建、查询、修改和删除任务，也知道怎样看配置、启动容器、查日志。但初始 API 还不能直接交给多个人使用：它没有登录和数据归属，普通 PUT 可能覆盖别人的修改，本机 H2 数据也会随进程退出消失。

这一课围绕一个问题收尾：**怎样把这个起点补成一个能供用户使用、也能由别人接手运行的小任务系统？** 下面是需要你逐项实现和验证的扩展，不是说仓库已经完成了它们。基础代码仍来自 [任务 API](./07-build-a-crud-api)，Java 17、接口路径和既有响应结构继续沿用。

## 1. 先确定这次要交付什么

先不加附件、通知或微服务。第一轮只做：用户能登录和退出，只能看、改、删自己的任务；任务有标题、状态、创建时间和更新版本；数据保存到 MySQL，应用重启后仍在。列表继续分页，并有稳定排序。

除此之外，常见失败也要有明确行为：标题非法、未登录、无权操作、任务不存在、版本过期时，前端分别怎样处理。应用要有测试和请求日志，别人能按说明启动，数据也能从备份恢复。

## 2. 从“只能看自己的任务”开始补登录

先决定用户如何登录。浏览器小系统可以先评估服务器 Session，不因听说 JWT 就默认选择它。具体原理和安全边界见 [安全课](./32-security)。

可以先运行 [Session 登录实验](./32a-session-login-lab)，理解登录、CSRF、退出和任务归属，再把这些做法集成进持久化项目。它是独立工程，不是给初始 API 激活一个 profile 就能得到的功能；演示用户、任务数据和 Session 都在内存中，也不提供可直接上线的 MySQL 安全配置。

集成时，顺序可以这样安排：

1. 在隔离练习环境先把任务 API 接到 MySQL，确认原有 CRUD 仍符合契约。
2. 用版本化迁移加入 users、任务的 `owner_id` 和 `version`，明确旧任务归谁、怎样回填，再设置约束和索引。模型取舍见 [数据模型](./10-sql-and-indexes)。
3. 接入认证，从服务端安全上下文取得用户身份，不接受客户端自报的 uid、ownerId 或角色。
4. Repository 中的读取、更新、删除以及列表总数，都带用户归属条件。响应不返回密码哈希等内部字段，请求 DTO 只接收明确允许编辑的字段。

然后用用户 A 创建一条任务，再用用户 B 查询列表、直接读 ID、修改和删除。B 都不应拿到 A 的数据。伪造 ownerId 或 uid 头也不应改变结果。路由守卫只能控制界面，网关验过 token 也只能确认一部分身份信息，记录归属仍由应用执行。

登录本身也要验证：密码不以明文保存，错误凭据、未登录、过期、退出后的行为明确。Session 方案还要检查 CSRF，以及登录后会话和 token 的变化，不能只看到页面跳转成功。

## 3. 再把这些行为写回接口契约

权限加进去后，前端需要知道哪些响应发生了变化。沿用 [API 设计](./34-api-design) 的成功和错误结构，补齐几项约定：

创建任务仍默认 TODO，归属取登录用户，不让前端指定。重复提交是否允许产生两条，要明确；如果需要重试不重复，设计服务端幂等，而不只禁用按钮。

列表仍用零基页码、有限页大小和稳定排序，items 与 total 都按当前用户过滤。读取、更新或删除别人的任务时，可以返回 403，或统一隐藏为 404，但要事先选择并在各接口保持一致。Session 实验使用后者；删除不可见资源返回 404，与初始示例重复 DELETE 的 204 不同，不能假定两套规则天然一致。

更新除了标题和状态，还需要版本条件；缺失、过期时如何响应，下一节一并实现。退出则明确会话或令牌何时失效，以及旧凭据是否还能使用。

每种行为准备一个正常和失败响应示例，前端就能据此模拟，不必等全部代码写完后再猜字段和状态。安全能力补齐前，初始 API 仍只放在受控本地环境。

## 4. 两个人同时改，怎样避免后提交的覆盖前一个？

普通 PUT 只按任务 ID 写入。A、B 读到同一版本，A 改完后，B 再提交旧内容，就可能把 A 的修改覆盖掉。

现在让客户端提交读到的版本，或使用 ETag 条件请求。数据库更新同时检查任务 ID、owner 和旧版本，成功后增加版本。A 成功之后，B 的条件就不再匹配，应得到约定的 409 或 412，前端提示重新读取或处理冲突，而不是静默覆盖。

测试要真的构造两份旧版本请求，确认只有一次更新成功，再查数据库最终状态。若还要求“修改任务并写审计记录”一起成功，则把两步放在同一事务；故意让审计写入失败，验证任务修改也回滚。见 [事务课](./11-transactions-consistency)。

接着把前面依赖手工操作的情况固定成自动测试：

- 正常 CRUD、分页边界、空白、超长和错类型输入。
- 404、405、415 保持语义，不被全局异常处理全变成 500。
- 登录失败、未登录、过期、退出，以及普通用户调用受限动作。
- A/B 的读写删隔离，包括列表总数和伪造归属字段。
- 旧版本冲突、事务回滚，以及重复请求的约定行为。

基础 H2 测试仍有价值，但不能代替 MySQL 上的验证。还要用隔离 MySQL 检查 SQL、唯一约束、时间往返、锁和回滚，保存实际数据库版本、测试命令和结果。未执行的部分明确标注，测试安排见 [测试课](./35-testing)。

## 5. 让另一台电脑也能按说明运行

当功能和数据行为稳定后，再整理 [Docker 课](./23-docker-in-practice) 的交付方式。请另一位同学从干净的隔离环境按说明操作：准备配置，执行迁移和测试，启动应用，登录后完成一条任务的创建、修改与查询。

说明中要写清数据在哪个卷、哪些变量必须提供、服务监听在哪里、怎样查看日志和安全停止。应用用非 root，数据库使用按实际操作授权的业务账号；迁移权限与日常运行权限分开。密钥通过受控方式提供，不进入 Git、镜像层或公开日志。

本机此前缺少可用的 Compose 插件 / daemon，容器没有实际验证。本轮也未补做，因此不能把文档中的预期结果写成容器已经启动成功。只有在可用环境真正跑过，才能更新这项记录。

如果计划对外服务，还要按实际域名配置 HTTPS、可信代理、CORS 和 CSRF，不用通配设置代替设计。区分进程在运行、应用已就绪和依赖可用；起始源码没有 Actuator，新增健康检查时要明确检查内容、暴露信息和访问权限。

交付的镜像与依赖应固定到已验证版本或摘要，记录构建来源并检查漏洞、维护状态。迁移先在副本验证，再安排发布。还要写明哪些版本能够回滚：应用回滚不会自动撤销不兼容表结构或已经产生的数据。

## 6. 任务留下来了，还能从故障中找回来吗？

先按 Docker 课重启应用、重建容器，查询同一条任务，确认确实使用了持久数据。然后把数据库备份到独立受控位置，在另一套隔离库恢复，核对任务数量、ID、归属、时间和约束。一次备份命令成功，不等于已经验证可恢复。

接下来做少量本地故障对照。错误 Content-Type 应得到 415，带可关联的 requestId，且没有脏数据；数据库暂时不可用时，要看实际失败期限、连接池等待和日志原因，恢复后再查询，不能无限重试。前面的旧版本冲突也重新执行一次，确认两个请求只有一个成功。

只在自己的隔离环境做这些操作，不擅自停止共享测试或生产服务。按 [日志课](./26-reading-logs) 留下这次请求、实际日志、确认的原因、修复和复测结果即可，不需要堆一页错误截图。这样别人遇到相同问题时，才能沿着原来的检查继续做。

## 7. 上面都能解释清楚后，再选一个扩展

先选一个真正需要的功能，不把 Redis、MQ、附件和微服务全加入项目。下面是后续选择，不阻塞前面的小系统完成。

::: details 选项一：大列表导出
先用持久 jobs 表保存导出任务。提交返回 202 和任务 ID，由后台执行程序（worker）分批读数据、保存文件引用，接口能查进度和失败原因。测试重复请求、并发领取、旧 worker、任务过期和文件权限。

量小可以先不用 MQ；确需消息解耦时，再考虑 outbox、消费幂等、重试和告警，见 [消息与任务](./33-mq-reliability)。运行中停止隔离的 worker 后，任务应恢复或明确失败，不能永远卡在 RUNNING，也不能产生重复副作用。用户 A 不能下载 B 的文件。
:::

::: details 选项二：附件上传
小文件可以先流式经过应用写入对象存储，大文件再评估预签名直传和分片；数据库保存元数据与归属。下载先鉴权，短期签名 URL 也不是公开永久链接。

验证超限文件被拒绝、不盲信扩展名或 MIME，未授权用户拿不到下载资格，失败产生的文件可以清理。具体边界见 [附件场景](./39-backend-feature-map#attachments)。
:::

::: details 选项三：允许短暂陈旧的统计缓存
只缓存允许短暂旧数据的统计，key 包含权限维度，并说明 TTL、更新后失效和回源上限。先不要缓存余额或授权结论。

在隔离环境验证 Redis 不可用时的失败期限和数据库压力，缓存删除失败时也有恢复方式。它不能承诺超出设计的一致性，见 [Redis](./12-redis-in-practice)。
:::

## 8. 用 AI 帮忙时，一次只交给它一个明确改动

例如先让它补任务归属，而不是一句“生成生产级系统”：

```text
请沿用现有 Java 17 工程、接口路径和错误结构，先实现任务归属。
先说明身份从哪里取得、哪些查询和写入需要带 owner 条件。
列出当前已实现、需要修改以及仍需我提供的配置，不另造公共模块。
给出正常请求、未登录、A/B 越权和伪造 owner 字段的测试。
说明实际运行过的命令与结果；未运行的明确标注。
并发版本、事务、超时和重试如果尚未处理，列为后续事项，不宣称已完成。
```

检查它给出的代码、测试和实际结果，再继续下一项。组件少不是缺点，做过与没做过的事情分得清，别人才能放心接手。

回看前面几步，如果你能解释一条请求怎样处理，证明用户只能操作自己的数据，确认并发不会静默覆盖，并在隔离环境启动、查错和恢复，就可以按 [学习节奏](./93-learning-path) 决定下一轮深入哪里，不必先补齐所有选修工具。
