# 综合实战：交付一个可靠的小任务系统

> 目标不是「用了最多组件」，而是把任务管理从页面、接口、数据库做到可验证、可运行、可恢复。以下是**分阶段扩展作业**，不把初始 CRUD 声称为已经完整实现的业务系统。

前置：完成 [学习地图](./index) 的 A → E，或按下面检查点补齐。基础代码来自 [任务 API](./07-build-a-crud-api)，网络和单体场景保持一致。

## 1. 需求先缩小到可验收范围

### 第一轮必须交付

- 用户能登录、退出，只能查看和修改自己的任务。
- 任务有标题、状态、创建时间和更新版本；列表分页且排序稳定。
- 输入非法、未登录、无权操作、不存在、版本冲突都有明确响应。
- 数据保存到 MySQL，应用重启不丢；数据库有迁移方案与受控账号。
- 有自动测试、请求关联日志、Docker 本机交付与备份恢复演练。

### 第二轮可选，不要阻塞第一轮

附件、导出、邮件通知、搜索、Redis 缓存、MQ、微服务。先用 [功能地图](./39-backend-feature-map) 判断需求，再选其中一个加入，**不是全部必须上**。

## 2. 阶段一：定契约与失败表

产物是一份可以给前端 mock 的接口表，而不是先让 AI 写几千行代码。

| 用例 | 要明确的行为 | 关键失败 |
| --- | --- | --- |
| 登录 / 退出 | Session 或 JWT 的选择、Cookie / token 策略 | 凭证错、过期、限流、注销后行为 |
| 创建任务 | 身份来自服务端，默认 TODO | 非法标题、未登录、重复提交策略 |
| 查询列表 | 零基页码、最大页大小、稳定顺序 | 不得泄露其他用户任务 |
| 更新任务 | owner + version 条件，更新允许字段 | 404 / 409 或 412 的明确契约 |
| 删除任务 | 幂等删除与资源隐藏策略 | 不得删除他人任务 |

成功结构与错误结构沿用 [API 设计](./34-api-design)。前端禁用按钮不算服务端幂等，路由守卫不算授权。

**过关**：正常与失败响应示例都写完；用户 A 访问用户 B 的资源时采用 403 还是隐藏为 404，团队先达成一致。

## 3. 阶段二：数据迁移与可信身份

按 [数据模型](./10-sql-and-indexes) 扩展 users、owner_id、version：

1. 在练习分支接入 MySQL，同结构迁移先跑通。
2. 用版本化迁移建用户和目标字段，决定旧任务如何归属与回填。
3. 先跑通 [Session 纵切实验](./32a-session-login-lab)，再把其身份与归属思想集成到持久化项目。实验的内存用户并不等于已经做好生产账号；最小浏览器系统可优先评估服务器 Session，不因听说 JWT 就默认选择。
4. 从安全上下文获得用户，Repository 查询显式带 owner 条件。
5. 请求 DTO 不开放 owner、角色、内部版本以外的受控字段；响应不含密码哈希等内部数据。

**过关**：数据库约束有效，密码不是明文；A 的列表没有 B 的任务，伪造 ownerId / uid 头不能越权，注销与过期行为有测试。见 [安全](./32-security)。

不要只在网关做一次认证，就默认所有数据权限问题已经解决。动作权限、租户与记录归属仍由业务边界执行。

## 4. 阶段三：并发与自动测试

第一版 API 的普通 PUT 会静默覆盖。加入版本字段或 ETag：两个客户端读同版本，A 更新成功后，B 的旧版本更新应失败。

必测清单：

- [ ] 正常 CRUD、分页边界、空白 / 超长 / 错类型输入。
- [ ] 404 / 405 / 415 不被全局异常处理改成 500。
- [ ] 未登录、过期、退出、普通用户调用管理动作。
- [ ] A 读取 / 修改 / 删除 B 的记录均被拒绝。
- [ ] 并发旧版本只能成功一次，不凭单次点测判断。
- [ ] 修改任务 + 审计同事务；故意让后一步失败，前一步也不生效。
- [ ] MySQL 上验证 SQL、唯一约束、时间往返、锁和回滚。

**过关**：保存测试命令、数据库版本、结果与故障用例。基础 H2 测试是起点，不是全部项目测试。见 [测试课](./35-testing) 和 [事务课](./11-transactions-consistency)。

## 5. 阶段四：选择一个真实扩展

### 选项 A：大列表导出

先用持久 jobs 表：创建任务返回 202 + ID，worker 分批读数据，保存文件引用，查询进度；有失败状态和恢复。任务过期、并发领取、旧 worker、重复请求与文件权限都要测。

量小可先不引入 MQ。确需消息解耦再实现 outbox、消费幂等、重试与告警。见 [消息与任务](./33-mq-reliability)。

**验收**：导出期间重启 worker，任务能恢复或明确失败，不永远卡 RUNNING；A 不能下载 B 的文件。

### 选项 B：附件上传

小文件先流式经过应用上传对象存储，大文件再评估预签名直传和分片；数据库只存元数据与归属。下载先鉴权，短期签名 URL 不是公开永久链接。

**验收**：超限文件被拒绝，恶意扩展名 / MIME 不被盲信，未授权用户拿不到下载资格，失败文件可清理。见 [附件场景](./39-backend-feature-map#attachments)。

### 选项 C：可过期的统计缓存

只缓存允许短暂陈旧的数据，key 包含权限维度，定义 TTL、失效和回源上限。不要先缓存余额或授权结论。

**验收**：Redis 不可用时故障时限与数据库压力符合设计；删除失败有恢复，承认一致性边界。见 [Redis](./12-redis-in-practice)。

## 6. 阶段五：交付与恢复

按 [Docker 课](./23-docker-in-practice) 在隔离环境运行，**安全扩展完成前不能把初始 API 暴露到公网**。

- 应用使用非 root、数据库用业务最小权限账号；密钥不进 Git、镜像层或公开日志。
- TLS、代理、可信头、CORS / CSRF 按实际前后端域名设计，不用通配设置糊过去。
- 区分「进程运行」「应用就绪」「依赖正常」。当前起始源码没有 Actuator，扩展健康检查时明确暴露内容和权限。
- 固定已验证镜像与依赖版本，构建运行测试，并检查漏洞和升级支持状态。
- 迁移先在副本验证，再按发布流程执行；应用回滚不能撤销不兼容 schema 和已经产生的数据。
- 备份存到独立受控位置，在另一套隔离库恢复并核对，而不是只备份不还原。

**过关**：另一位同学能按 README 从干净环境启动；数据卷、配置、迁移、测试、恢复与已知限制都有说明。

## 7. 最后一次低风险排障演练

只在自己的隔离环境做：

| 演练 | 收集什么 | 修复后验证 |
| --- | --- | --- |
| 请求错误 Content-Type | 状态、请求 ID、访问日志 | 保留 415，未写脏数据 |
| 数据库暂时不可用 | 根因、等待时限、连接池表现 | 恢复后能查询，未无限重试 |
| 两端同时改旧版本 | 两个响应、影响行数 | 一个成功，一个冲突 |
| 停止后台导出 worker | 持久状态、租约与恢复日志 | 恢复或明确失败，没有重复副作用 |

照 [日志课](./26-reading-logs) 写一份「现象 → 证据 → 根因 → 修复 → 回归」记录。不在共享测试 / 生产环境擅自停服务或造故障。

## 8. 使用 AI 时，要求可验证交付

```text
请先输出任务系统这一个用例的契约与失败表，不要先铺微服务。
列出哪些代码已实现，哪些只是示意，哪些需要我提供账号/配置。
实现应沿用已有工程、Java 17、接口路径与错误结构。
说明身份来源、数据归属、事务、约束、超时和重试边界。
给出可运行命令和正常/非法输入/未登录/越权/冲突测试。
不要以“生产可用”替代证据，不要自行发明我仓库中没有的公共模块。
```

你要审查的是测试、约束和失败恢复证据，不是 AI 是否自信地说「全部完成」。

## 自测与毕业标准

1. 没有 Redis 和 MQ 能毕业吗？**能，若需求与容量不需要，少依赖反而更容易交付可靠系统。**
2. Compose 能跑是不是可以上线？**不是，还要安全、配置、数据、备份、监控和发布流程。**
3. 一次备份命令成功等于可恢复吗？**不等于，要实际隔离恢复与核对。**

到这里，你应能解释一条请求、独立完成一个小用例，并能判断失败在哪个边界。再去学 JVM、Kubernetes 与微服务，工具才有位置。返回 [主线地图](./index) 或 [学习节奏](./93-learning-path) 安排下一轮。
