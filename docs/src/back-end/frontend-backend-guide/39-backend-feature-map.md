# 后端功能地图：上传、导出、协作和回调分别怎样做

任务 API 能增删改查以后，需求还会继续增加：“让同事一起处理”“能上传合同”“每天自动出报表”“付款后开通团队版”。这些功能的处理过程不同，不必都拆成微服务，也不是先装齐一组中间件再开始做。

本篇按功能类别介绍：先说需要什么，再从单体应用能完成的做法开始，最后看看最容易出问题的位置。遇到当前不需要的功能，可以跳过，等有相应需求时再回来。

示例背景仍是 Java 17 + Spring Boot 3.x 的 `task-api`，本地 `8080`、入口 `/api/tasks`。初版用 H2，持久化扩展以 MySQL 为主；下面大多数能力是后续设计，**并非初版源码已经全部提供**。Session 登录另有独立实验，不与初版混为同一套功能。

![围绕任务管理需求逐步引入后端能力的功能地图](/backend-guide/features-overview.svg)

## 1. 多人协作：谁能看任务，谁能修改 {#collaboration}

个人待办只需保护“我的任务”。团队版则可能要求成员可查看、负责人可编辑、团队管理员可管理成员，而且 A 公司不能看见 B 公司的数据。先把这些规则写成具体动作，才能决定要存哪些关系。

### 先存成员关系，再决定请求的数据范围

个人版可以在 tasks 保存 owner_id，读写都限定当前认证用户。团队版再增加 team、team_member 和任务所属团队。服务器先验证当前用户确实是目标团队的有效成员，再根据角色与任务关系判断动作。

请求里传来 tenantId 或 ownerId，只能表示用户想操作哪个范围，不能证明他有权访问。更新时可以同时要求任务 ID、已授权团队范围和当前版本匹配，检查影响行数；请求 DTO 也不能随意绑定实体的 role 等内部字段，否则普通成员可能把自己改成管理员。

权限多了以后，可以用 **RBAC** 把一组权限赋给角色。例如 member 可以看任务，manager 可以分配任务；角色通常属于某个团队，而不是全站一个 isAdmin。若规则还取决于任务密级、部门或归档状态，可以加入 **ABAC**，按用户与资源属性判断。两者能配合，但普通 owner 比较没有必要先接通用策略引擎。

服务多个客户组织时，还要做**多租户隔离**。共享表加 tenant_id、按 schema 或数据库隔离，都有不同成本；它讨论的是数据和运行边界，不是再增加一个“租户角色”。单人本地待办不需要这些组织结构，稳定的两种角色也不必先做任意策略表达式。

| 动作 | 可以采用的规则 |
| --- | --- |
| 看任务 | 当前用户是任务所属团队的有效成员 |
| 改任务 | 是负责人，或拥有明确的团队管理权限 |
| 管成员 | 有管理权限，目标成员也在同一团队 |
| 导出 | 有导出权限，而且实际查询的每条记录都在允许范围内 |

### 容易漏掉的，是 SQL 之外的入口

登录只证明是谁。隐藏按钮、UUID 和前端路由守卫，都拦不住直接调用 API。除了查询和更新，缓存 key、搜索结果、附件、后台 job、导出文件、管理端和日志也要沿用相同范围，否则主页面隔离了，导出却泄露了。

成员被移除后，旧会话、令牌里的角色、缓存和已有下载地址还可能短暂可用，要定义撤权生效时间。团队管理员与平台运营也要分开，紧急高权限访问可审计，不让“管理员”默认绕过所有客户隔离。

检查时，用成员 A 查询团队 A，再把路径 ID、tenantId 和导出条件换成团队 B，确认所有入口都不能读写 B 的数据。具体实现见 [安全教程](/back-end/frontend-backend-guide/32-security) 和 [测试](/back-end/frontend-backend-guide/35-testing)。

## 2. 附件：怎样让上传的合同只被有权的人下载 {#attachments}

小图片、合同 PDF 和百兆附件都叫文件，但存储和读取方式可能不同。先确定公开还是私有、允许的类型与大小、谁能下载，以及删除任务后保留多久，不能只在任务表加一列 URL 就结束。

### 小文件可以先由后端接收

单机学习时，可以让小文件经过 `task-api`，写到专用存储目录，数据库另存附件 ID、任务 ID、服务端生成的存储键、大小、类型、上传者和状态。原始文件名只作安全处理后的显示名，不直接拼磁盘路径；存储目录也不作为公开静态目录。

下载时先查当前用户对任务和附件的权限，再返回内容。上传时限制请求体和解压后的体积，检查真实内容，不只相信扩展名和客户端 MIME。需要扫描时，文件先处于待检状态，通过后才能下载；预览也要使用安全策略，大文件不塞进普通业务行。

### 多实例或大文件出现后，再把字节交给对象存储

本地文件跟着某台机器走，多实例共享或容器重建时就不方便。OSS、S3 一类对象存储按 key 保存文件，能独立扩容和管理生命周期。应用仍保存附件元数据和权限，不把对象存储的地址本身当成授权。

大文件可以多段上传，失败只补传部分。网络分发成为瓶颈时再考虑 CDN，它缓存并分发内容，不是对象存储本身。一个本地演示、几张小图不需要先接 CDN 或分片，但权限和大小限制始终要有。

![私有附件通过授权后获得短期签名上传地址，完成后验证再成为可下载附件](/backend-guide/features-file-upload.svg)

直传时，后端可以签发一份短时访问能力，让浏览器上传到指定私有对象，而不暴露永久 AccessKey。一次完整过程应是：

1. 客户端请求 `POST /api/tasks/{taskId}/attachments/upload-intents`。
2. 后端检查用户能否编辑任务、文件类型和配额，创建 UPLOADING 元数据，只允许上传指定对象和动作。
3. 浏览器向私有对象存储上传字节；分片场景还要管理 uploadId 归属、数量与大小限制。
4. 客户端报告完成。后端检查对象存在、大小和摘要等约束，并对**确定的对象版本**扫描。通过后，要么绑定该不可变版本，要么由服务端把**这份已验证的内容**复制到客户端没有写权限的 final key，然后才标记 READY；不能扫描一个版本，复制时却重新读取可被覆盖的最新内容。
5. 下载时重新检查权限，读取绑定的已验证版本或 final key，再代理返回或签发短时下载地址，不读取“这个 key 当前最新的内容”。

第四步不能省略。预签名 PUT 往往能在有效期内重复使用、覆盖同 key。若只是扫描后改个 READY 标志，用户可能先传安全文件、通过扫描后再覆盖成恶意文件。**扫描、READY 记录和下载必须指向同一份不可变内容**；缩短有效期或只保存一个摘要，都不能代替这个绑定。应测试 READY 之后复用旧上传能力，也无法改变已允许下载的内容。

### 还要处理上传了一半和删除了一半

对象字节与数据库不在同一本地事务里。上传成功、元数据提交失败会留下孤儿；删除任务和删除文件也可能只有一边成功。用中间状态、重试和定期对账清理，未完成分片也要过期回收，避免一直计费。

签名 URL 通常是有效期内“持有就能用”的凭据，不进日志、Referer 或随手分享。它可能无法单独撤销，退出登录或撤销角色也未必立即让旧地址失效。CDN 还可能继续缓存源站已删内容，所以私有文件要定义缓存和撤销时限，不把私有桶改成公开读来省鉴权。

浏览器直传涉及对象存储自己的 CORS，但放行跨源不代表有业务权限。用户要求服务器从任意 URL 转存时，还要防 SSRF，避免访问内网和云元数据服务；压缩文件也要限制解压资源。

检查时试一次未登录取上传能力、跨用户下载、伪造完成报告、中断分片，以及 READY 后覆盖原上传 key。它们应分别被拒绝或按策略恢复。更多见 [安全](/back-end/frontend-backend-guide/32-security)、[配置](/back-end/frontend-backend-guide/25-config-and-env) 和 [网络](/back-end/frontend-backend-guide/22-networking-for-backend)。

## 3. 导入、导出和调度：很多行数据怎样分批处理 {#batch-jobs}

导入一万行 CSV 时，用户不只关心最后多了多少任务，还要知道哪些行错了、能不能续跑。每天生成报表，则要确定“昨天”按哪个时区、数据取哪个时间点、文件谁能下载。这些约定先于循环代码。

### 先确定整份成功，还是允许部分成功

小文件可以限制体积、列和行数，在请求预算内校验并同步写入。大文件耗时较长，就先保存文件和 background_job，返回 `202 + jobId`，由同一单体中的有界 worker 分批读取、验证、写入，并持久保存进度和失败摘要。

如果允许部分成功，批次事务可以缩小锁与回滚范围，还需要行级结果和续跑标识。例如 `(import_job_id, row_number)` 唯一，防止重启后再次插入同一行。一万行里 50 行不合法，最终就明确报告“9950 成功 / 50 失败”，不含糊地给一个成功提示。

如果要求全有或全无，可以先写暂存区，验证完成后统一发布。这会增加存储和流程，但比默认套一个巨大事务更能控制成本。批处理只是成批执行，并不天然要求整份文件处于同一个事务。

导出也按体量选择：小数据同步生成，大数据后台分页或游标读取，写出结果文件后提供鉴权下载和过期时间。读取期间数据可能变化，要告诉用户拿到的是近似结果还是一致快照；严格快照可能需要更长事务、业务版本或离线数据集，存在额外成本。

### 需要每天自动生成时，再加调度

先从手工触发 job 开始。确有每天自动报表的需求，可以用 Spring `@Scheduled` 等触发器，同时保存执行记录。之后要求停机补跑，再增加调度元数据和漏跑策略；多个实例需要协调领取或分片时，才考虑分布式调度及运维平台。

cron 表达的是时间规则。Spring 常见六字段 `0 0 2 * * *` 表示每天 02:00；传统 Unix 常见五字段写法是 `0 2 * * *`。字段数、周与日语义、时区支持随工具不同，不能照抄。显式指定 `Asia/Shanghai` 等时区，还要定义夏令时、跨日、节假日和漏跑处理。

以 `(tenant_id, report_type, business_date)` 等业务键保证同一日报表只有一份逻辑结果。多个节点或补跑重复触发时，也不会额外生成同一业务结果。延迟消息只让一条消息未来可见，不能替代周期规则、执行历史与补跑管理。

每月手工导入一次小文件，没有必要接 MQ 或调度平台。非关键的单实例清理可以从简单定时开始；一旦承诺“不漏跑、可恢复”，就需要持久记录，而不是只加一个分布式锁。

### 容易出的问题在恢复和资源消耗

只把任务放进 `@Async`，重启会丢掉已受理工作。job 领取、租约过期和重复执行如何处理，见 [消息任务可靠性](/back-end/frontend-backend-guide/33-mq-reliability)。测试时停止 worker 后重启、重放同一个 job，业务记录都不应重复。

解析不能把巨大 CSV 或 Excel 一次全读入堆。限制解析资源、分批读取、控制 worker 并发，防内存耗尽、压缩炸弹和长事务。进度到 99% 后，写文件仍可能失败，所以终态需要可解释和可恢复，不永远卡在 99%。

导出的不可信文本还可能被表格软件当成公式执行。按目标工具设计安全文本策略，处理 `= + - @` 等触发风险并做兼容测试；CSV 加引号只处理分隔格式，不能解决公式注入。

## 4. 支付回调和 Webhook：怎样相信“已经付款” {#webhooks}

团队版开始收费后，浏览器跳回“支付成功”页，只能作为界面提示。真正给团队发权益，要依据支付平台的可信结果。通知可能延迟、重复或乱序，也可能扣款成功却没及时通知，所以不能只处理顺利到达的一次回调。

Webhook 指一个服务器在事件发生后，主动向另一个服务器的 HTTP 地址推送通知。支付是其中高风险的一类，仓库更新、物流和日历也有类似通知。没有这些外部事件的任务工具，不需要先加支付模块；同进程内能直接完成的调用，也不用包装成 Webhook。

### 先用沙箱完成一次可信状态更新

服务端按受控商品和价格创建本地订单，记录商户单号、金额、币种、租户和待支付状态。不接受前端把最终金额改成一个任意数，也不因 `paid=true` 就开通权益。

发起支付和验签按平台官方 SDK 或协议完成。回调到达时，读取平台要求的原始请求字节或规范化内容，使用可信密钥、证书验签，再检查商户、订单、金额、币种和事件类型。签名算法、证书轮换和响应格式都按平台要求，不自己拼 SHA256 字符串冒充验签；来源 IP 白名单可以辅助，不能代替验签。

校验通过后，在本地事务中记录事件、条件更新订单、创建权益或权益待处理事件。可靠落库后才按平台协议确认。如果想快速响应，可以先持久保存事件再由后台处理，不能先返回成功、只把工作留在内存里。

### 签名正确，也要处理合法重复通知

签名证明内容符合可信密钥的签名结果，不能单独说明它是新消息。时间戳和 nonce 等新鲜度检查要遵循平台协议，同时容纳合法延迟和重试，不能任意拒绝所有旧通知。

用平台 eventId 去重，再对订单发权益的业务效果施加唯一约束。这样即使两个不同通知 ID 指向同一笔支付，也不会发两次。状态更新还要防止旧 PENDING 覆盖 PAID；退款需要独立记录与权益规则，不是简单把所有状态改回未支付。

几个检查各自负责不同位置，可以查表区分：

| 检查 | 作用 |
| --- | --- |
| TLS | 保护传输并验证连接对端，不替每个公开入口请求证明业务身份 |
| 签名或 MAC | 检测篡改、验证可信签名结果 |
| 时间戳、nonce | 按协议限制恶意重放 |
| eventId、商户单号唯一约束和状态规则 | 合法重复或乱序通知不重复发权益 |
| 查单与对账 | 回调缺失、超时未知或账实不符时恢复事实 |

### 回调缺了，要能主动找回结果

本地处理失败，允许平台重试；一直没收到或结果未知，就按业务单号查单、定期对账，并保留人工恢复入口。不能把对账当作跳过验签和金额检查的理由。

验签常依赖精确字节，先反序列化再序列化可能改变内容，框架读 body 后也要让 SDK 取得正确原文。即使签名合法，金额不符、错误商户、未知事件或已关闭订单仍应隔离并告警。沙箱或模拟验签不能带进生产。

对外发送 Webhook 时也要签名、有限重试并记录投递；客户填写回调 URL 时防 SSRF，不允许访问内部敏感地址。

在沙箱重复投递三次，只应发一次权益；改一个字节应验签失败；正确签名但金额不符也不生效；扣款成功却没回调，应能查单恢复。处理事务和重复效果的细节见 [消息任务可靠性](/back-end/frontend-backend-guide/33-mq-reliability)，密钥与身份见 [安全](/back-end/frontend-backend-guide/32-security)。

## 按需补充：其他功能从哪里开始

### 搜索：用户想按关键词找到任务

按状态、日期和标题做简单筛选，先用 MySQL 条件查询、合适索引与受限分页，注意 `%keyword%` 的成本，必要时评估数据库全文检索。

真正需要分词、相关性、高亮和错别字容忍时，再考虑 Elasticsearch 等搜索引擎。倒排索引按“词项对应哪些文档”组织，适合全文搜索；SQL 常用 B-tree 更擅长有序值查找，但 SQL 数据库也能提供全文索引，不是完全不能搜索。小数据量或精确、前缀查询已够时，不额外维护搜索集群。

搜索索引通常是数据库的异步副本，要能重建和对账。租户、权限和软删除都必须过滤，必要时对命中结果做权威校验；已删内容还可能出现在旧高亮摘要里。先看 [SQL 与索引](/back-end/frontend-backend-guide/10-sql-and-indexes)，再用 [事务与一致性](/back-end/frontend-backend-guide/11-transactions-consistency) 理解双写问题，不把所有 LIKE 换成 ES 当作优化完成。

### 工作流：不是谁传什么 status，就改成什么

任务增加审核、退回、转交和会签后，要先列明状态与允许动作，用条件更新、版本检查执行转换，非法转换按约定返回冲突。

状态机用于表达状态、事件和转换条件；跨多人、多步骤、需要流程版本和人工等待时，再评估工作流引擎。三种稳定状态往往在 Service 集中管理规则就够，不必接 BPMN 平台。

并发审批、重复动作、超时取消和旧流程版本都要处理。流程撤回后，已经发出的邮件或支付也不会自动回滚，需要业务补偿规则。

### 软删除、审计和脱敏：三个独立需求

误删想恢复，可以加 deleted_at 并统一默认过滤；想知道谁改过数据，记录操作者、动作、对象、时间和受控摘要；客服不应看到完整手机号，则在响应和日志中按字段与角色脱敏。

它们可以分别引入，不必为了普通 CRUD 保存所有敏感快照或上事件溯源。不需要恢复的数据，也可以按规则硬删除。

软删仍占存储，不等于完成隐私删除义务；唯一索引、关联查询、搜索和导出都要考虑已删数据。普通日志也不自动成为不可篡改审计，脱敏更不等于加密或匿名化，原始数据仍需访问控制和保留期限。

### 通知：先有可查询的站内信，再选择触达渠道

任务分配后需要提醒负责人，可以先保存通知记录，按用户管理未读和已读。需要触达离线用户，再接邮件、短信，增加模板、偏好、限频、退订和失败回执；在线及时展示再考虑 SSE 或 WebSocket。

刷新列表已经够用的工具，不必先接实时连接；没有重要时效需求，也不用先发收费短信。WebSocket 断开后，站内信事实仍要能查到。

MQ 确认不表示用户收到，供应商受理也不等于送达。重复投递可能骚扰用户或增加费用，所以业务去重、费用限额、内容净化和隐私控制仍由应用负责。

### 字典、配置和功能开关：先看谁修改、什么时候生效

稳定状态码可以用枚举；用户可维护的业务选项用字典表；不同环境的地址用运行配置；新提醒只对少量团队开放，则用服务端功能开关，也叫 Feature Flag。

需要多环境动态分发时再考虑配置中心，需要按团队灰度、紧急关闭时再完善开关管理。三个固定优先级不必做万能字典平台，单体少量配置也不必先接中心服务。

字典 code 保持稳定，展示名变化不改历史含义。密钥不混进普通可读配置。开关只决定是否开放，权限仍决定谁能操作什么，前端关按钮不等于后端禁用。服务端判定要稳定、可审计，定义配置源故障时的默认值，并清理旧开关；关闭功能也不会撤销已经发生的副作用。

## 把一个需求从头想完

可以选“团队管理员每天 08:00 获得昨天完成任务的报表”练习，不写代码，先把处理顺序说明白：服务器确认团队管理员，按明确时区确定“昨天”的半开区间，再创建该团队、报表类型和业务日期唯一的持久 job；worker 有界读取并生成私有文件，完成后才允许授权下载，文件到期清理。

然后补两个失败场景：生成途中重启，仍接着同一 job 做；另一个团队猜到 jobId 或结果地址，也不能下载。观察最老任务等待年龄，用 jobId 找到日志，失败要可查询。这份小方案已经能让前后端讨论状态、等待和错误，而不是只剩一串组件名称。选做实现见 [33 章练习](/back-end/frontend-backend-guide/33-mq-reliability#failure-exercises)。
