# 39. 后端功能地图：同事说的这些能力，到底在解决什么需求

## 学习目标

读完本章，你应该能：

- 把“上 RBAC、接 OSS、做异步导出”等说法还原成具体用户需求。
- 给出单体应用的最小方案，解释为什么要升级、什么时候不用升级。
- 识别权限、文件、批处理、支付回调四类功能最容易遗漏的失败边界。
- 给需求评审补上数据范围、重复请求、失败恢复、可观测与验收标准，而不是只列中间件名。

## 39.1 先有产品需求，再有技术名词

我们仍维护 **Java 17 + Spring Boot 3.x 的单体 `task-api`**：本地端口 `8080`，任务入口 `/api/tasks`。本地第一课用 H2 降低启动门槛，业务持久化主线用 MySQL。先把新增、查询、修改、删除跑通，再按真实需求加能力。一个应用里可以有很多模块；拥有“通知模块”不意味着必须有“通知微服务”。

![围绕任务管理需求逐步引入后端能力的功能地图](/backend-guide/features-overview.svg)

下面按四个真实场景深入，其余常见词给出选择边界，不把每一种选修能力都变成源码课。建议的提问顺序固定为：**需求 → 最小实现 → 为什么引入更复杂方案 → 什么时候不需要 → 失败边界**。

| 产品同事的说法 | 后端评审需要追问 | 常见术语 |
| --- | --- | --- |
| “同事可以一起处理任务” | 哪个人能看哪个任务、能做什么、属于哪个组织？ | 认证、授权、RBAC、ABAC、多租户 |
| “任务能传附件、大文件能续传” | 文件谁能读、大小多少、上传失败怎么算、多久清理？ | 对象存储、CDN、分片、签名 URL |
| “一次导入一万条，每天自动发报表” | 接受部分成功吗、能否重复、什么时候跑、漏跑怎么办？ | 批处理、异步任务、cron、分布式调度 |
| “付费开通团队版，收到通知自动生效” | 谁证明付钱、通知能否重复、金额不符怎么办？ | 支付回调、Webhook、签名、防重放、幂等 |

## 场景一：任务开始多人协作——认证、授权与租户 {#collaboration}

### 需求：不再只是“我的任务”

产品从个人待办扩展为团队协作：成员能看团队任务，负责人能编辑，团队管理员能管理成员；A 公司不能看到 B 公司的任务。这里其实有四个不同问题：

1. **认证**：请求者是谁？用登录会话或访问令牌建立可信身份。
2. **授权**：允许谁执行“编辑、分配、归档”等动作？
3. **资源范围**：允许操作的是哪个团队/用户的数据集合？
4. **租户隔离**：同一套产品服务多个客户组织时，如何阻止跨组织访问？

### 最小实现：先把数据范围落实

个人版先有 `tasks.owner_id`，读写都加当前登录用户范围。团队版再引入 `team`、`team_member`、任务所属团队，以及集中管理的权限判断。不要直接接受请求体中的 `ownerId` 或 `tenantId` 并据此放行；用户即使能够切换团队，也必须先验证其在目标团队中的有效成员身份。

| 动作 | 最小规则 | 需要的证据 |
| --- | --- | --- |
| 看任务 | 是任务所属团队的有效成员 | 已验证身份 + 服务端查到的成员关系 |
| 改任务 | 是负责人，或有明确的团队管理权限 | 任务归属 + 角色/负责人规则 |
| 管成员 | 有管理权限，且目标成员在同一团队 | 授权规则 + 同租户目标范围 |
| 导出 | 有导出权限，且每条记录都在授权范围内 | 不仅检查“能点导出”，还约束实际查询 |

更新可采用“任务 ID + 已授权团队范围 + 版本”的条件更新，处理影响行数为零的情形。普通成员不能通过修改 JSON 把自己变成管理员；请求 DTO 不应无差别绑定实体的所有字段。

### 为何引入 RBAC、ABAC、多租户

- **RBAC（基于角色的访问控制）**：角色对应一组权限，例如 `member` 可读任务，`manager` 可分配任务。当用户多、权限组合相对稳定时，比每人单独配置更容易管理。角色通常有团队/租户范围，不是全站一个 `isAdmin`。
- **ABAC（基于属性的访问控制）**：根据用户、资源、环境等属性判断，例如“同部门且密级允许且任务未归档才可编辑”。规则动态细腻时有价值，但规则冲突、解释与测试成本更高。
- **多租户（Multi-tenancy）**：多个客户组织共用系统。可以共享表并加 `tenant_id`，也可按 schema/库等隔离，强度与成本不同。它是数据和运行隔离设计，不是一个角色名。

RBAC 与 ABAC 可以结合：角色先决定动作范围，任务归属、状态等属性再缩小可访问资源。不必为每一个普通 `owner_id == currentUserId` 判断都先采购策略引擎。

### 何时不需要

只有单人使用的本地待办，不必引入租户、组织层级与通用权限后台。只有“用户/管理员”两种稳定权限的初期产品，也不必一上来支持任意策略表达式。先明确规则、集中实现并测试，等变化证据出现再抽象。

### 失败边界与验收

- 登录成功不是数据授权；UUID、隐藏菜单、前端路由守卫都不能阻止直接调用 API。
- 隔离不止 SQL：缓存键、搜索条件、对象存储路径/元数据、异步 job、导出文件、日志与管理端也可能跨租户泄露。
- 撤销成员权限后，旧会话、旧 token 中的角色、缓存和已签出的下载 URL 可能暂时仍有效；需定义撤权生效时限。
- 管理员规则要区分团队管理员与平台运营；紧急高权限操作要可审计，不能“管理员默认绕过所有隔离”。

**验收例**：成员 A 能查团队 A 的任务；把路径 ID、请求 `tenantId`、导出筛选换成团队 B，仍不能读写 B 的数据。详见 [安全教程](/back-end/frontend-backend-guide/32-security) 与 [测试](/back-end/frontend-backend-guide/35-testing)。

## 场景二：任务附带图片和合同——文件不是一列 URL {#attachments}

### 需求：上传、下载、预览，也要有权限

第一版允许每个任务上传一张小图片；后来需要合同 PDF、百兆附件、跨地区下载。要先问清：文件是公开还是私有？是否包含个人信息？允许多大、哪些类型？删除任务后附件是否保留？

### 最小实现：后端受控上传，元数据与文件分开

学习阶段可以把小文件传给 `task-api`，保存到配置的独立存储目录，数据库保存附件 ID、任务 ID、生成的存储键、大小、类型、上传者与状态。不要把原始文件名直接拼成磁盘路径，不把存储目录当公开静态目录，不把大型文件直接塞进普通业务行。

下载先校验任务/附件归属，再受控返回内容。原始文件名仅作安全处理后的显示名；服务端生成随机存储键；限制请求与解压后的体积，验证实际内容，不只信扩展名或客户端 MIME。可能需要恶意文件扫描、隔离待检状态和安全预览策略；未扫描通过的文件不公开。

![私有附件通过授权后获得短期签名上传地址，完成后验证再成为可下载附件](/backend-guide/features-file-upload.svg)

### 为何引入对象存储、CDN、分片与签名 URL

| 能力 | 它真正增加什么 | 仍需应用负责什么 |
| --- | --- | --- |
| 对象存储 OSS / S3 类服务 | 按对象键保存文件，独立扩容、生命周期管理，多实例无需共享本地目录 | 元数据、权限、命名、访问策略、删除与业务状态协调 |
| CDN | 将可缓存内容分发到更近的节点，减少源站压力 | 缓存键、失效策略、私有访问、过期内容治理；它不是对象存储本身 |
| 分片/多段上传 | 大文件分块发送，失败只补传部分，适合断线续传 | uploadId 归属、分片限制、完成校验、取消与过期分片清理 |
| 签名 URL | 对某个对象、动作、有效窗口授予受限访问能力，可由客户端直传/直下 | 先做业务授权，限制对象和方法，短有效期，防泄露与滥用 |

直传的一次典型交互：

1. 客户端请求 `POST /api/tasks/{taskId}/attachments/upload-intents`。
2. `task-api` 校验当前用户可编辑任务、类型和配额，创建 `UPLOADING` 元数据，生成只允许该对象操作的短期签名能力。
3. 浏览器把字节传到私有对象存储，不拿永久 AccessKey。
4. 客户端报告完成；后端不能只相信这个报告，而应检查对象是否真实存在、大小/摘要/状态是否符合约束，再扫描**一个确定的对象版本**。通过后将元数据绑定到不可变 version / 摘要；或由服务端把已验证内容复制到客户端无写权限的最终 key，才标记 `READY`。
5. 下载时再次验证当前权限，只返回绑定的已验证版本 / 最终对象，再代理下载或签发短时下载地址。不能下载「同一个 key 目前恰好指向的最新内容」。

### 何时不需要

一个本地演示、几张小图，不需要 CDN 和分片上传。没有明显网络或流量问题，不为“专业”引入多级缓存。部署到多实例、容器重建会丢本地目录、文件量明显增长时，对象存储的价值才更明确；但即使小文件，也不能省略权限与大小限制。

### 失败边界与验收

- **数据库事务管不到对象存储**：字节上传成功但元数据提交失败会留下孤儿；任务删除与文件删除也可能一边成功。用中间状态、重试和定期对账清理，而非宣称“一起回滚”。
- **预签名 PUT 往往可在有效期内复用并覆盖同 key**：只缩短有效期不能消除“先传安全文件通过扫描、再覆盖成恶意文件”的窗口。扫描和下载必须绑定不可变版本，或转存到客户端不能改的最终 key；验收 READY 后复用旧上传能力也不能改变可下载内容。
- 签名 URL 通常是“持有即可使用”的受限凭据。写日志、放 Referer 或分享出去都可能泄露；在过期前未必能单独撤销，角色撤销也未必立即阻止旧地址。
- CDN 可能继续缓存源站已删内容，尤其要定义私有数据的缓存和撤销时限。不能把私有桶配成公开读来绕过下载鉴权。
- 用户提供任意 URL 让服务端“转存”会产生 SSRF 风险，不能随便访问内网地址或云元数据服务。
- 浏览器直传涉及对象存储自己的 CORS，不等于业务授权。大文件还有超时、重复 complete、未完成分片计费和压缩炸弹问题。

**验收例**：未登录拿不到上传能力；其他用户不能获得附件的下载能力；伪造“上传完成”不会产生 READY 文件；中断上传后能按策略清理残片。配合 [安全](/back-end/frontend-backend-guide/32-security)、[配置](/back-end/frontend-backend-guide/25-config-and-env) 和 [网络](/back-end/frontend-backend-guide/22-networking-for-backend) 学习。

## 场景三：一万行任务导入与每天自动导出——批处理和调度 {#batch-jobs}

### 需求：不是“循环调用一万次新增”就结束

用户要导入一万行 CSV，查看进度与错误行；每天早上下载昨天已完成任务的报表。先定义：整份文件要么全成功，还是允许部分成功？重复上传同一文件算新导入还是续跑？导出包含哪个时间点的数据？报表谁能下载、保留多久？

### 最小实现：小批同步，大批持久化

- 小文件先严格限制行数、列和体积，校验后在可控时间内同步完成。不要把“初始只有 20 行”写成永远无限量。
- 耗时超过请求预算时，保存导入文件和 `background_job`，返回 `202 + jobId`；同一单体的有界 worker 分批读取、验证、写入，持久化进度与失败摘要。
- 批次事务缩小锁与回滚范围。若选择“部分成功”，应有明确的行级结果与续跑键，例如 `(import_job_id, row_number)` 唯一，不能回放一次就重复创建全部任务。
- 导出小数据同步生成；大数据在后台分页/游标读取，生成文件并保存结果位置，下载仍鉴权，给出过期时间。

业务一致性要说清楚：批处理（Batch Processing）是对一组数据分批执行操作的方式，不等于整份文件必然只有一个巨大的事务。需要跨批次全有或全无时，可以先写暂存区、完成验证后发布，代价是额外存储与流程；不是简单把全部代码套进 `@Transactional` 就无成本获得。

### 为何引入调度与分布式调度

| 阶段 | 能力 | 引入理由 |
| --- | --- | --- |
| 手工点导出 | 普通同步或后台 job | 偶尔使用，没有时间规则 |
| 单实例定时 | Spring `@Scheduled` 等触发器 + 持久执行记录 | 明确需要每天自动生成 |
| 可恢复的调度 | 调度元数据、漏跑策略、幂等业务键 | 重启期间错过执行、需要补跑与历史追踪 |
| 分布式调度 | 协调认领、分片、故障转移、运维控制台 | 多实例重复触发、任务多或确需分摊执行 |

`cron` 是时间规则表达方式，不是可靠执行保证。例如 Spring 常见六字段 cron `0 0 2 * * *` 表示每天 02:00；传统 Unix cron 通常五字段，类似 `0 2 * * *`。字段数、周/日语义、时区支持依工具而异，不能直接互抄。应显式设置时区，例如 `Asia/Shanghai`，并定义夏令时、停机漏跑、节假日与跨日边界。

每天报表可以以 `(tenant_id, report_type, business_date)` 为唯一业务键，触发重复也不生成第二份逻辑报表。**延迟消息不是定时调度**：它通常是让某一条消息在未来可见，不能替代周期规则、漏跑补跑、并发控制和运行历史。

### 何时不需要

每月只有一次手工小导入，不需要 MQ、调度平台或复杂作业编排。只有一个实例、非关键的清理任务，可以从简单定时触发开始；一旦要求“不漏跑、可补偿”，再增加持久执行记录，而不是先上分布式锁就宣称可靠。

### 失败边界与验收

- 重启不能丢受理的 job；只启动 `@Async` 不存任务，无法满足这个要求。认领、租约过期与重复执行见 [消息任务可靠性](/back-end/frontend-backend-guide/33-mq-reliability)。
- 不能一次把巨型 CSV/Excel 全读进堆；限制解析资源、分页读取、约束并发，防 OOM、压缩炸弹与数据库长事务。
- CSV 导出是数据但也可能被表格软件当公式执行。对于不可信文本，按目标消费工具采用安全的文本策略，处理 `= + - @` 等公式触发风险并做兼容测试；只加 CSV 引号不等于防公式注入。
- 分页导出时数据仍在变化，需要说明是“读取期间近似结果”还是一致快照；严格快照可能需要更长事务、业务版本或离线数据集，存在额外成本。
- 进度不是安全承诺：99% 后可能在文件写出阶段失败；失败状态应可解释、可重试，不永远卡住。

**验收例**：一万行中 50 行非法，结果明确为“9950 成功 / 50 失败”（若选择部分成功）；重启并重放同一 job 不重复插入；调度重复触发同一业务日期仍只对应一份逻辑报表。

## 场景四：团队付费开通——支付回调与 Webhook {#webhooks}

### 需求：用户说“支付成功”不能直接给权益

`task-api` 后来提供团队版。浏览器跳回“支付成功”页面只是 UI 信号，不是可信支付事实。支付平台可能向后端发通知，通知可能延迟、重复、乱序，平台也可能成功扣款却未及时通知。

**Webhook** 是服务端在某个事件发生后主动向另一个服务的 HTTP 地址推送通知的方式。支付回调是一类高风险 Webhook；普通仓库更新、物流、日历通知也会用它。

### 最小实现：先接沙箱，不自己实现支付协议

1. 服务端按受控商品与价格建立本地订单，记录商户单号、金额、币种、租户及待支付状态；不能信任前端提交的最终金额。
2. 使用支付平台官方 SDK/协议发起支付。浏览器查本地订单状态，不因前端传 `paid=true` 就发权益。
3. 回调入口按官方要求读取**原始请求字节或规定的规范化内容**，使用受信任平台密钥/证书验证签名；校验商户身份、订单号、金额、币种和事件类型。
4. 在本地事务中记录事件、条件更新订单、创建权益或权益待处理事件。只有可靠落库后才按平台协议确认收到。
5. 未处理成功允许平台重试；回调缺失或结果未知通过查单和定期对账恢复，保留人工处理入口。

签名算法、证书轮换和回调响应格式照平台要求使用 SDK，不自己“用 SHA256 拼一个串”冒充验签。也不要因为“来源 IP 看起来对”就跳过验签；IP 白名单可以是附加防线，不是通用身份协议。

### 为何引入签名、防重放与幂等

| 控制 | 防什么 | 不防什么 |
| --- | --- | --- |
| TLS | 传输中的窃听和篡改，验证连接对端 | 不证明任意到达公开回调地址的请求都来自平台 |
| 消息签名 / MAC | 证明内容符合可信密钥的签名结果、检测修改 | 本身不保证消息新鲜；一份旧的合法消息仍可能被重发 |
| 时间戳 / nonce 等协议机制 | 限制可接受的新鲜度窗口，按提供方协议防恶意重放 | 不能替代处理合法重复通知的业务幂等 |
| eventId / 商户单号唯一约束 + 状态机 | 同一事件或同一订单的重复通知不重复发权益 | 不自动验证订单金额或识别伪造来源 |
| 查单 / 对账 | 回调丢失、超时未知、账实不一致时恢复事实 | 不应成为允许跳过回调校验的借口 |

合法平台也会重试旧事件；时间窗口和重放策略必须遵循提供方协议，不能拍脑袋拒绝全部延迟通知。用平台事件 ID 去重，同时对“订单已付款”到“发放权益”的业务效果施加唯一约束，防止不同通知 ID 指向同一笔支付时重复执行。

### 何时不需要

没有资金、权益或外部系统通知的任务工具，不需要支付模块。早期只需演示流程时使用沙箱或模拟事件，不能把模拟验签、硬编码商户身份带进生产。普通内部事件如果同进程可直接调用，也不必包装成 HTTP Webhook。

### 失败边界与验收

- 验签常依赖精确字节顺序。先反序列化再重新序列化，可能改变内容导致验签错误；框架读取 body 后还要保证 SDK 能取得所需原始内容。
- **先返回成功再异步放进内存**会让平台不再重试，但本地可能没处理。若要快响应，应先可靠保存事件，后续按持久 job/outbox 处理。
- 相同事件重复来要能安全确认；订单状态乱序到达不能从 `PAID` 被旧 `PENDING` 覆盖。退款不是简单把所有状态设回“未支付”，需独立记录与权益规则。
- 回调签名通过不代表业务有效；金额不符、错误商户、已关闭订单、未知事件类型都应隔离处理并告警。
- 对外发送 Webhook 时同样要签名、有限重试、记录投递；客户填写回调 URL 时还需防 SSRF，不允许访问内部敏感地址。

**验收例**：沙箱事件投递三次只发一次权益；改一个字节验签失败；正确签名但金额不符不生效；支付成功但回调缺失可通过查单恢复。幂等和 outbox 细节见 [消息任务可靠性](/back-end/frontend-backend-guide/33-mq-reliability)，身份与密钥边界见 [安全](/back-end/frontend-backend-guide/32-security)。

## 39.2 其它常见需求：知道用途，别急着把组件全装上

下面每一行仍沿用“需求 → 最小实现 → 引入理由 → 不需要的条件 → 失败边界”。

### 搜索：先问 SQL 为什么不够

| 步骤 | 选择 |
| --- | --- |
| 现实需求 | 按任务标题关键词、状态、日期查找，后来希望全文分词、相关性、高亮、错别字容忍 |
| 最小实现 | MySQL 条件过滤、合适索引与受限分页；明确 `%keyword%` 的成本，必要时评估数据库全文检索 |
| 为什么引入 ES | Elasticsearch 等搜索引擎的倒排索引组织“词项 → 命中文档”，适合全文检索与相关性排序；SQL 常用 B-tree 索引更擅长有序值查找，但 SQL 数据库也能提供全文索引，不是“SQL 不能搜索” |
| 何时不需要 | 小数据量、精确查询/前缀查询足够、数据库性能可接受时，不必多维护一套索引集群 |
| 失败边界 | 数据库通常仍是事实源，搜索索引是异步投影：可能延迟、漏同步，要能重建和对账；租户、权限、软删除必须正确过滤，必要时对命中结果再做权威校验；删除后的索引和高亮摘要也可能泄露内容 |

不要把所有 `LIKE` 换成 ES 就宣称性能解决；先看 [SQL 与索引](/back-end/frontend-backend-guide/10-sql-and-indexes)，再读 [事务与一致性](/back-end/frontend-backend-guide/11-transactions-consistency) 理解双写。

### 工作流与状态机：业务规则，不是只加一个 status 字段

| 步骤 | 选择 |
| --- | --- |
| 现实需求 | 任务要 `TODO → DOING → DONE`，后来增加审核、退回、转交、会签 |
| 最小实现 | 明确状态与允许动作，用条件更新和版本控制执行转换；非法转换返回冲突，不直接接受任意 status |
| 为什么引入 | 状态机帮助表达状态、事件、守卫条件；跨多人、多步骤、需要流程版本和人工等待时，工作流引擎可减少自建编排 |
| 何时不需要 | 三种稳定状态不必引入 BPMN 引擎；把转移规则集中到 Service 已足够 |
| 失败边界 | 并发审批、重复动作、超时取消、旧流程版本、撤回后的外部副作用；引擎也不能自动回滚已经发出的邮件或支付 |

### 软删除、审计、数据脱敏：删除按钮后面有三件事

| 步骤 | 选择 |
| --- | --- |
| 现实需求 | 误删可恢复、知道谁改过数据、客服查资料不能看到完整手机号 |
| 最小实现 | 仅有恢复需求时加 `deleted_at` 并统一默认过滤；审计记录操作者、动作、对象、时间和受控变更摘要；响应/日志按字段与角色脱敏 |
| 为什么引入 | 软删除支持回收站，审计支持追责与合规，脱敏减少暴露；三者可独立引入，不是同一能力 |
| 何时不需要 | 不需恢复的数据可按规则硬删除；不必保存每次全量敏感快照，更不必为普通 CRUD 引入事件溯源体系 |
| 失败边界 | 软删仍占存储，不等于满足隐私删除义务；唯一索引、关联查询、搜索索引、导出都要处理已删记录；普通应用日志不自动成为不可篡改审计；脱敏不等于加密/匿名化，原始数据访问与保留期仍要控制 |

### 消息通知：站内信、短信、邮件与实时推送各不相同

| 步骤 | 选择 |
| --- | --- |
| 现实需求 | 任务分配后提醒负责人，重要截止日发短信，普通更新发站内信 |
| 最小实现 | 通知记录表支持用户范围、未读数与已读状态；小规模先站内信，不先接所有渠道 |
| 为什么引入 | 邮件/短信触达不在线的用户；模板、偏好、限频、退订、异步投递与失败回执随需求增加；SSE/WebSocket 可改善在线实时体验 |
| 何时不需要 | 刷新列表即可满足的内部工具不必用 WebSocket；没有时效需求不必用收费短信 |
| 失败边界 | MQ 消费成功不等于用户收到，供应商“受理”也不等于送达；重复投递可能骚扰用户，需业务去重、费用限额、内容净化与隐私控制；WebSocket 断线不应丢掉站内信事实 |

### 字典、配置、Feature Flag：看起来都是 key/value，生命周期不同

| 步骤 | 选择 |
| --- | --- |
| 现实需求 | 任务优先级名称可维护、不同环境地址不同、新提醒功能只向小部分团队开放 |
| 最小实现 | 稳定状态码用代码枚举；可维护业务选项用字典表；运行参数用环境配置；简单新功能用服务端受控开关 |
| 为什么引入 | 字典管理业务编码与展示项；配置中心解决多环境和动态分发；Feature Flag 支持灰度、按团队放量与紧急关闭 |
| 何时不需要 | 三个不会变的优先级不必做万能低代码字典平台；单体少量配置不必先上配置中心 |
| 失败边界 | 字典 code 稳定，改展示名不应破坏历史数据；Secret 不混入普通可读配置；开关不是授权，前端关按钮不代表后端禁用；服务端判定要稳定、审计、定义配置源不可用时的默认值，旧开关要清理；关闭开关不能撤销已产生的副作用 |

## 39.3 一条克制的实现路线

1. **先跑通一个资源**：[CRUD](/back-end/frontend-backend-guide/07-build-a-crud-api) → [SQL](/back-end/frontend-backend-guide/10-sql-and-indexes) → [事务](/back-end/frontend-backend-guide/11-transactions-consistency)。
2. **先做正确再做更多功能**：[API 契约](/back-end/frontend-backend-guide/34-api-design) → [认证与数据范围](/back-end/frontend-backend-guide/32-security) → [测试](/back-end/frontend-backend-guide/35-testing)。
3. **耗时证据出现再异步**：[线程池](/back-end/frontend-backend-guide/15-thread-pools-executor) → [持久任务、幂等、outbox、MQ](/back-end/frontend-backend-guide/33-mq-reliability)。
4. **到交付时补运行闭环**：[配置](/back-end/frontend-backend-guide/25-config-and-env) → [可观测性](/back-end/frontend-backend-guide/30-observability) → [部署](/back-end/frontend-backend-guide/36-cicd-deployment) → [综合实战](/back-end/frontend-backend-guide/38-capstone-feature-to-prod)。
5. **最后评估架构升级**：[架构总览](/back-end/frontend-backend-guide/02-architecture-overview) 中的微服务方案，是在边界、独立发布和组织协作有证据时的选修，不是以上功能的入场券。

## 动手练习：给任务导出写一页需求评审

选一个需求：“团队管理员能导出昨天完成的任务，每天 08:00 自动生成报表。”先不写代码，用下面的清单补齐设计。

| 需要提交的内容 | 最小答案形态 |
| --- | --- |
| 谁能申请和下载 | 服务端确认的团队管理员；结果文件不能跨团队 |
| 数据与时间范围 | 显式时区，“昨天”采用半开时间区间；声明快照或近似读取 |
| 第一版实现 | 单体内持久 job + 有界 worker；小规模不引入 MQ/ES |
| 重复与失败 | 同团队、同报表类型、同业务日期唯一；重启恢复，永久失败可查询 |
| 存储与保留 | 私有文件，鉴权后短时下载；明确文件过期与清理 |
| 可观测与验收 | jobId 关联日志，最老任务年龄告警，两个团队交叉访问测试 |

**预期结果**：一页方案能让前后端明确接口状态、权限、等待过程与错误处理；列出“不做 MQ、不做分布式调度”的条件，而不是堆一串待安装组件。选做：按 [33 章练习](/back-end/frontend-backend-guide/33-mq-reliability#failure-exercises) 实现本地持久 job，验证重启与重复执行。

## 自测与答案

1. 有 `tenant_id` 字段就完成多租户了吗？

   **答案**：没有。所有读写路径及缓存、搜索、文件、后台任务都要落实可信租户范围，并测试跨租户访问。
2. 使用私有对象存储，为什么一份签名下载 URL 泄露后仍有风险？

   **答案**：签名 URL 通常是有效期内可使用的受限凭据，持有者可能直接下载；应用注销不必然撤销它。
3. 为何一万行导入不默认套一个超大事务？

   **答案**：锁、内存、回滚和超时成本高；先约定整体/部分成功语义，再选择分批或暂存发布，不能只凭注解决定业务语义。
4. 签名正确的支付通知能直接发权益吗？

   **答案**：还要验证商户、订单、金额、币种与事件状态，并在事务/唯一约束内幂等处理；合法通知也可能重放或乱序。
5. 为什么 SQL 查询变慢不立即上 ES？

   **答案**：先看查询形态、索引、数据量与性能证据；ES 增加异步一致性与运维成本，适合需要全文搜索能力的场景，不是所有慢 SQL 的解药。
6. Feature Flag 可以替代权限系统吗？

   **答案**：不能。开关决定功能是否开放，授权决定谁能对哪些资源做什么，两种检查要同时成立。
