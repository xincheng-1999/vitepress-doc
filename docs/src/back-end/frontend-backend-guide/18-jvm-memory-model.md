# JVM 内存模型：对象、调用栈和进程内存

::: info 按需阅读
这一篇回答“Java 进程的内存都用在哪里”，为 [GC](/back-end/frontend-backend-guide/19-garbage-collection) 和 [OOM 排查](/back-end/frontend-backend-guide/20-oom-memory-leak) 提供背景。它讨论的是 JVM 运行时内存区域，不是并发语义中的 **Java Memory Model（JMM）**；后者规定共享内存读写的可见性与顺序等规则。第一次学习可继续走 [五阶段主线](./index)。
:::

任务系统运行在一个内存上限为 2GiB 的容器里。有人把 `-Xmx` 也设成 2GiB，认为“把可用内存全部交给 Java 就行了”，结果容器还是因内存不足被终止。

问题在于：**`-Xmx` 只限制 Java 堆，不限制整个进程的内存。** 要看懂这句话，先从创建一条任务时产生的对象说起。

## 1. 方法返回了，对象为什么还在

看一个省略了业务类定义的片段：

```java
public Task createTask(String title) {
    int initialProgress = 0;
    Task task = new Task(title);
    task.setProgress(initialProgress);
    return task;
}
```

调用这个方法时，可以先用下面的模型理解：

```text
当前线程的调用栈                    堆
┌────────────────────┐          ┌──────────────────────┐
│ createTask 的栈帧    │          │ Task 对象             │
│ initialProgress = 0│          │ title ──→ String 对象 │
│ task ──────────────┼─────────→│ progress = 0          │
└────────────────────┘          └──────────────────────┘
```

**调用栈**记录线程正在执行哪些方法。每次方法调用都有相应的栈帧，用来保存局部变量、执行中的临时数据等；方法返回，相应调用结束。`task` 是局部引用，不是任务对象本身。

**堆**主要存放对象和数组。返回 `task` 时，调用方拿到了同一对象的引用，所以方法结束不代表对象被销毁。只要调用方或别处仍能通过有效的引用链访问它，它就可能继续存活；不再可达后，也不是当场消失，而是由 GC 在合适的时候回收。

不要把这简化成“基本类型都在栈，引用都在栈”。上面局部变量 `initialProgress` 是基本类型，但对象字段 `progress` 也存基本类型值，它属于对象；对象字段也可以保存指向其他对象的引用。HotSpot 的 JIT 还可能消除某些实际对象分配，示意图不是每一字节的物理布局。

Java 对象传参是**传递引用的值**：修改同一对象的字段，其他持有者能观察到；把形参重新指向另一对象，不会替调用方改掉它的变量。基础可回看 [Java 速成](/back-end/frontend-backend-guide/05-java-crash-course)。

## 2. 多条线程，各有调用栈，也可能指向同一对象

同一个 JVM 中，工作线程 A 和 B 各有自己的栈帧，但各自的局部引用可能都指向同一个堆对象。这就是为什么“局部变量不串”不代表“对象可以随意并发改”。

线程越多，需要的栈空间通常也越多。平台线程的栈大小受平台、JVM 和 `-Xss` 等影响，不是固定每条 1MB。深递归会不断增加调用层级，可能出现 `StackOverflowError`；创建太多平台线程则可能耗尽原生内存或系统线程配额，产生另一类错误。

运行时规范还定义了每线程的程序计数器和本地方法栈。前者可粗略理解为执行位置记录，后者服务于 native 方法调用；HotSpot 的具体实现不必与示意图逐块对应。读业务报错时，先分清调用栈与堆就够了，不需要为这些小区域逐项调参数。

JS 引擎也有对象存储、调用栈和 GC，使用 Worker 时也会有多条执行路径。它们不是前端完全看不到的黑盒，Chrome DevTools、Node 的诊断工具同样能观测内存；本篇只是改用 JVM 的术语和工具。

## 3. 堆之外，进程还在使用什么

把视角从一条任务放大到整个 Java 进程：

```text
Java 进程的内存，不止堆
  ├─ Java 堆：业务对象、数组等
  ├─ Metaspace 等：类元数据
  ├─ 线程栈：各线程的方法调用
  ├─ 直接内存等：部分 I/O 缓冲区
  └─ JIT 代码缓存、GC 数据结构、JVM 与本地库的其他开销
```

这些区域的使用量、保留量和操作系统看到的驻留内存，不是完全相同的指标，不能直接拿几项监控相加后认为一定等于容器用量。

### 类的说明与对象不是一回事

加载 `Task` 类时，JVM 需要保存类结构、方法等元数据。**方法区**是 JVM 规范中的概念；Java 17 的 HotSpot 使用本地内存中的 **Metaspace（元空间）**存放主要类元数据，不是简单把一块堆“改了名字”。

它与堆的边界也不能记成“所有 static 都在 Metaspace”。在现代 HotSpot 中，静态字段的存储与堆中的类镜像对象有关；静态字段引用的业务对象仍在堆中。长寿命的类及其静态字段，可以间接保持大量对象存活。

类也不是永远只加载一份、永远不能卸载。同一个名字可由不同类加载器加载为不同的类；类卸载需要满足相应条件。如果类加载器一直被保留，它加载的类元数据就可能无法回收。`OutOfMemoryError: Metaspace` 应从类数量、类加载器和上限等方向调查，不是直接增加 `-Xmx`。

### 直接内存也不受 Xmx 统一管理

一些网络、文件客户端会使用堆外缓冲区，例如 NIO 的直接缓冲区。它们占的是进程内存，却不等于 Java 堆用量；具体分配与释放方式还取决于使用的库。

所以，堆看起来没满，仍可能发生堆外内存问题，或者进程总用量触及容器限制。

## 4. 堆里的新生代和老年代，先理解目的

任务请求会产生许多临时对象：入参、转换结果、临时字符串。多数很快不再使用，少数对象如单例 Bean 或缓存则活得久。分代收集利用这种常见的生命周期差异，避免每次都对所有对象做同样的工作。

对于常见的分代收集器，可以先理解为：新对象通常在年轻区域分配，存活对象可能经过复制、年龄增长等过程进入老年代。**这不是所有收集器、所有对象都严格遵守的一条搬家路线。**

::: details 按需看：为什么不能把 Eden → Survivor → Old 当成固定规则
传统分代示意常画 Eden 和两个 Survivor 区；Java 17 常见的 G1 则把堆划为多个 Region，分别承担年轻代、老年代等角色。它还对占 Region 较大的对象作特殊处理。

对象的晋升不只由固定年龄决定，也与空间和收集器策略有关。“默认熬满 15 次才进老年代”“大于某阈值的数组一律直接进老年代”都不能脱离收集器使用；`PretenureSizeThreshold` 也不是 G1 的通用大对象开关。

同样，老年代未满时就可能启动相关回收，Full GC 也可能有多种触发原因。具体类型和原因应读实际 GC 日志，下一篇再解释。
:::

## 5. 认识参数，但先不要照抄调参

| 参数 | 控制什么 | 边界 |
| --- | --- | --- |
| `-Xms` | 初始堆大小 | 不等于启动时立刻驻留同样多的物理内存 |
| `-Xmx` | 最大堆大小 | 不是进程总内存上限 |
| `-Xss` | 平台线程栈大小的相关设置 | 调小可能增加栈溢出风险，行为依平台而异 |
| `-XX:MetaspaceSize` | 元空间相关的初始 GC 阈值 | 不是预先分配的固定元空间大小 |
| `-XX:MaxMetaspaceSize` | 元空间上限 | 需要结合实际类加载规模设置 |
| `-Xmn` | 某些收集器的新生代大小设置 | 不是初学必配项，固定它还可能干扰 G1 的自适应策略 |

例如下面是**启动参数的形状**，`app.jar` 代表你自己已经打包的应用，不是本页另外提供的文件：

```bash
java -Xms256m -Xmx512m -jar app.jar
```

它会启动应用并限制堆，不是读取当前进程的诊断命令。只在自己的实验环境使用，生产参数变更需要容量验证和发布流程。`Xms` 与 `Xmx` 设成相同值可以减少堆伸缩，但也可能减少弹性，不是任何服务都必须这样配。

如需让 OOM 留下堆快照，可使用 `-XX:+HeapDumpOnOutOfMemoryError` 和 `-XX:HeapDumpPath`，但需要预先安排磁盘容量、访问权限和数据保护，详见 [OOM 排查](/back-end/frontend-backend-guide/20-oom-memory-leak)，不要把采集快照当零成本操作。

## 6. 先读取现状，再判断哪里紧张

在授权的目标环境中，先核对 PID。下面都是读取信息，不修改堆大小；诊断仍有一定开销，应避免高频执行：

```bash
jps -l
jcmd <pid> VM.flags
jstat -gcutil <pid> 2000 5
```

`VM.flags` 可用于查看生效参数；`jstat` 每两秒采样一次，共五次，得到的列随 JDK 和收集器可能不同：

```text
  S0     S1     E      O      M     CCS    YGC    YGCT    FGC   FGCT    GCT
 0.00  31.25  68.40  45.12  96.30  92.10   128   1.245      3  0.890  2.135
```

这里 `E`、`O` 分别表示年轻区域和老年代的相关使用百分比，`YGC`、`FGC` 是相应计数，耗时列通常是累计秒数。看变化趋势比单个值有用：堆在分配后上升、回收后下降是常见现象；长期回收后水位持续抬高，值得继续分析存活对象，但不能只凭它认定泄漏。

`M` 接近 100% 也不等于元空间快到配置上限，它反映的通常是相对当前容量的使用比例，容量还可能增长。需要结合实际字节数、上限和类加载趋势。工具与版本注意事项见 [诊断工具箱](/back-end/frontend-backend-guide/29-diagnostic-toolbox)。

## 7. 回到 2GiB 容器：为什么不能把堆也设到 2GiB

堆之外还有元空间、线程栈、直接缓冲区和本地库等开销。把堆上限设到容器总限额，即使堆没用满，进程也可能因总用量超限被内核终止。应用日志不一定有 Java 的 `OutOfMemoryError`，因为这不是 JVM 自己完成的一次异常处理。

现代 JDK 17 通常具备容器感知能力，但仍要核对具体发行版、容器配置和实际生效的堆上限。不能把所有问题都归因于“JVM 误看成宿主机内存”。`MaxRAMPercentage` 是另一种按可用内存估算堆上限的方式，也没有替非堆内存自动预留一份适合所有业务的安全预算。

应该根据真实的堆存活量、线程数、堆外使用和负载峰值，为各部分留余量，再验证容器总用量。没有通用的“2GiB 容器必配 1.5GiB 堆”答案。看到退出码 `137` 只能先知道可能是 `SIGKILL`，还要结合 `OOMKilled` 状态、事件和系统记录确认原因，详见 [Kubernetes 实战](/back-end/frontend-backend-guide/24-kubernetes-in-practice)。

到这里，内存问题已经可以先分方向：对象太多看堆，调用太深看栈，类加载异常看元空间，容器超限看进程总用量。`StackOverflowError`、`OutOfMemoryError` 与普通异常的区别见 [Java 异常处理](/back-end/java/05-exception)；对象什么时候可以从堆里回收，继续看 [垃圾回收](/back-end/frontend-backend-guide/19-garbage-collection)。
