# 后端到底负责什么：从页面到可信的数据

> 学习目标：看到一个「新增任务」按钮，能说出服务器除了接收 JSON，还必须承担哪些责任。

前置：会发 `fetch` 请求即可。不需要先学 Java，也不需要先理解微服务。

## 1. 从你熟悉的页面出发

页面有标题输入框、任务列表、完成按钮。你已经会做 loading、校验、错误提示：

```ts
await fetch('/api/tasks', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: '学会写第一个接口' }),
})
```

后端不是「接过这段 JSON 放进一个数组」。它要回答：

1. **谁在调用？** 未登录还是已登录，凭证是否有效？
2. **允许做什么？** 能创建自己的任务，但不能替另一个用户创建。
3. **数据合法吗？** 标题空白、超长、错误类型，都不能因为绕过页面就被接受。
4. **数据存在哪？** 进程重启后任务还在不在？
5. **多个请求怎么办？** 两个人改同一条任务，不能悄悄覆盖彼此。
6. **失败怎么办？** 数据写入了但响应丢失，用户重试不能制造重复扣款。
7. **事后怎么查？** 错误必须能关联到一次请求，但日志不能泄露密码和 token。

![前端与后端共享契约，但服务器负责可信身份、规则和持久化](/backend-guide/core-responsibility.svg)

## 2. 不要把前后端理解成「简单 vs 复杂」

前端也有长期运行、资源泄漏、离线数据、SSR、安全和并发问题。后端并非天然都用 Java 多线程，Node.js 也是后端。真正的区别是**运行位置、信任边界和共享数据的范围**。

| 你熟悉的做法 | 到后端后需要补上的约束 |
| --- | --- |
| 表单禁用提交按钮 | 别人能直接用 curl 调接口，服务器仍须校验、鉴权、限流 |
| 把当前用户放在 store | 服务器不能用一个全局 `currentUser` 服务所有用户 |
| React Query 缓存接口结果 | 多用户共享缓存必须包含权限维度，还要处理过期和失效 |
| 失败后展示「请重试」 | 服务端可能已经执行成功；先定义哪些操作可以安全重试 |
| 本地 JSON mock | 生产数据要持久化、备份，并验证能恢复 |
| 前端路由守卫 | 只隐藏页面不构成授权，接口和每条数据都要检查权限 |

## 3. 三个位置：浏览器内存、服务内存、数据库

- **浏览器内存**：这个标签页的临时 UI 状态，刷新通常丢失。
- **服务进程内存**：某个运行实例自己的临时状态，重启丢失，另一个实例也看不到。
- **持久数据库**：在正确配置持久化、备份和恢复的前提下，作为业务事实源。

「无状态服务」不是说系统没有状态，而是**不要求下一次请求必须回到同一个服务实例才能正确处理**。用户任务、订单、会话可以存在进程之外。

第一版课程故意用 H2 内存数据库：先降低启动门槛，**它重启会丢数据**。这不是生产方案；后续迁移 MySQL 后才讨论持久化和备份。Redis 也不能因为叫「外置状态」就自动成为永不丢失的事实源。

## 4. 单线程也会竞态，多线程又多了什么

前端里你可能遇过：先搜索「A」，再搜索「AB」，A 的旧响应最后回来覆盖了新结果。这是**异步竞态**。

Node 服务里下面的代码同样可能丢更新：

```ts
// 错误示意：两个请求都读到旧值 10，然后都写回 11
const task = await db.read(id)
await db.write(id, { count: task.count + 1 })
```

Java 多线程还可能在同一时刻执行共享对象的字段读写。无论哪个语言，只要存在**共享可变状态 + 可交错执行**，都要考虑正确性。

学到这里先知道解决方向：数据库条件更新、唯一约束、事务、版本号。不是一遇到并发就加 Redis 锁。具体在 [事务与并发更新](./11-transactions-consistency) 动手验证。

## 5. 超时不是失败的确定证据

想象你创建任务，服务器已经提交数据库，但返回响应时网络断了。浏览器看到超时，数据库却有了任务。

- 「没有收到成功」≠「对方没有执行」。
- `AbortController` 停止客户端等待，**不保证服务器撤销已经开始的操作**。
- 对查询重试通常风险较低；扣费、发消息、创建订单要先定义业务幂等策略。

**幂等**指同一业务操作重复执行，不会额外产生业务副作用。不是要求每次 HTTP 状态码和响应文本都完全相同。

## 6. 每个工具都要有引入理由

| 遇到的问题 | 先做什么 | 之后才可能引入 |
| --- | --- | --- |
| 列表慢 | 限分页、查 SQL、看索引和数据量 | Redis 缓存 |
| 导出要一分钟 | 建持久任务记录、返回任务 ID | MQ、独立 worker |
| 单机处理不过来 | 测量瓶颈，检查数据库和资源上限 | 多实例与负载均衡 |
| 团队需独立发布模块 | 明确业务和数据边界 | 微服务、服务治理 |
| 几个进程容易部署错 | 配置分离、构建可重复 | Docker Compose；更多规模才考虑 K8s |

不要把「我用过多少中间件」当作学习进度。能解释**不使用它会遇到什么问题、使用它又带来什么问题**，才算理解。

## 动手：把一张前端需求单翻译成后端责任

需求：「用户能创建任务，查看自己的列表，把任务标成完成。」

先不写代码，写一页设计：

- 三个接口分别是什么？每个输入和输出是什么？
- 用户身份从哪里得到？为什么不直接相信 body 里的 `userId`？
- 哪些数据在任务表，哪些只在页面里？
- 两个标签页同时更新怎么办？
- 假设服务重启、数据库断开、重复提交，前端分别看到什么？

**预期产物**：一张接口表、一张数据归属图、一份失败场景清单。不要求现在实现所有保护。

## 自测与参考答案

1. 按钮已经防抖，后端还要防重复吗？**要。多个设备、直接调用和网络重试都能绕过按钮。**
2. `currentUser` 为什么不能放在单例 Service 字段？**不同请求共享对象，会串用户；身份应该来自已验证的请求安全上下文。**
3. 后端是否必须使用多线程？**不是。运行模型可不同，共享数据、权限和失败处理仍然是必须解决的问题。**
