# 一个“新增任务”按钮，为什么需要后端？

先做一个你熟悉的页面：输入任务标题，点击新增，任务出现在列表里。如果只是演示，把它放进一个数组就够了。

但用户接着提出了要求：“刷新以后还要在，换一台电脑也要能看到，而且只能看到自己的任务。”

后端要解决的问题，就从这里开始。

## 1. 先让任务离开当前页面

浏览器里的数组属于当前页面。刷新以后，它通常就没了。把数据存到 localStorage 可以解决一部分本机保存的问题，但另一台电脑并不会自动拥有这份数据。

因此，我们让一台大家都能访问的计算机负责接收和保存任务。运行在上面、处理这些请求的程序，就是这里说的后端应用。

页面不再直接决定任务是否保存成功，而是向后端发请求：

```ts
await fetch('/api/tasks', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: '学会写第一个接口' }),
})
```

这段代码告诉后端：“请创建一条标题为‘学会写第一个接口’的任务。”后端处理以后返回结果，页面再据此更新列表。

## 2. 后端接到数据，为什么还要检查？

你可能已经在表单里限制了标题不能为空。但别人可以不用这个页面，直接向接口发送空标题、数字，或者超长文本。

所以，页面校验负责尽早提醒用户，后端校验负责决定哪些数据真正能被接受。两边做了类似的检查，目的却不同。

再看“只能看到自己的任务”。前端隐藏其他人的任务还不够：用户可以修改请求里的 ID，尝试读取别人的记录。后端需要先确认调用者是谁，再检查这条任务是否属于他。

以后你会听到**认证**和**授权**：前者确认身份，后者判断这个身份可以做什么。这里先把它们和“查看自己的任务”对应起来，不用急着选登录框架。

## 3. 后端也有内存，为什么还需要数据库？

如果后端只把任务放进自己的数组，页面刷新后确实还能请求到它。但后端程序一重启，数组同样会消失。

为了长期保存，我们通常把任务交给数据库。后端收到新增请求，检查通过后写入数据库；收到列表请求，再从数据库查询并返回。

这样就能分清三个位置：页面内存保存当前界面需要的临时状态，后端内存保存程序运行时的数据，而配置了持久化的数据库负责长期保存任务。长期保存仍然需要备份和恢复，不能只靠“用了数据库”这件事。

课程的第一个实验为了方便启动，会先用 **H2 内存数据库**，不要求你安装 MySQL。它能让我们练完整的读写过程，但重启会丢数据；后面再学习如何用 MySQL 持久化。

## 4. 一个接口跑通后，还有哪些问题？

现在，“点击新增 → 后端检查 → 数据库保存 → 页面显示”已经连起来了。接下来遇到的问题，也可以放回这条过程里理解。

比如，两个人同时修改同一条任务，后保存的人可能覆盖前一个人的修改。这需要在更新数据时处理，我们会在 [事务与并发更新](./11-transactions-consistency) 中实际观察。

又比如，后端已经保存任务，返回结果时网络却断了。页面只看到了超时，再发一次请求就可能重复创建。以后讲重试时，要解决的就是“怎样确认这次操作是否已经完成”，而不只是给按钮加防抖。

这些不全是 Java 或多线程才有的问题。只要多个请求会访问同一份数据，使用 Node.js 等其他后端语言也需要考虑。

## 5. 先把这一个功能做完整

第一轮不用急着接 Redis、消息队列或微服务。我们先让一个任务能被创建、查询、修改和删除，再逐步加入登录、权限和可靠的保存方式。
