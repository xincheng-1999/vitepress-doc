# 系统地图：先单体，再认识中间件

> 学习目标：分清代码模块、进程、机器、服务、数据库、中间件，画出最小可用的系统。

前置：[后端的责任](./01-backend-mindset)。本章不要求安装任何软件。

## 1. 先拆开六个经常混用的词

| 名词 | 是什么 | 在任务系统里 |
| --- | --- | --- |
| 代码仓库 | 版本管理边界 | 一个 Git 仓库可包含前端和后端 |
| 模块 / 包 | 代码组织边界 | `task` 包和 `user` 包不一定独立运行 |
| 进程 | 操作系统中一个运行的程序实例 | 启动一次 `java -jar` 就有一个 Java 进程 |
| 线程 | 进程内的执行单元，共享部分内存 | 请求处理线程、后台任务线程 |
| 机器 / 服务器 | 提供 CPU、内存、网络、磁盘的运行环境 | 可以是你的电脑、云虚拟机或物理机 |
| 服务 / 实例 | 对外提供能力；实例是其中一个运行副本 | `task-api` 可在两台机器各运行一个实例 |

**服务不是必然一台机器，包不是必然一个服务，仓库也不是必然一个进程。** 一个进程能监听多个端口，一台机器也能运行多个进程。

## 2. 本课程的最小架构

![从本地 H2 到 MySQL 再到按需引入缓存和后台任务的系统演进](/backend-guide/core-system-map.svg)

### 第一步：只跑一个后端进程

```text
浏览器 / curl → task-api:8080 → H2（同一 Java 进程里的教学数据库）
```

Java 负责运行程序，Spring Boot 负责组装 Web 应用；内嵌 Tomcat 处理 HTTP，SQL 负责读写数据。**H2 不需要另开一个服务，但内存模式重启会丢数据。**

### 第二步：把数据库独立出来

```text
浏览器 → task-api:8080 → MySQL:3306
```

此时 MySQL 是独立数据库进程。应用重启不应影响数据库持久化的数据；不过磁盘损坏、错误删除仍可能造成数据损失，所以还需要备份和恢复。

浏览器**不能直接连接数据库**：那会暴露凭证、绕过权限与业务规则，还把数据库协议直接暴露在公网。

### 第三步：有需要再增加组件

| 组件 | 管什么 | 不管什么 |
| --- | --- | --- |
| Nginx / 反向代理 | 对外入口、静态文件、转发请求、TLS 终止 | 不能代替所有业务授权 |
| Redis | 缓存、短期共享数据、限流等 | 不能因为快就代替业务事务和事实源 |
| MQ | 在生产者和消费者之间传递消息、缓冲和解耦 | 不自动保证业务只执行一次，也不自动回滚数据库 |
| 对象存储 | 图片、附件、导出文件等对象 | 不同于 CDN，也不同于关系数据库 |
| Worker | 执行导出、转码等后台工作 | 不应该只把进度保存在内存 |
| 监控 / 日志平台 | 观察延迟、错误、资源和链路 | 不会替你定义正确的业务规则 |

这些常被统称为**基础设施 / 中间件**：给应用提供通用能力的运行组件。边界不是严格分类学，不必争一个组件到底属于哪一类，先明确职责与故障影响。

## 3. 什么是单体，什么是微服务

**单体**：多个业务模块一起构建、部署为一个应用。代码仍可以分层、按领域分包，并不是「全写在一个文件」。

**微服务**：一组有明确业务边界、能够独立部署的服务，通常拥有自己的数据边界，并通过网络通信。不是把 `controller`、`service`、`repository` 分别起进程。

| 方面 | 单体 | 微服务引入的新成本 |
| --- | --- | --- |
| 模块调用 | 进程内方法调用 | 网络、序列化、超时、重试 |
| 本地开发 | 一个应用与数据库 | 多服务版本、地址、启动依赖 |
| 一致性 | 同库事务通常较直接 | 跨服务不能靠普通本地事务一起回滚 |
| 发布 | 应用整体发布 | 需兼容契约、处理滚动升级与回滚 |
| 优点 | 起步简单、容易跟完整链路 | 独立发布、扩缩容和团队自治 |

所以主线先做单体。公司用了微服务，也可以先在其中**一个业务服务内部跟通一个接口**，再看网络边界。

## 4. 单体不等于单实例

同一个单体应用可以部署两个相同副本，由负载均衡分配流量：

```text
                    ┌→ task-api 实例 A ─┐
浏览器 → 负载均衡器 ┤                   ├→ 同一个 MySQL
                    └→ task-api 实例 B ─┘
```

这叫**横向扩容**。如果两次请求分别落到 A、B，A 内存里的任务 B 看不到，所以任务应该在共享持久存储中。共享数据库也可能成为瓶颈，增加实例不是无限提升性能。

**纵向扩容**则是增加一台机器的 CPU / 内存。先测量 CPU、SQL、网络、连接池谁受限，不要只加机器。

## 5. 用一次新增任务分清协议和调用

- 浏览器 → 应用：HTTP，JSON 作为数据格式。
- 应用 Controller → Service：普通 Java 方法调用，不经过 HTTP。
- Service → Repository：仍是 Java 方法调用。
- JDBC 驱动 → MySQL：数据库协议，经 TCP 连接。
- H2 内嵌模式：进程内访问，不需要与独立 MySQL 服务器建立 TCP。

**JSON 不是 HTTP，TCP 不是 HTTP，接口也不是只能叫 HTTP 接口。** 协议是通信规则，数据格式是内容如何编码。

## 动手与自测

画出你正在开发的前端页面实际依赖的系统，只写你能证实的部分。问同事：「这个接口在哪个服务？外面有没有代理？数据在哪个库？本地需要哪些依赖？」不要凭名字猜架构。

**参考答案**：

1. 一个 Git 仓库里有五个目录，就是五个微服务吗？**不是。要看运行和部署边界。**
2. 单体能不能同时服务很多用户？**能，容量取决于实现和资源；单体不是单线程或单用户。**
3. 本课程第一版的 H2 和后面的 MySQL 最大差异是什么？**首先是运行与持久化方式；H2 内存版免安装但重启丢数据。SQL 方言、锁和执行计划也不能假设完全相同。**
