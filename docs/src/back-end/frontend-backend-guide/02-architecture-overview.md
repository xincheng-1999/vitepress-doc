# 任务系统里，哪些东西需要运行起来？

上一篇知道了，页面要把任务交给后端保存。接下来先认清它们各自运行在哪里，免得还没写接口，就被“服务、实例、中间件”这些词绕住。

## 1. 先在自己的电脑上运行

学习时不需要先买云服务器。你的电脑既可以运行浏览器，也可以运行后端程序。

本课程的后端叫 `task-api`。启动它，就有一个 Java 程序在运行；操作系统把这样一个正在运行的程序叫作**进程**。它监听 8080 端口，等待浏览器或 curl 发来请求。

最初的结构很简单：

```text
浏览器或 curl → task-api:8080 → H2
```

这里的 H2 是嵌在 Java 进程里的教学数据库，不需要单独启动另一台数据库服务器。整个后端在本机就能跑起来，不过这个内存数据库重启后会丢数据。

这也能帮助理解“服务器”这个词：有时同事指的是提供计算资源的机器，有时说的是机器上提供服务的程序。遇到“服务器启动了吗”，最好确认他问的是哪一个。

## 2. 需要长期保存时，再单独运行数据库

换成 MySQL 后，结构多了一项需要独立运行的程序：

```text
浏览器 → task-api:8080 → MySQL:3306
```

任务仍然由后端接收和检查，只是保存时要连接 MySQL。两者可以运行在同一台机器，也可以在不同机器上。

此时后端重启，数据库里已经保存的任务仍然可以保留。以后部署时，我们还要配置数据存储和备份，才能应对误删或磁盘故障。

浏览器不直接连接 MySQL。数据库密码留在服务端，后端检查用户和业务规则后，再决定执行什么查询。否则，用户绕过页面就可能直接操作数据库。

## 3. 为什么先做“单体”？

假如任务系统有任务管理、用户管理、通知三个功能，我们可以把它们放在同一个应用里，一起启动和发布。这就是**单体应用**。

它仍然可以按功能分目录、分模块，不是把所有代码塞进一个文件。第一轮用这种方式，更容易从一个请求跟到数据库，不用同时启动一堆服务。

以后某些功能确实需要由不同团队独立发布，可以考虑拆成多个通过网络通信的服务，也就是微服务。但拆开以后，还要处理服务地址、调用失败、版本兼容等问题。我们先把一个应用内部的工作过程学明白，再讨论这些额外问题。

代码放在几个仓库、分成几个文件夹，都不能单独说明是不是微服务。要看它们是否独立运行、怎样构建和发布。

## 4. 单体也可以运行多个副本

一个应用不代表只能运行一份。用户变多后，可以在两台机器上各启动一份相同的 `task-api`。每一份运行中的副本，通常叫一个**实例**。

```text
                    ┌→ task-api 实例 A ─┐
浏览器 → 负载均衡器 ┤                   ├→ 同一个 MySQL
                    └→ task-api 实例 B ─┘
```

负载均衡器把请求分给不同实例，这叫横向扩容。因为两次请求可能交给不同实例处理，任务就不能只存在 A 的内存里，要让它们能够访问同一份持久数据。

另一种方式是给原来的机器增加 CPU 或内存，叫纵向扩容。选哪种方式，要看实际慢在哪里；数据库查询慢时，只增加应用实例可能没有帮助。

## 5. 图里其他组件，什么时候才需要？

先有任务应用和数据库，就能完成基本业务。之后每增加一个组件，都应该能说清它在解决什么问题。

例如，对外统一提供 HTTPS 入口时，可以引入 Nginx 等反向代理；列表查询确实需要缓存时，再考虑 Redis；导出文件耗时太久时，可以交给后台任务处理，必要时用消息队列传递任务通知。

这些为应用提供通用能力的组件，经常被称作“中间件”或“基础设施”。现在只需知道它们是按需求增加的，不是启动第一个接口之前必须安装的清单。
