# 05 App Store Connect 后台配置

App Store Connect 像「应用发布平台 + 商品管理 + 测试分发 + 部分运营后台」。它不会替你实现业务登录、会员数据库或 App 页面。

本章按工作目标解释入口。界面语言、角色、平台和苹果页面改版可能导致栏目名称或位置变化；未实际登录的后台页没有配成功截图，以下路径以官方帮助为依据。

## 1. 首页入口分别做什么

| 入口 | 配置 / 查看内容 | 不负责什么 |
| --- | --- | --- |
| Apps（App） | 商店 App 记录、版本、构建、内购、订阅、TestFlight | 不注册签名私钥 |
| Users and Access | 团队用户、角色、App 访问、沙盒测试者及相关集成权限 | 不管理你 App 的手机号用户 |
| App Analytics | 商店及 App 的使用、转化等指标，按权限和可用数据提供 | 不等于你后端完整业务分析 |
| Sales and Trends | 销售、下载、内购和订阅等趋势 | 不直接修改某个业务用户的会员 |
| Payments and Financial Reports | 结算及财务报表 | 不作为客户端每次支付的即时验单接口 |
| Business（旧界面可能称 Agreements, Tax, and Banking） | 协议、税务、银行账户等 | 不决定客户端使用哪个测试域名 |

你看不到某个入口，先核对团队和角色。不要把权限不足误当作后台没开通。

## 2. 创建 App 记录：让商店知道这个 App

前提：正确团队中已注册 Bundle ID，账户持有人处理了当前要求的协议，操作者拥有创建 App 的角色。

路径：**Apps → “+” → New App**。

| 字段 | 怎么理解 | 常见错误 |
| --- | --- | --- |
| Platform | iOS 等支持平台 | 与当前要上传的构建平台不一致 |
| Name | 商店中的 App 名称 | 当成 Bundle ID 填写；名称可用性及长度以页面为准 |
| Primary Language | 商店元数据的主语言 | 不等于必须实现多语言 App |
| Bundle ID | 从团队注册的标识符中选择 | 选到另一个产品或测试包身份 |
| SKU | 团队内部管理用的唯一标识，不对用户展示 | 当成苹果内购商品 Product ID |
| User Access | 谁能在团队里管理这款 App | 忘记给开发者分配 App，导致其登录后列表为空 |

创建后苹果会生成商店 App 的**数字 Apple ID**。这里的“Apple ID”不是账号邮箱，做服务端交易通知校验时有时会用到这个数字。

App 记录创建成功，不表示已上架，也不表示上传过构建。先准备记录，之后才有版本、构建、审核和销售状态。

## 3. 版本号与构建号

| 字段 | iOS 对应 | Flutter 对应例子 | 用途 |
| --- | --- | --- | --- |
| Version | `CFBundleShortVersionString` | `1.2.0+42` 中的 `1.2.0` | 用户看到的产品版本 |
| Build | `CFBundleVersion` | `1.2.0+42` 中的 `42` | 区分同版本不同编译产物 |

修复一个 1.2.0 测试包，可重新上传 1.2.0 / 43，再在版本页选择新构建。不要重复上传同一版本下已使用的构建号，或以为本地文件名不同就代表新的构建。

业务域名、权限、SDK 行为等配置变化，也要明确对应哪次构建。不能仅凭商店版本号判断手机上是哪一份二进制。

## 4. App 信息与商店展示

| 配置 | 作用 | 准备方法 |
| --- | --- | --- |
| 分类、内容与年龄分级 | 帮商店正确展示和限制受众 | 按实际内容填写问卷，不是为了更容易过审随意选 |
| 名称、副标题、描述、关键词 | 帮用户理解和找到产品 | 与实际交付功能一致 |
| 图标、截图、预览视频 | 商店展示 | 按苹果当期要求的设备规格准备，使用真实可交付界面 |
| 支持 URL | 用户找帮助 | 提供可访问且能联系到支持方的页面 |
| 隐私政策 URL | 解释数据处理 | 与 App 及 SDK 实际行为一致 |
| 版权、联系信息 | 归属与沟通 | 使用真实授权主体 |
| 国家/地区、价格与可用性 | 决定在哪些商店出售或开放 | 检查区域限制、合规要求和产品策略 |

有用户账号的 App 还要按适用审核要求提供账户删除等能力；登录或短信限制会影响审核，应提供可用的审核方式。

## 5. App Privacy、Privacy Manifest 和权限弹框

这三者可以类比成：产品对外披露、代码依赖声明、用户现场授权。但类比不意味着可以只保留一项。

| 层次 | 在哪里 | 回答的问题 |
| --- | --- | --- |
| App Privacy 隐私标签 | App Store Connect | 你和第三方 SDK 收集哪些数据，是否关联身份、是否用于追踪 |
| Privacy Manifest | App / SDK 内的 `PrivacyInfo.xcprivacy` 等 | 特定隐私行为、必要理由 API 等声明 |
| 用途说明与系统弹框 | Info.plist + 原生权限 API | 此次为什么访问相机、相册、定位等，用户是否允许 |
| ATT 授权（适用时） | App 内系统流程 | 是否允许相关跨 App / 网站追踪，不是普通登录或所有统计都自动属于追踪 |

不要照抄别人的隐私标签。即使业务代码没采集某项数据，广告、统计、崩溃等 SDK 也可能涉及它。提审前应让客户端、后端和产品一起核对。

## 6. 审核信息：让审核员能走到核心功能

版本页一般需要提供：审核联系人、演示账号（如果功能需要登录）、备注、必要的附件、选中的构建等。

审核备注应写具体路径，例如：

> 启动后进入“我的 → 登录”，使用所提供的测试账号登录；会员入口位于“我的 → 会员中心”。测试账号已具备进入核心功能的必要条件。购买由苹果内购完成。

不要在公开教程或 Git 中写真实审核账号密码。若验证码、地域网络、企业白名单限制了访问，应提前提供可行方案，不能只写“请联系开发者”。

## 7. 商务设置为什么会影响支付

开发者会员有效，不等于所有收费相关协议都已生效。要销售付费 App 或内购，需满足苹果要求的付费应用协议及相关税务、银行等配置。

出现无法销售、商品状态异常时，让账户持有人或相应管理人员查看 Business 状态。签协议、修改收款信息属于组织事务，不应由开发者为了测试随意操作。

## 8. 内购、订阅、通知和密钥的入口

在目标 App 下分别管理 **In-App Purchases** 和 **Subscriptions** 等内容；沙盒测试者通常位于 Users and Access → Sandbox。

需要服务端查询交易时，还会用到 App Store Server API 的相应密钥配置。自动通知则在 App 的 App Store Server Notifications 配置中填写服务器 URL。完整字段关系与实际流程见 [下一章](/apple-development/06-in-app-purchase)。

## 本章验收

你能找到目标 App，核对 Bundle ID 和数字 Apple ID；知道当前版本选择了哪个构建；知道隐私、审核、商务和内购配置分别由谁负责。
