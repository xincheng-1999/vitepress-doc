# 07 TestFlight、审核与正式发布

到这里你已经能运行 App，理解签名和支付。本章把开发产物交给测试者，再走到 App Store 正式发布。

## 1. 不同交付物不要混用

| 产物 | 是什么 | 能做什么 |
| --- | --- | --- |
| 模拟器 `.app` | 面向模拟器架构和运行环境的应用 | 在模拟器运行，不能当作 iPhone IPA 安装 |
| 真机 `.app` | 设备架构应用目录 | 在签名与安装条件满足时由开发工具安装 |
| `.xcarchive` | Xcode 归档，包含应用、符号等相关信息 | 供验证、导出或上传，并保留崩溃符号资料 |
| `.ipa` | iOS 分发安装包容器 | 可用安装途径取决于其签名和分发类型，不是任意 iPhone 都能装 |
| App Store Connect Build | 上传后经苹果处理的构建记录 | 选择用于 TestFlight 或某个版本的审核 |

前端 `dist` 上传到静态服务器就能被浏览器访问，iOS IPA 则还受签名和分发机制限制。

## 2. 从 Xcode 归档到上传

在主 App 工程或 workspace 中：

1. 确认源代码、依赖、业务环境、Bundle ID、版本号和构建号。
2. 选择正确 Scheme 和设备归档目标，不能选 iPhone Simulator 来生成商店归档。
3. 执行 **Product → Archive**。
4. 在 **Window → Organizer → Archives** 找到本次归档。
5. 检查版本、团队和标识，执行验证，再按界面选择 **Distribute App → App Store Connect** 的上传流程。
6. 处理签名、能力、导出合规等校验提示。
7. 上传完成后，等待 App Store Connect 处理构建；上传成功不等于处理成功或已发布。

不同 Xcode 版本的分发向导名称可能变化，应以实际目标“上传 App Store Connect”判断。使用 CI、Transporter 或 Flutter 构建命令也遵循相同身份和分发要求。

如果这是首次建原生练习项目，可从 Xcode → File → New → Project → iOS App 开始，选择团队和唯一 Bundle ID，先做一页能运行的 UI。不要一开始就添加推送、内购、登录等所有能力。Flutter 项目则使用团队已有的工程初始化方式，随后打开生成的 workspace。

## 3. TestFlight 内部与外部测试

路径：**App Store Connect → 目标 App → TestFlight**。

| 类型 | 面向谁 | 主要条件 |
| --- | --- | --- |
| 内部测试 | 有适当角色及 App 访问权的 App Store Connect 用户 | 不是组织里任何员工都自动成为内部测试者 |
| 外部测试 | 非后台成员的测试者 | 配置测试信息和分组，构建可能需要 Beta App Review；首次外部测试构建需审核 |

按当前官方说明，内部测试最多 100 名具备条件的用户，外部最多 10,000 名；构建可测试最多 90 天。规则可能变化，配置时查看后台限制。

操作顺序：

1. 找到处理完成的构建，补齐出口合规等尚未完成的信息。
2. 填写 What to Test、测试说明、联系人及必要登录信息。
3. 创建内部或外部测试组，添加构建和测试者。
4. 外部测试如需审核，等待相应批准后再邀请。
5. 测试者安装 TestFlight，接受邀请，安装指定构建。
6. 收集反馈、崩溃及设备信息，修复后递增构建号上传。

TestFlight 通常不需要管理员收集每个测试者的 UDID，也不要求每个人付费注册开发者会员。只有为了协作管理后台，才按职责赋予后台成员权限。

**TestFlight 支付是沙盒测试，App Store 正式版本中的付款才是正式交易。** 使用同一业务后端时仍要明确沙盒交易的权益处理规则。

## 4. App Store 送审前，把四类材料对齐

| 类别 | 需要确认 |
| --- | --- |
| 二进制 | 无测试开关、演示账号或调试入口误入正式配置；签名、能力、系统版本、SDK 符合当期要求 |
| 商店材料 | 名称、说明、截图、年龄分级、支持 URL、隐私政策、地区和价格等已填写 |
| 隐私与合规 | 隐私标签、SDK 行为、Privacy Manifest、权限用途说明、出口合规、适用地区备案或许可等真实一致 |
| 审核与业务 | 审核员可进入核心流程；接口和账号可用；内购关联正确；收费协议等已完成 |

不要背一份固定的“今年最低 Xcode 版本”永久执行。上传前查看 [Upcoming Requirements](https://developer.apple.com/news/upcoming-requirements/)，不同平台、SDK 和区域要求可能更新。

中国大陆等目标地区可能有额外备案、许可及内容要求；这是产品上线条件，不能用签名成功代替。

## 5. 提交、审核与发布的顺序

1. 在目标 App 的版本页选择正确构建。
2. 检查 App 信息、审核资料和关联内购等提交项。
3. 按页面提示添加到审核并完成最终提交。
4. 关注待审核、审核中、待补充信息、被拒或批准等状态。
5. 若有拒审意见，逐条回复或修复；如果修改了二进制，就需要新的构建。
6. 按已选择的手动、自动或适用的分阶段发布方式上线。
7. 确认目标地区商店实际可见、版本正确，再验收下载、登录及关键业务。

“审核通过”和“用户已经能下载”可能不是同一时刻，例如选择手动发布后还要执行发布操作，商店同步也需要时间。不要仅凭上传日志宣布上线。

## 6. 发布后还要做什么

- 监测崩溃、启动、登录、接口错误和支付成功率；注意不同 iOS 和机型。
- 保留构建对应的符号资料，才能把崩溃堆栈还原到源码位置。
- 监测 App Store Server Notifications、补单任务和权益异常。
- 管理证书、描述文件、服务端 API 密钥及会员续费；它们有不同的有效期和轮换方式。
- 发布更新时保持 App 身份，维护版本和构建号、数据库/本地数据兼容性。
- 出现事故时，可以暂停适用的分阶段发布或关闭可控的服务端功能；商店二进制不能像网页那样保证一键让所有用户回退，通常需要新的修复版本。

## 7. CI/CD 如何参与

当手动流程稳定后再自动化：安装锁定依赖 → 静态检查与测试 → 构建归档 → 签名 → 验证 → 上传 → 收集版本和结果。

CI 需要有明确的凭据类型、最小权限和受控存储。例如用于上传的 App Store Connect API Key，与用于 App Store Server API 验单的密钥不能只因为都是 `.p8` 就互相替代；按 API 和密钥权限确认。

不能把本机成功归因于“仓库里已有所有签名材料”，因为本机钥匙串或 Xcode 登录态可能承担了关键步骤。新 CI 机器需要独立准备签名方式、证书私钥或受支持的云签名条件。

## 本章验收

至少分别记录：归档成功、上传成功、苹果处理完成、TestFlight 安装运行、审核状态、发布状态、商店实际可下载。每个阶段有各自证据，不用一个“打包成功”概括全部。
