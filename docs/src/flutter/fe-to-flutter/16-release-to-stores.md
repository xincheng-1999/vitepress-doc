# 第十六章：内测、上架与持续交付

发布目标是让用户安装后可完成任务，发现问题后也有处置路径。AI 可以整理材料、生成检查清单，但账号、隐私声明和发布决策必须与真实产品行为一致。

## 16.1 先交付内测包

交付给测试者的材料至少包含：安装方式、版本号、支持系统、可测试功能、已知限制、反馈入口。主线离线笔记应明确“卸载可能丢失本地数据”，不承诺尚未实现的云备份。

同一个待发版本经过新安装、覆盖升级与冷启动验证后再扩大分发。没有必要第一轮就把账号、支付、推送都加入项目，它们分别需要新的业务设计和验收。

## 16.2 Android 发布路径

1. 确认 applicationId、展示名称、图标、版本号与正式签名。
2. 构建 AAB，按 Play Console 流程配置 App Signing 并上传内部测试轨道。
3. 填写商店资料、截图、内容分级、数据安全、权限用途与隐私政策。
4. 若有账号，提供审核访问方式；核对账号删除等适用要求。
5. 根据当前账号和地区要求完成必要的测试与审核，再逐步扩大发布。

Google Play 之外的 Android 商店有各自要求，不能把 Play 清单当作统一规则。target API、测试资格、媒体权限政策等会变化，发版时查当前控制台与官方要求，不从旧教程复制日期或固定人数。

通过 Play 分发后的应用签名可能与本地上传签名不同。涉及登录 SDK、地图或支付时，用真实轨道安装包再验证证书相关功能。

## 16.3 iOS 发布路径

1. 在开发者后台和 App Store Connect 建立匹配 Bundle ID 的应用记录。
2. 通过 Xcode Archive 或 `flutter build ipa` 生成合适的签名产物并上传。
3. 等待处理完成，补充出口合规等信息，发给 TestFlight 测试者。
4. 根据内外部测试规则完成对应审核与邀请。
5. 提交商店版本、截图、隐私说明、审核备注与可用测试账号。
6. 审核通过后按产品安排发布，并观察首批用户反馈。

隐私清单（Privacy Manifest）、Required Reason APIs 与 App Privacy 回答要覆盖应用及第三方 SDK 的实际行为。模型无法仅凭应用名称替你准确声明“没有收集任何数据”。

## 16.4 发布验收表

| 类别 | 必须看到的证据 |
| --- | --- |
| 核心业务 | 新建/编辑/删除、失败重试、重启数据仍在 |
| 升级 | 旧版数据在新包中可读，迁移成功 |
| 平台交互 | 返回、键盘、大字体、权限拒绝、后台恢复 |
| 网络扩展 | 超时、取消、401、重试不重复写入 |
| 图片扩展 | 长期存储、取消清理、丢失占位与恢复 |
| 环境 | 生产地址、签名、版本、日志脱敏正确 |
| 产品材料 | 截图与当前版本一致，声明与实际数据流一致 |

测试“返回首页了”不等于保存成功；测试“新装能启动”不等于旧用户升级不丢数据。用实际用户任务描述验收，而不是列出几十个按钮名称。

## 16.5 CI 从可复现开始

CI 固定 Flutter 版本，使用应用提交的 pubspec.lock，执行依赖解析、format 检查、analyze 和测试。Android 在配好 Android 工具链的 runner 构建，iOS 需要 macOS 与对应 Xcode；签名材料通过受控 secret 注入。

保存构建日志、符号文件、测试结果和版本信息，确保线上崩溃能对应到源码。不要让 CI 在每次运行时自动升级所有依赖，然后宣称构建可复现。

## 16.6 发布后的恢复策略

先小范围分发并监控崩溃、启动失败、保存失败等关键指标。商店发布后不能假定随时让所有用户立即退回旧包；通常需要暂停扩大分发、修复后发布更高版本构建。

数据库已经前向迁移后，旧二进制不一定能读新 schema。设计迁移时就考虑兼容与备份，发布前验证；不要用“卸载重装”当作数据型应用的默认客服方案。

## 16.7 最后的能力验收

让 AI 帮你在随手记上新增一项「搜索本地笔记」功能。你应能自行定义搜索范围、空结果、大小写、状态归属与测试，读懂模型改动，定位一次失败，然后交付一个可安装版本。

如果这些步骤可以完成，你已经具备继续开发的基础。下一阶段按产品需要学习同步、推送、后台任务、原生通道或动画，不需要先把所有 Flutter API 学完。
